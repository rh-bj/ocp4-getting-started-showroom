== 배경지식: Secret

=== Secret을 사용하는 목적

앞의 ConfigMap 실습에서는 애플리케이션의 설정 정보를 Deployment와 분리하여 관리하는 방법을 살펴보았습니다.

하지만 모든 설정값을 ConfigMap에 저장하는 것은 적절하지 않습니다.

예를 들어 다음과 같은 정보는 외부에 노출되어서는 안 되는 **민감한 정보**입니다.

* 데이터베이스 사용자 이름과 비밀번호
* API Token
* TLS 인증서와 Private Key
* SSH Key
* 이미지 레지스트리 인증 정보

쿠버네티스의 ``Secret``은 이러한 **민감한 데이터를 애플리케이션 코드나 컨테이너 이미지와 분리하여 저장하고 Pod에 전달하기 위한 리소스**입니다.

ConfigMap과 Secret은 모두 key-value 형태의 데이터를 저장하고 Pod에서 사용할 수 있다는 점에서는 비슷하지만, 사용 목적이 다릅니다.

[cols="1,2,2",options="header"]
|===
|리소스
|용도
|예

|ConfigMap
|기밀이 아닌 애플리케이션 설정
|DB 주소, API URL, 로그 레벨

|Secret
|민감한 정보
|Password, Token, 인증서 Key
|===

예를 들어 애플리케이션에서 다음과 같은 데이터베이스 접속 정보가 필요하다고 가정해 보겠습니다.

[source,text]
----
DB_USER=MyUserName
DB_PASSWORD=mypassword
----

이 값을 애플리케이션 코드나 컨테이너 이미지 안에 직접 포함하면 해당 코드나 이미지를 볼 수 있는 사람에게 자격 증명이 노출될 위험이 있습니다.

대신 Secret에 민감한 데이터를 저장하고, Pod에서 필요한 Secret만 참조하도록 구성할 수 있습니다.

Pod에서는 Secret의 값을 대표적으로 다음 두 가지 방법으로 사용할 수 있습니다.

* **환경 변수**로 전달
* **Volume을 통해 파일**로 마운트

앞의 ConfigMap 실습에서는 환경 변수 방식을 사용했으므로, 이번 실습에서는 Secret을 **Volume으로 마운트하여 파일로 사용하는 방법**을 살펴봅니다.


=== Secret의 값은 어떻게 저장될까?

Secret의 내용을 YAML이나 JSON 형식으로 조회하면 실제 문자열 대신 ``Base64``로 인코딩된 값이 보입니다.

예를 들어 다음과 같은 Secret이 있다고 가정해 보겠습니다.

[source,yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=
  password: cGFzc3dvcmQ=
----

``YWRtaW4=`` 값을 Base64로 디코딩하면 다음과 같이 원래 값을 쉽게 확인할 수 있습니다.

[source,bash]
----
echo 'YWRtaW4=' | base64 --decode
----

[source,text]
----
admin
----

[IMPORTANT]
====
**Base64는 암호화가 아닙니다.**

Base64는 데이터를 문자열 형태로 표현하기 위한 **인코딩 방식**일 뿐이며 누구나 쉽게 원래 값으로 되돌릴 수 있습니다.

따라서 Secret의 값이 Base64 형태로 표시된다는 사실 자체가 데이터를 보호해 주는 것은 아닙니다.
====

Secret을 사용하는 중요한 이유는 민감한 데이터를 애플리케이션 코드나 Deployment 정의와 **분리하여 관리할 수 있고**, Kubernetes/OpenShift의 권한 제어를 통해 Secret에 대한 접근을 제한할 수 있기 때문입니다.

하지만 Secret 자체를 비밀번호 관리 시스템이나 암호화 저장소와 동일하게 생각해서는 안 됩니다.

실제 운영 환경에서는 다음과 같은 보안 설정도 함께 고려해야 합니다.

* RBAC을 이용하여 Secret을 읽을 수 있는 사용자를 최소화
* 필요하지 않은 사용자나 ServiceAccount에 Secret 접근 권한을 부여하지 않기
* etcd의 저장 데이터 암호화 사용
* 필요한 경우 외부 Secret 관리 시스템과 연동

이번 실습에서는 Secret의 기본적인 생성 및 Pod 전달 방법에 집중합니다.

=== Secret 생성하기

이제 애플리케이션에서 사용할 데이터베이스 계정 정보가 있다고 가정해 보겠습니다.

이번 실습에서는 다음 값을 사용합니다.

[source,text]
----
user=MyUserName
password=mypassword
----

NOTE: 실제 운영 환경의 자격 증명이 아닌 **실습용 예제 값**입니다.

``oc create secret generic`` 명령을 사용하면 일반적인 key-value 데이터를 저장하는 Secret을 만들 수 있습니다.

터미널 1에서 다음 명령어를 실행합니다.

[#create-secret-cli-secrets]
[.console-input]
[source,bash]
----
oc create secret generic mysecret \
  --from-literal=user='MyUserName' \
  --from-literal=password='mypassword'
----

생성된 Secret을 확인합니다.

[#get-secret-cli-secrets]
[.console-input]
[source,bash]
----
oc get secrets
----

환경에 따라 다음과 비슷한 결과가 표시됩니다.

[.console-output]
[source,bash]
----
NAME                       TYPE                             DATA   AGE
builder-dockercfg-xxxxx     kubernetes.io/dockercfg        1      10m
default-dockercfg-xxxxx     kubernetes.io/dockercfg        1      10m
deployer-dockercfg-xxxxx    kubernetes.io/dockercfg        1      10m
mysecret                   Opaque                           2      5s
----

TIP: 기본적으로 보이는 Secret의 종류와 개수는 클러스터 구성에 따라 다를 수 있습니다. 이번 실습에서 직접 생성한 것은 ``mysecret``입니다.

``TYPE``이 ``Opaque``인 것을 확인할 수 있습니다.

``Opaque``는 특정 용도가 정해져 있지 않은 일반적인 key-value 형태의 Secret입니다.


=== Secret의 데이터 확인하기

먼저 ``describe`` 명령으로 Secret을 확인합니다.

[#describe-secret-cli-secrets]
[.console-input]
[source,bash]
----
oc describe secret mysecret
----

[.console-output]
[source,bash]
----
Name:         mysecret
Namespace:    myspace
Labels:       <none>
Annotations:  <none>

Type:  Opaque

Data
====
password:  10 bytes
user:      10 bytes
----

``describe`` 결과에서는 실제 Secret 값 대신 각 값의 크기만 표시됩니다.

이번에는 YAML 형식으로 확인해 봅니다.

[#get-secret-cli-yaml-secrets]
[.console-input]
[source,bash]
----
oc get secret mysecret -o yaml
----

[.console-output]
[source,yaml]
----
apiVersion: v1
data:
  password: bXlwYXNzd29yZA==
  user: TXlVc2VyTmFtZQ==
kind: Secret
metadata:
  name: mysecret
  namespace: myspace
type: Opaque
----

이번에는 값이 보이지만 우리가 입력했던 문자열과 다릅니다.

----
mypassword
          ↓ Base64
bXlwYXNzd29yZA==
----

Secret의 ``data`` 필드에는 값이 Base64로 인코딩되어 저장되기 때문입니다.

직접 디코딩해 봅니다.

[#get-secret-cli-password-secrets]
[.console-input]
[source,bash]
----
echo 'bXlwYXNzd29yZA==' | base64 --decode
----

[.console-output]
[source,text]
----
mypassword
----

사용자 이름도 확인할 수 있습니다.

[#get-secret-cli-username-secrets]
[.console-input]
[source,bash]
----
echo 'TXlVc2VyTmFtZQ==' | base64 --decode
----

[.console-output]
[source,text]
----
MyUserName
----

Secret에서 값을 직접 가져와 디코딩할 수도 있습니다.

[#get-secret-oc-password-secrets]
[.console-input]
[source,bash]
----
oc get secret mysecret \
  -o jsonpath='{.data.password}' | base64 --decode
----

[.console-output]
[source,text]
----
mypassword
----

즉, Secret의 데이터는 쉽게 원래 값으로 되돌릴 수 있다는 것을 확인했습니다.

[IMPORTANT]
====
실제 운영 환경에서는 Secret 값을 터미널에 출력하거나 로그에 남기는 작업도 민감 정보 노출의 원인이 될 수 있습니다.

위 명령은 Secret의 동작을 이해하기 위한 **실습용 확인 과정**입니다.
====


=== Secret을 Volume으로 사용하기

이제 ``mysecret``의 값을 Pod 안에 파일 형태로 제공해 보겠습니다.

Secret을 Volume으로 사용하는 Deployment는 다음과 같이 구성할 수 있습니다.

[#deploy-myboot-secret-volume]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myboot
  labels:
    app: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
        - containerPort: 8080
        volumeMounts:
        - name: mysecret-volume
          mountPath: /mystuff/secretstuff
          readOnly: true
        resources:
          requests:
            memory: "400Mi"
            cpu: "250m"
          limits:
            memory: "600Mi"
            cpu: "1000m"
      volumes:
      - name: mysecret-volume
        secret:
          secretName: mysecret
EOF
----

중요한 부분을 하나씩 살펴보겠습니다.

먼저 ``volumes``에서는 어떤 Secret을 사용할지 정의합니다.

[source,yaml]
----
volumes:
- name: mysecret-volume
  secret:
    secretName: mysecret
----

여기서는 앞에서 생성한 ``mysecret`` Secret을 ``mysecret-volume``이라는 Volume으로 사용하도록 정의했습니다.

그리고 ``volumeMounts``에서는 이 Volume을 컨테이너의 어느 경로에 연결할지 지정합니다.

[source,yaml]
----
volumeMounts:
- name: mysecret-volume
  mountPath: /mystuff/secretstuff
  readOnly: true
----

따라서 관계를 그림으로 나타내면 다음과 같습니다.

[source,text]
----
Secret: mysecret
    │
    │
    ▼
Volume: mysecret-volume
    │
    │
    ▼
컨테이너의 /mystuff/secretstuff
----

Deployment의 Pod 템플릿이 변경되었으므로 새로운 Pod가 생성됩니다.

터미널 2에서 새 Pod가 ``Running`` 상태가 될 때까지 확인합니다.

또는 터미널 1에서 다음 명령으로 기다릴 수도 있습니다.

[#wait-secret-rollout]
[.console-input]
[source,bash]
----
oc rollout status deployment/myboot
----


=== Pod 안에서 Secret 확인하기

Secret이 실제로 어떻게 보이는지 확인해 봅니다.

[#list-secret-volume-secrets]
[.console-input]
[source,bash]
----
oc exec deployment/myboot -- ls -l /mystuff/secretstuff
----

다음과 비슷한 결과가 표시됩니다.

[.console-output]
[source,bash]
----
total 0
lrwxrwxrwx. 1 root root 15 password -> ..data/password
lrwxrwxrwx. 1 root root 11 user -> ..data/user
----

Secret의 각 key가 **파일 이름**이 되었습니다.

즉,

[source,text]
----
Secret
  user: MyUserName
  password: mypassword
----

은 컨테이너 안에서 다음과 같이 보입니다.

[source,text]
----
/mystuff/secretstuff/
├── user
└── password
----

``user`` 파일을 확인합니다.

[#print-secret-user]
[.console-input]
[source,bash]
----
oc exec deployment/myboot -- cat /mystuff/secretstuff/user
----

[.console-output]
[source,text]
----
MyUserName
----

이번에는 ``password`` 파일을 확인합니다.

[#print-secret-password]
[.console-input]
[source,bash]
----
oc exec deployment/myboot -- cat /mystuff/secretstuff/password
----

[.console-output]
[source,text]
----
mypassword
----

여기서 중요한 점은 **Pod 안에서는 Base64로 인코딩된 문자열이 아니라 실제 Secret 값이 파일 내용으로 제공된다는 것**입니다.

애플리케이션이 이 Secret을 사용하려면 이러한 파일을 읽도록 만들어져 있어야 합니다.

예를 들어 애플리케이션이 다음 파일들을 읽도록 구성할 수 있습니다.

[source,text]
----
/mystuff/secretstuff/user
/mystuff/secretstuff/password
----


=== Secret을 변경하면 실행 중인 Pod에는 어떻게 보일까?

앞의 ConfigMap 실습에서는 ConfigMap을 **환경 변수**로 사용했습니다.

환경 변수는 컨테이너가 시작될 때 한 번 설정되므로 ConfigMap을 변경하더라도 실행 중인 컨테이너의 환경 변수는 자동으로 변경되지 않았습니다.

이번에는 Secret을 **Volume으로 마운트**했습니다.

Volume으로 마운트된 Secret은 동작 방식이 다릅니다.

먼저 Secret의 값을 변경해 보겠습니다.

[#update-secret-secrets]
[.console-input]
[source,bash]
----
oc set data secret/mysecret \
  user='NewUserName' \
  password='newpassword'
----

변경된 Secret을 확인합니다.

[#check-updated-secret-secrets]
[.console-input]
[source,bash]
----
oc get secret mysecret -o yaml
----

Secret이 변경되었더라도 Pod가 새로 생성되지는 않습니다.

터미널 2의 Pod 상태를 확인해 보면 기존 Pod가 그대로 실행되고 있는 것을 확인할 수 있습니다.

잠시 후 Pod 안의 Secret 파일을 다시 확인합니다.

[#check-updated-volume-secret]
[.console-input]
[source,bash]
----
oc exec deployment/myboot -- cat /mystuff/secretstuff/user
----

[.console-output]
[source,text]
----
NewUserName
----

password도 확인합니다.

[#check-updated-volume-password]
[.console-input]
[source,bash]
----
oc exec deployment/myboot -- cat /mystuff/secretstuff/password
----

[.console-output]
[source,text]
----
newpassword
----

Pod를 다시 생성하지 않았는데도 Volume에 마운트된 파일의 내용이 변경된 것을 확인할 수 있습니다.

쿠버네티스는 Volume으로 마운트된 Secret이 변경되면 이를 감지하여 **실행 중인 Pod의 Volume에 변경된 내용을 반영**합니다.

다만 변경 내용이 즉시 반영된다고 보장되는 것은 아니며, kubelet이 변경 사항을 감지하고 Volume을 갱신할 때까지 약간의 시간이 걸릴 수 있습니다.

[source,text]
----
Secret 변경
      ↓
Pod는 그대로 실행
      ↓
kubelet이 변경 감지
      ↓
마운트된 Secret 파일 갱신
----

[NOTE]
====
Secret을 **환경 변수**로 사용하는 경우에는 동작이 다릅니다.

환경 변수로 전달된 Secret은 실행 중인 컨테이너에 자동으로 갱신되지 않으므로 새로운 값을 적용하려면 Pod를 다시 생성해야 합니다.

따라서 앞의 ConfigMap 실습과 마찬가지로 다음 차이를 기억해 두면 좋습니다.

----
환경 변수로 주입
→ Pod 재시작 필요

일반 Volume으로 마운트
→ 실행 중인 Pod의 파일에 변경 내용이 나중에 반영될 수 있음
----
====


=== 정리: ConfigMap과 Secret

앞의 ConfigMap 실습과 이번 Secret 실습을 함께 정리하면 다음과 같습니다.

[cols="2,2,2",options="header"]
|===
|구분
|ConfigMap
|Secret

|주요 용도
|일반적인 설정
|민감한 정보

|예
|URL, 포트, 로그 레벨
|Password, Token, 인증서 Key

|Pod에서 사용
|환경 변수 또는 Volume
|환경 변수 또는 Volume

|환경 변수로 사용 후 값 변경
|실행 중인 Pod에는 자동 반영되지 않음
|실행 중인 Pod에는 자동 반영되지 않음

|일반 Volume으로 사용 후 값 변경
|실행 중인 Pod의 파일에 나중에 반영 가능
|실행 중인 Pod의 파일에 나중에 반영 가능
|===

그리고 가장 중요한 점은 다음과 같습니다.

**Secret은 민감한 정보를 애플리케이션과 분리해서 관리하기 위한 Kubernetes 리소스이지만, Secret을 만들었다는 사실만으로 해당 데이터가 완전히 안전해지는 것은 아닙니다.**

실제 환경에서는 Secret에 대한 접근 권한과 저장 데이터 암호화 등의 보안 설정도 함께 고려해야 합니다.


== 실습 환경 정리

터미널 2에서 kbd:[Ctrl+c]를 눌러 실행 중인 명령어를 취소합니다.

생성했던 리소스를 정리합니다.

[#clean-secrets]
[.console-input]
[source,bash]
----
oc delete deployment myboot
oc delete service myboot
oc delete secret mysecret
----
