= oc: 쿠버네티스/OpenShift 클라이언트

``oc``는 OpenShift(그리고 그 기반이 되는 쿠버네티스) 클러스터의 API 서버와 대화하기 위한 공식 명령줄 도구입니다. 웹 콘솔로 클릭해서 할 수 있는 거의 모든 작업(리소스 조회, 생성, 수정, 삭제, 로그 확인 등)을 터미널에서 명령 한 줄로 처리할 수 있으며, 실무에서는 스크립트나 CI/CD 파이프라인에 자동화하기에도 훨씬 편리합니다. ``oc``는 쿠버네티스의 표준 CLI인 ``kubectl``이 이해하는 모든 명령을 그대로 이해하면서, 여기에 ``oc new-project``, ``oc expose``, ``oc debug node``처럼 OpenShift 전용 기능까지 추가로 제공합니다. 이 실습 환경에서는 일반 사용자 권한 구조상 ``kubectl create namespace``처럼 클러스터 수준 권한이 필요한 명령이 막혀 있는 경우가 많으므로, 이 튜토리얼에서는 ``oc``를 기본으로 사용합니다. 여기서 배우는 명령과 개념은 순수 쿠버네티스 클러스터에서 ``kubectl``을 사용할 때도 그대로 적용됩니다.

이번 장에서는 ``oc``의 기본 사용법을 익히면서, 앞으로 계속 마주치게 될 쿠버네티스의 핵심 객체들(Node, Namespace, Deployment, ReplicaSet, Pod, Service)을 가볍게 한 바퀴 둘러봅니다. 각 개념의 자세한 내용은 이후 장에서 하나씩 깊이 다룰 예정이니, 지금은 "이런 게 있구나" 정도로 감을 잡는 것을 목표로 하세요.

[[talk]]
== 클러스터와 대화하기

``oc``는 `KUBECONFIG` 환경 변수가 가리키는 설정 파일(또는 기본 위치인 `~/.kube/config`)을 읽어서 어떤 클러스터에, 누구로 접속할지를 알아냅니다. 이 파일에는 클러스터 API 서버의 주소와 인증 정보가 들어 있습니다. 다음 명령으로 현재 어떤 클러스터와 사용자로 연결되어 있는지 확인해 보세요:
[#kubectl-view-config]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
echo $KUBECONFIG
oc config view
----

== 노드 확인하기

쿠버네티스 클러스터는 여러 대의 컴퓨터(가상 머신 또는 물리 서버)로 이루어져 있으며, 이 각각의 컴퓨터를 __노드(Node)__라고 부릅니다. 여러분이 배포하는 애플리케이션의 Pod들은 결국 이 노드들 중 하나에서 실제로 실행됩니다. 클러스터에 어떤 노드가 있는지, 그리고 어떤 네임스페이스들이 존재하는지 확인해 봅시다:

[#kubectl-get-nodes]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get nodes
oc get nodes --show-labels
oc get namespaces
----

== 기본 제공 Pod 확인하기

__Pod__는 쿠버네티스에서 배포할 수 있는 가장 작은 단위로, 하나 이상의 컨테이너를 묶어서 같은 네트워크와 스토리지를 공유하며 함께 스케줄되도록 만든 것입니다. 즉, 여러분이 만든 컨테이너 이미지는 항상 Pod라는 껍데기에 담겨서 클러스터에 배포됩니다.

한편 __네임스페이스(Namespace)__는 클러스터 안의 리소스를 논리적으로 나누는 구획입니다(OpenShift에서는 "프로젝트"라고도 부릅니다). 클러스터 운영에 필요한 시스템 컴포넌트들도 결국 Pod로 실행되며, 보통 여러분의 애플리케이션과 섞이지 않도록 별도의 네임스페이스에 들어 있습니다. 
`--all-namespaces` 옵션을 주면 특정 네임스페이스에 한정하지 않고 클러스터 전체의 Pod를 볼 수 있지만, 지금 여러분이 권한을 가진 네임스페이스는 `{ocp4_starter_project}` 뿐이므로, 현재 사용 중인 `{ocp4_starter_project}` 네임스페이스에 배포되어 있는 Pod들만 확인해보겠습니다.

[#kubectl-get-pods]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get pods --all-namespaces
oc get pods --all-namespaces --show-labels
oc get pods --all-namespaces -o wide
----

[[deploy-app]]
== 무언가 배포하기

이제 직접 무언가를 배포해 봅시다. 먼저 다른 사람의 리소스와 섞이지 않도록 우리만의 네임스페이스를 만듭니다. 쿠버네티스의 ``namespace``는 클러스터 관리자만 만들 수 있는 클러스터 범위 리소스라서, 일반 사용자 권한으로 ``oc create namespace``를 실행하면 대부분 권한 오류가 납니다. 대신 OpenShift는 일반 사용자도 스스로 만들 수 있도록 ``oc new-project``라는 명령을 제공합니다 — 내부적으로는 똑같은 네임스페이스를 만들면서, 동시에 앞으로 실행할 명령들이 기본적으로 이 네임스페이스를 대상으로 하도록 컨텍스트까지 함께 전환해 줍니다.

그런 다음 ``oc create deployment``로 __Deployment__를 하나 만듭니다. Deployment는 "이 컨테이너 이미지를, 이만큼의 개수로, 항상 이렇게 실행되고 있어야 한다"는 __원하는 상태(desired state)__를 선언적으로 기술하는 객체입니다. 여러분이 직접 Pod를 하나하나 만드는 것이 아니라, Deployment에게 원하는 상태를 알려주면 쿠버네티스가 알아서 그 상태를 만들고 계속 유지해 줍니다(Pod가 죽으면 새로 만들어 채워 넣는 식으로요):

[#kubectl-deploy-app]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc new-project {user}-mystuff

oc create deployment myapp --image=quay.io/rhdevelopers/quarkus-demo:v1
----

== 이벤트 모니터링하기

방금 실행한 `oc create deployment` 명령 하나가 실제로는 클러스터 내부에서 여러 단계를 거칩니다: Deployment가 만들어지고, Deployment는 ReplicaSet을 만들고, ReplicaSet은 다시 Pod를 만들고, 그 Pod의 컨테이너 이미지를 내려받아 실행합니다. 쿠버네티스는 이런 단계마다 __Event__라는 기록을 남기는데, `-w`(watch) 옵션으로 이 이벤트들을 실시간으로 지켜보면 방금 실행한 명령이 클러스터 뒤편에서 실제로 어떤 일을 일으켰는지 눈으로 확인할 수 있습니다:

=== ReplicaSet

Deployment 아래에는 ReplicaSet이 하나 있습니다. ReplicaSet의 역할은 단순합니다: "지정된 개수(DESIRED)만큼의 Pod가 항상 떠 있도록 유지한다"는 것뿐입니다. 실제로 어떤 이미지를 어떻게 배포할지 같은 결정은 Deployment가 내리고, ReplicaSet은 그 실행 개수만 책임집니다.

[#kubectl-get-replicasets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get replicasets
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME               DESIRED   CURRENT   READY   AGE
myapp-5dcbf46dfc   1         1         1       2m1s
----

== Service 노출하기

Pod는 재시작될 때마다 IP가 바뀌기 때문에, 다른 애플리케이션이 Pod의 IP를 직접 알고 접근하는 것은 위험합니다. __Service__는 레이블이 일치하는 Pod들 앞에 놓여, Pod가 바뀌어도 변하지 않는 하나의 안정적인 주소를 제공합니다(Service는 xref:service.adoc[Service] 장에서 자세히 다룹니다). ``oc expose``는 기존 Deployment를 대상으로 이런 Service를 빠르게 만들어 주는 단축 명령입니다:

[#kubectl-expose]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc expose deployment myapp --port=8080 --type=LoadBalancer
----

== 앱 스케일하기

이번에는 Deployment의 `replicas` 값을 늘려서 애플리케이션을 __스케일__해 보고, 그 과정에서 Pod들이 어떻게 늘어나는지, 그리고 트래픽이 여러 Pod에 어떻게 분산되는지를 동시에 관찰해 봅시다. 이를 위해 터미널 창을 세 개 엽니다: 하나는 Pod 목록을 지켜보고, 하나는 계속 요청을 보내고, 나머지 하나는 실제로 명령을 실행하는 용도입니다.

[#watch-pods]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----

=== 터미널 3

이제 실제로 명령을 실행할 세 번째 터미널입니다. 먼저 복제본(`replicas`) 수를 3으로 늘려 봅시다. 터미널 1(Pod 목록)과 터미널 2(요청 루프)의 출력이 함께 바뀌는 것을 눈으로 확인하면서 진행하세요:

[#change-replicas]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc scale deployment myapp --replicas=3
----

[source,bash,subs="+macros,+attributes"]
----

myapp-5dcbf46dfc-6sn2s   0/1     ContainerCreating   0          4s
myapp-5dcbf46dfc-ghrk4   1/1     Running             0          5m32s

이번에는 Deployment가 사용하는 컨테이너 이미지를 바꿔서 애플리케이션 버전을 업그레이드해 봅시다. 이미지를 바꾸면 쿠버네티스는 기존 Pod를 한꺼번에 내리지 않고, 새 버전의 Pod를 하나씩 띄우면서 구버전 Pod를 하나씩 내리는 방식으로 서비스 중단 없이 전환합니다(이를 __롤링 업데이트__라고 부르며, xref:rolling-updates.adoc[롤링 업데이트] 장에서 더 자세히 다룹니다). 터미널 2의 요청 루프를 계속 지켜보면, 응답이 끊기지 않으면서 메시지만 서서히 바뀌는 것을 볼 수 있을 것입니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc set image deployment/myapp quarkus-demo=quay.io/rhdevelopers/myboot:v1
----

Aloha from Spring Boot! 0 on myapp-58b97dbd95-vxd87

방금 일으킨 변경 사유를 기록으로 남겨 둡시다. 이렇게 남긴 메모는 바로 다음에 확인할 ``rollout history``에 표시되어서, 나중에 "이 리비전이 왜 만들어졌는지"를 쉽게 알아볼 수 있게 해 줍니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc annotate deployment/myapp kubernetes.io/change-cause="Reverting to old SpringBoot version" --overwrite
----

Deployment는 이미지나 설정이 바뀔 때마다 그 변경 이력을 __리비전(revision)__으로 남겨 둡니다. 덕분에 문제가 생기면 특정 시점으로 되돌아갈 수 있습니다. 지금까지 쌓인 리비전 히스토리를 살펴봅니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc rollout history deployment/myapp
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
deployment.apps/myapp
REVISION  CHANGE-CAUSE
1         <none>
2         Restoring to old SpringBoot version
----

사실 각 리비전은 그 나름의 ReplicaSet을 하나씩 가지고 있습니다. Deployment는 옛 리비전의 ReplicaSet을 삭제하지 않고 복제본 수를 0으로 줄여서 남겨 두는데, 덕분에 롤백할 때 이미지를 다시 내려받지 않고도 빠르게 되돌아갈 수 있습니다. ``deployment``의 ReplicaSet 목록을 조회해서 이를 확인해 봅시다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get rs
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME               DESIRED   CURRENT   READY   AGE
myapp-65c9d96df4   3         3         3       2m
myapp-67fc4b6f94   0         0         0       8m
----

가장 최근에 성공했던 버전으로 되돌리려면(예: 리비전 2에서 리비전 1로), undo 명령을 사용합니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc rollout undo deployment/myapp
----

[TIP]
====
다음 옵션을 추가하면 리비전 번호를 지정할 수 있습니다: `--to-revision=1`
====

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
Aloha from Spring Boot! 16 on myapp-fc6b78bb-d495j
Supersonic Subatomic Java with Quarkus myapp-76d84b5f46-jlzs7:1
Supersonic Subatomic Java with Quarkus myapp-76d84b5f46-jlzs7:2
Aloha from Spring Boot! 17 on myapp-fc6b78bb-d495j
Aloha from Spring Boot! 18 on myapp-fc6b78bb-d495j
Supersonic Subatomic Java with Quarkus myapp-76d84b5f46-jlzs7:3
Aloha from Spring Boot! 19 on myapp-fc6b78bb-d495j
Supersonic Subatomic Java with Quarkus myapp-76d84b5f46-jlzs7:4
----

=== 정리

이번 장에서 만든 네임스페이스와 그 안의 모든 리소스(Deployment, ReplicaSet, Pod, Service)를 정리합니다. 네임스페이스를 삭제하면 그 안에 속한 리소스들이 함께 정리되므로, 다음 장을 새 상태에서 시작할 수 있습니다:

[#delete-namespace]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc delete project {user}-mystuff
oc config set-context --current --namespace={ocp4_starter_project}
----
