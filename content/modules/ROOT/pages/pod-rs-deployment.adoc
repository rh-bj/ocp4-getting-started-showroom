= Pod, ReplicaSet, Deployment

쿠버네티스에서 애플리케이션을 실행하는 방법에는 여러 단계가 있습니다. 이번 장에서는 그중 가장 기본이 되는 세 가지 객체 Pod, ReplicaSet, Deployment를 순서대로 직접 만들어 보면서, 각 객체가 이전 단계의 어떤 한계를 보완하기 위해 존재하는지 확인합니다:

* __Pod__는 컨테이너를 실제로 실행하는 가장 작은 단위입니다. 하지만 Pod를 혼자(맨몸으로) 배포하면, 그 Pod가 죽었을 때 아무도 다시 살려주지 않습니다.
* __ReplicaSet__은 "이 Pod가 항상 N개 떠 있어야 한다"를 보장해서, Pod가 죽으면 자동으로 새 Pod를 만들어 채워 넣습니다.
* __Deployment__는 ReplicaSet을 감싸서, 이미지 업데이트나 롤백 같은 __변경 관리__ 기능까지 더해 줍니다.

먼저 작업할 네임스페이스를 생성합니다:

[#create-namespace]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl create namespace {user}-myspace
kubectl config set-context --current --namespace={user}-myspace
----

== Pod

먼저 아무런 보호 장치 없이 Pod 하나만 직접 만들어 봅니다. 이렇게 상위 컨트롤러(ReplicaSet이나 Deployment) 없이 만든 Pod를 https://kubernetes.io/docs/concepts/configuration/overview/#naked-pods-vs-replicasets-deployments-and-jobs[네이키드(naked) Pod]라고 부릅니다. 이 실습의 목적은, 이런 Pod가 왜 실무에서 그대로 쓰이지 않는지를 직접 겪어 보는 것입니다:

[#create-pod]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: quarkus-demo
spec:
  containers:
  - name: quarkus-demo
    image: quay.io/rhdevelopers/quarkus-demo:v1
    securityContext:
      seccompProfile:
        type: RuntimeDefault
EOF
----

pod의 라이프사이클을 지켜봅니다:

[#watch-pod]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get pods -w
----

[.console-output]
[source,bash]
----
NAME           READY   STATUS              RESTARTS   AGE
quarkus-demo   0/1     ContainerCreating   0          10s
----

ContainerCreating 상태에서 Running으로 바뀌면서 Ready가 1/1이 됩니다:

[.console-output]
[source,bash]
----
NAME           READY   STATUS    RESTARTS   AGE
quarkus-demo   1/1     Running   0          18s
----

Pod 안의 애플리케이션을 확인합니다:

[#verify-pod]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl exec -it quarkus-demo -- /bin/sh
----

다음 명령을 실행합니다.
컨테이너 인스턴스 안에 있기 때문에 호스트 이름이 ``localhost``인 것에 주목하세요.

[#curl-inside-pod]
[.console-input]
[source,bash]
----
curl localhost:8080
----

[.console-output]
[source,bash]
----
Supersonic Subatomic Java with Quarkus quarkus-demo:1
exit
----

앞서 만든 Pod를 삭제해 봅시다:

[#delete-naked-pod]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl delete pod quarkus-demo
----

[#watch-all-naked-pod]
[.console-input]
[source,bash]
----
kubectl get pods -w
----

[.console-output]
[source,bash]
----
NAME           READY   STATUS        RESTARTS   AGE
quarkus-demo   0/1     Terminating   0          9m35s

No resources found in myspace namespace.
----

네이키드 Pod는 영원히 사라집니다. 아무도 이 Pod를 다시 만들어 주지 않기 때문입니다. 애플리케이션이 크래시하거나 노드에 장애가 생겼을 때도 마찬가지로 아무 일도 일어나지 않습니다 — 이것이 바로 Pod를 그대로 배포하지 않는 이유입니다.

== ReplicaSet

이번에는 같은 Pod를 ReplicaSet으로 감싸서 만들어 봅니다. ReplicaSet의 ``spec.replicas``에 원하는 개수를, ``spec.template``에 각 Pod의 모양(방금 만들었던 Pod의 정의와 거의 같습니다)을 정의하면, ReplicaSet 컨트롤러가 그 개수를 계속 유지해 줍니다:

[#create-replicaset]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: ReplicaSet
metadata:
    name: rs-quarkus-demo
spec:
    replicas: 3
    selector:
       matchLabels:
          app: quarkus-demo
    template:
       metadata:
          labels:
             app: quarkus-demo
             env: dev
       spec:
          containers:
          - name: quarkus-demo
            image: quay.io/rhdevelopers/quarkus-demo:v1
EOF
----

레이블과 함께 pod 목록을 조회합니다:

[#replicaset-show-labels]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get pods -w --show-labels
----

[.console-output]
[source,bash]
----
NAME                    READY   STATUS    RESTARTS   AGE   LABELS
rs-quarkus-demo-jd6jk   1/1     Running   0          58s   app=quarkus-demo,env=dev
rs-quarkus-demo-mlnng   1/1     Running   0          58s   app=quarkus-demo,env=dev
rs-quarkus-demo-t26gt   1/1     Running   0          58s   app=quarkus-demo,env=dev
----

[#get-rs]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get rs
----

[.console-output]
[source,bash]
----
NAME              DESIRED   CURRENT   READY   AGE
rs-quarkus-demo   3         3         3       79s
----

RS를 describe해서, 맨 아래 Events 섹션에 ``replicaset-controller``가 방금 Pod 3개를 만든 기록이 남아 있는지 확인해 봅시다:

[#describe-rs-quarkus-demo]
[.console-input]
[source,bash]
----
kubectl describe rs rs-quarkus-demo
----

[.console-output]
[source,bash]
----
Name:         rs-quarkus-demo
Namespace:    myspace
Selector:     app=quarkus-demo
Labels:       <none>
Annotations:  kubectl.kubernetes.io/last-applied-configuration:
                {"apiVersion":"apps/v1","kind":"ReplicaSet","metadata":{"annotations":{},"name":"rs-quarkus-demo","namespace":"myspace"},"spec":{"replicas...
Replicas:     3 current / 3 desired
Pods Status:  3 Running / 0 Waiting / 0 Succeeded / 0 Failed

  Labels:  app=quarkus-demo
           env=dev
  Containers:
   quarkus-demo:
    Image:        quay.io/rhdevelopers/quarkus-demo:v1
    Port:         <none>
    Host Port:    <none>
    Environment:  <none>
    Mounts:       <none>
  Volumes:        <none>
Events:
  Type    Reason            Age   From                   Message
  ----    ------            ----  ----                   -------
  Normal  SuccessfulCreate  89s   replicaset-controller  Created pod: rs-quarkus-demo-jd6jk
  Normal  SuccessfulCreate  89s   replicaset-controller  Created pod: rs-quarkus-demo-t26gt
  Normal  SuccessfulCreate  89s   replicaset-controller  Created pod: rs-quarkus-demo-mlnng
----

Pod는 ReplicaSet에 "소유"됩니다. Pod 객체 안의 `ownerReferences` 필드를 확인해 보면, 이 Pod를 누가 만들고 책임지는지 알 수 있습니다. 이 소유 관계 덕분에, 잠시 후 Pod를 하나 지웠을 때 ReplicaSet이 그것을 알아채고 새 Pod로 채워 넣을 수 있는 것입니다:

[#rs-owned-ref]
[.console-input]
[source,bash]
----
kubectl get pod rs-quarkus-demo-mlnng -o jsonpath='{.metadata.ownerReferences[]}'
----

[.console-output]
[source,bash]
----
{
  "apiVersion": "apps/v1",
  "blockOwnerDeletion": true,
  "controller": true,
  "kind": "ReplicaSet",
  "name": "rs-quarkus-demo",
  "uid": "1ed3bb94-dfa5-40ef-8f32-fbc9cf265324"
}
----

이제 앞서 네이키드 Pod로 겪었던 것과 똑같은 상황, 즉 Pod가 갑자기 사라지는 상황을 재현해서 ReplicaSet이 이번에는 어떻게 다르게 반응하는지 지켜봅시다. Pod 목록을 지켜보면서 그중 하나를 삭제합니다:

[#delete-pod-rs]
[.console-input]
[source,bash]
----
kubectl delete pod rs-quarkus-demo-mlnng
----

그러면 이를 대체할 새 pod가 생겨납니다. 이것이 바로 네이키드 Pod에는 없었던 __자가 치유(self-healing)__ 능력입니다:

[.console-output]
[source,bash]
----
NAME                    READY   STATUS              RESTARTS   AGE    LABELS
rs-quarkus-demo-2txwk   0/1     ContainerCreating   0          2s     app=quarkus-demo,env=dev
rs-quarkus-demo-jd6jk   1/1     Running             0          109s   app=quarkus-demo,env=dev
rs-quarkus-demo-t26gt   1/1     Running             0          109s   app=quarkus-demo,env=dev
----

ReplicaSet을 삭제해서 연결된 모든 pod를 제거합니다:

[#delete-rs]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl delete rs rs-quarkus-demo
----

== Deployment

ReplicaSet은 "개수 유지"는 잘하지만, 정작 "이미지를 v1에서 v2로 바꾸고 싶을 때 어떻게 무중단으로 전환할 것인가"와 같은 __변경 관리__는 책임지지 않습니다. 이런 기능을 ReplicaSet 위에 얹어 주는 것이 바로 Deployment입니다. 아래 정의를 보면 ``spec.replicas``와 ``spec.template``이 방금 만들었던 ReplicaSet과 거의 똑같다는 것을 알 수 있는데, 이는 Deployment가 내부적으로 ReplicaSet을 만들고 관리하기 때문입니다(그 증거는 다음 명령의 Pod 이름에 있는 `pod-template-hash` 부분에서 확인할 수 있습니다 — 이것이 Deployment가 만든 ReplicaSet의 흔적입니다):

[#create-deployment]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: quarkus-demo-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: quarkus-demo
  template:
    metadata:
      labels:
        app: quarkus-demo
        env: dev
    spec:
      containers:
      - name: quarkus-demo
        image: quay.io/rhdevelopers/quarkus-demo:v1
        imagePullPolicy: Always
        ports:
        - containerPort: 8080
EOF
----

[#pod-show-labels-dep]
[.console-input]
[source,bash]
----
kubectl get pods --show-labels
----

[.console-output]
[source,bash]
----
NAME                                       READY   STATUS    RESTARTS   AGE   LABELS
quarkus-demo-deployment-5979886fb7-c888m   1/1     Running   0          17s   app=quarkus-demo,env=dev,pod-template-hash=5979886fb7
quarkus-demo-deployment-5979886fb7-gdtnz   1/1     Running   0          17s   app=quarkus-demo,env=dev,pod-template-hash=5979886fb7
quarkus-demo-deployment-5979886fb7-grf59   1/1     Running   0          17s   app=quarkus-demo,env=dev,pod-template-hash=5979886f
----

[#exec-inside-pod-labels]
[.console-input]
[source,bash]
----
kubectl exec -it quarkus-demo-deployment-5979886fb7-c888m -- curl localhost:8080
----

[.console-output]
[source,bash]
----
Supersonic Subatomic Java with Quarkus quarkus-demo-deployment-5979886fb7-c888m:1
----

다음 섹션에서는 ``Service``라는 개념을 배웁니다.
이는 쿠버네티스 생태계에서 중요한 요소입니다.
