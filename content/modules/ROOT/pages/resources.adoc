쿠버네티스는 컨테이너마다 CPU와 메모리 사용량을 두 가지 값으로 조절할 수 있습니다: __Requests__(스케줄러가 이 Pod를 배치할 노드를 고를 때 "최소 이만큼은 확보해 달라"는 값)와 __Limits__(컨테이너가 실제로 사용할 수 있는 __최대__ 한도). 문제는, 오래된 JVM은 자신이 __컨테이너 안에__ 있다는 것을 알지 못하고 호스트 머신 전체의 메모리를 기준으로 힙 크기를 계산한다는 것입니다. 이 둘을 지정하지 않으면 어떤 문제가 생기는지, 그리고 이 JVM 문제가 쿠버네티스 위에서는 어떻게 나타나는지를 이번 장에서 직접 확인해 봅니다.

일부러 과도하게 큰 CPU를 요청하도록 resource request를 지정해서 새 deployment를 생성합니다. 클러스터의 어떤 노드도 이만큼의 여유 CPU를 갖고 있지 않아서 Pod가 스케줄되지 못하는 상황을 재현하기 위한 것입니다:

[#limits-resource]
[.console-input]
[source, bash]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
          - containerPort: 8080
        resources:
          requests: 
            memory: "300Mi" 
            cpu: "16000m" # 16 cores
EOF
----

pod 스펙의 "resource requests"는 최소 하나의 워커 노드가 N개의 코어와 X만큼의 메모리를 사용 가능해야 함을 요구합니다. 이 조건을 만족하는 워커 노드가 없다면 "PENDING" 상태와 함께 이벤트 목록에 해당 내용이 표시됩니다.

pod에 ``oc describe``를 실행해서 실패에 대한 더 자세한 정보를 확인할 수도 있습니다.

:section-k8s: resource-limit
:label-describe: app=myboot
include::partial$describe.adoc[]

[source,text]
--------------------------------------------
0/13 nodes are available: 13 Insufficient cpu.
no new claims to deallocate,
preemption: 0/13 nodes are available:
13 Preemption is not helpful for scheduling.
--------------------------------------------

이 메시지는 **Pod가 요청한 CPU를 제공할 수 있는 노드가 클러스터에 하나도 없어서 스케줄링에 실패했다**는 의미입니다.

먼저 가장 중요한 부분은 다음입니다.

[source,text]
--------------------------------------------
0/13 nodes are available: 13 Insufficient cpu.
--------------------------------------------

클러스터에는 총 13개의 노드가 있지만, 13개 노드 모두 이 Pod가 요청한 만큼의 CPU를 추가로 할당할 수 없다는 뜻입니다.

여기서 Kubernetes Scheduler가 확인하는 것은 **현재 실제 CPU 사용률**이 아니라, 각 Pod가 설정한 **CPU Request의 합계**입니다.

예를 들어 어떤 노드가 8 CPU를 Pod에 할당할 수 있고 이미 다른 Pod들이 총 6 CPU를 Request하고 있다면,

[source,text]
------------------------
노드의 할당 가능 CPU     : 8 CPU
기존 Pod들의 CPU Request : 6 CPU
남은 스케줄링 가능 CPU   : 2 CPU
------------------------

새 Pod가 다음과 같이 4 CPU를 요청하면,

[source,yaml]
--------
resources:
  requests:
    cpu: "4"
--------

현재 실제 CPU 사용률이 낮더라도 Scheduler 입장에서는 남은 2 CPU보다 큰 4 CPU를 요청했으므로 이 노드에는 Pod를 배치할 수 없습니다.
이 때 Pod는 삭제되거나 실패한 것이 아니라, 적절한 노드를 찾을 때까지 **Pending** 상태로 남게 됩니다.

이제 현실적인 값의 Requests/Limits로 이 deployment를 고쳐 봅시다. ``replace``로 변경 이력을 유지하면서 deployment를 수정합니다:

[#apply-deployment-sane-limit-resource]
[.console-input]
[source, bash]
----
cat <<EOF | oc replace -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
          - containerPort: 8080
        resources:
          requests: 
            memory: "400Mi" 
            cpu: "250m" # 1/4 core
          # NOTE: These are the same limits we tested our Docker Container with earlier
          # -m matches limits.memory and --cpus matches limits.cpu
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
EOF
----

위 명령은 Deployment 템플릿을 교체하고 Pod에 컨테이너 제한을 지정하도록 지시합니다.
