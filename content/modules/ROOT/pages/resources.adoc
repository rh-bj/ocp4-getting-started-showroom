== 배경지식: 요청(Requests)과 제한(Limits)

Kubernetes에서는 여러 애플리케이션이 같은 노드의 CPU와 메모리를 공유해서 사용합니다. +
이때 특정 애플리케이션이 필요로 하는 리소스를 Kubernetes에 알려주거나, 하나의 애플리케이션이 지나치게 많은 리소스를 사용하는 것을 막기 위해 **Requests**와 **Limits**를 설정할 수 있습니다.

* **요청(Requests)**
** 컨테이너를 실행하기 위해 필요하다고 Kubernetes에 요청하는 리소스의 양입니다.
** Kubernetes Scheduler는 Pod를 어느 노드에 배치할지 결정할 때 각 컨테이너에 설정된 Requests를 기준으로 판단합니다.
** 예를 들어 CPU Request를 `250m`으로 설정하면 Scheduler는 현재 CPU 사용률이 아니라, 노드의 할당 가능한 CPU와 이미 배치된 Pod들의 CPU Request를 비교하여 이 Pod를 배치할 수 있는지 판단합니다.
** 요청한 리소스를 수용할 수 있는 노드가 없다면 Pod는 실행되지 않고 **Pending** 상태로 남습니다.

* **제한(Limits)**
** 컨테이너가 사용할 수 있는 리소스의 최대 범위를 설정합니다.
** CPU Limit을 초과하려고 하면 컨테이너가 종료되는 것이 아니라 CPU 사용이 제한(throttling)됩니다.
** 반면 Memory Limit을 초과하여 메모리를 계속 사용하면 컨테이너가 **OOMKilled**로 강제 종료될 수 있습니다.
** 예를 들어 Memory Limit을 `512Mi`로 설정하면 컨테이너가 사용할 수 있는 메모리를 512Mi로 제한할 수 있습니다.

즉, Requests와 Limits는 서로 다른 목적으로 사용됩니다.
* Requests: 이 Pod를 어디에 배치할 수 있는가?
* Limits : 실행된 컨테이너가 어디까지 리소스를 사용할 수 있는가?

Requests와 Limits를 지정하지 않으면 Kubernetes는 해당 컨테이너가 어느 정도의 CPU와 메모리를 필요로 하는지 알 수 없으며, 컨테이너가 사용할 수 있는 리소스의 상한도 설정되지 않습니다. +
이번 장에서는 먼저 Requests와 Limits를 설정하지 않은 Pod를 확인하고, 이어서 과도한 Request 때문에 Pod가 스케줄링되지 않는 상황과 Memory Limit을 초과하여 컨테이너가 `OOMKilled`되는 상황을 직접 확인해 봅니다.

=== 과도하게 큰 리소스를 요청하여 배포

이번에는 Requests를 지정한 버전으로 다시 배포하기 위해, 먼저 해당 deployment를 삭제합니다:

[#delete-deployment-resource]
[.console-input]
[source, bash]
----
oc delete deployment myboot
----

다음과 같이 일부러 과도하게 큰 CPU(100코어)를 요청하도록 request를 지정해서 새 deployment를 생성합니다. 클러스터의 어떤 노드도 이만큼의 여유 CPU를 갖고 있지 않기 때문에 Pod가 스케줄되지 못할 겁니다. 

[#limits-resource]
[.console-input]
[source, bash]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
          - containerPort: 8080
        resources:
          requests: 
            memory: "300Mi" 
            cpu: "100000m" # 100 cores
EOF
----

그리고 Pod의 상태를 확인합니다.

[#limits-get-pod-resource]
[.console-input]
[source, bash]
----
oc get pods
----

[.console-output]
[source,bash]
----
NAME                      READY   STATUS    RESTARTS   AGE
myboot-7b7d754c86-kjwlr   0/1     Pending   0          19s
----

현재 Pending 상태인 것이 보입니다. 
pod에 ``oc describe``를 실행해서 실패에 대한 더 자세한 정보를 확인할 수도 있습니다.

:section-k8s: resource-limit
:label-describe: app=myboot
include::partial$describe.adoc[]

[source,text]
--------------------------------------------
0/15 nodes are available: 15 Insufficient cpu. 
no new claims to deallocate, 
preemption: 0/15 nodes are available: 
15 Preemption is not helpful for scheduling.
--------------------------------------------

이 메시지는 **Pod가 요청한 CPU를 제공할 수 있는 노드가 클러스터에 하나도 없어서 스케줄링에 실패했다**는 의미입니다.

먼저 가장 중요한 부분은 다음입니다.

[source,text]
--------------------------------------------
0/15 nodes are available: 15 Insufficient cpu.
--------------------------------------------

클러스터에는 총 15개의 노드가 있지만, 15개 노드 모두 이 Pod가 요청한 만큼의 CPU를 추가로 할당할 수 없다는 뜻입니다.
이 때 Pod는 삭제되거나 실패한 것이 아니라, 적절한 노드를 찾을 때까지 **Pending** 상태로 남게 됩니다.

=== 적절한 리소스 설정으로 배포

이제 현실적인 값의 Requests/Limits로 이 deployment를 고쳐 봅시다. ``replace`` 명령어로 변경 이력을 유지하면서 deployment를 수정합니다:

[#apply-deployment-sane-limit-resource]
[.console-input]
[source, bash]
----
cat <<EOF | oc replace -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
          - containerPort: 8080
        resources:
          requests: 
            memory: "400Mi" 
            cpu: "250m" # 1/4 core
          # NOTE: These are the same limits we tested our Docker Container with earlier
          # -m matches limits.memory and --cpus matches limits.cpu
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
EOF
----

위 명령은 Deployment 템플릿을 교체하고 Pod에 적절한 리소스 제한을 지정하도록 지시합니다.
