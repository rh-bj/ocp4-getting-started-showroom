= Volume과 Persistent Volume
include::vars.adoc[]
include::_attributes.adoc[]
:watch-terminal: 터미널 2
:file-watch-terminal: 터미널 3

컨테이너는 기본적으로 **일시적인(ephemeral) 실행 환경**입니다.

컨테이너가 실행되는 동안 파일을 생성하거나 데이터를 저장할 수 있지만, 이러한 데이터가 컨테이너 자체의 파일 시스템에만 저장되어 있다면 컨테이너가 삭제되거나 새로 생성될 때 그대로 유지된다는 보장이 없습니다.

예를 들어 데이터베이스를 컨테이너로 실행하면서 데이터 파일까지 컨테이너 내부에만 저장한다면, 컨테이너가 재생성되었을 때 중요한 데이터가 사라질 수 있습니다.

Kubernetes에서는 이러한 문제를 해결하기 위해 **Volume**을 사용할 수 있습니다.

Volume은 Pod에 정의되고, Pod 안의 하나 이상의 컨테이너에 특정 디렉터리로 마운트하여 사용할 수 있는 저장 공간입니다.

[source,text]
-------------------
Pod
│
├─ Container A
│     └─ /data ───┐
│                 │
├─ Container B    │
│     └─ /shared ─┤
│                 │
└─ Volume ────────┘
-------------------

즉, 컨테이너는 Volume을 자신의 파일 시스템 안에 있는 일반적인 디렉터리처럼 사용할 수 있습니다.

Volume의 실제 데이터가 어디에 저장되고 얼마나 오래 유지되는지는 **어떤 종류의 Volume을 사용하느냐**에 따라 달라집니다.

대표적으로 다음과 같은 방식이 있습니다.

* `emptyDir`
  ** Pod가 실행되는 동안 사용할 임시 저장 공간입니다.
  ** 컨테이너가 재시작되어도 같은 Pod가 유지되는 동안에는 데이터가 남아 있습니다.
  ** 하지만 Pod가 삭제되면 데이터도 함께 사라집니다.

* `hostPath`
  ** Worker Node의 특정 디렉터리를 Pod에 직접 마운트합니다.
  ** Pod가 다른 Node로 이동하면 같은 데이터를 사용할 수 없기 때문에 일반적인 애플리케이션의 영구 저장소로 사용하는 것은 적합하지 않습니다.

* **Persistent Volume**
  ** Pod의 수명과 관계없이 데이터를 유지해야 할 때 사용합니다.
  ** 애플리케이션은 일반적으로 `PersistentVolumeClaim(PVC)`을 통해 필요한 저장 공간을 요청합니다.
  ** 실제 저장소는 NFS, Ceph, 클라우드 Block Storage 등 다양한 시스템이 될 수 있으며, 현재 Kubernetes에서는 주로 **CSI(Container Storage Interface)** 드라이버를 통해 이러한 외부 스토리지를 연결합니다.

[source,text]
-------------------------
Pod
│
│ mount
▼
PVC (PersistentVolumeClaim)
│
▼
PV (PersistentVolume)
│
▼
실제 Storage
(NFS, Ceph, Cloud Disk 등)
-------------------------

따라서 중요한 것은 **Volume 자체가 항상 영구적인 저장 공간을 의미하는 것은 아니라는 점**입니다.

[source,text]
------------------------------------------
emptyDir      → Pod가 없어지면 데이터도 사라짐
PersistentVolume → Pod가 없어져도 데이터를 유지할 수 있음
------------------------------------------

이번 실습에서는 실제로 Volume을 생성하고 컨테이너에 마운트하여, 컨테이너에서 데이터를 어떻게 저장하고 사용할 수 있는지 확인해 보겠습니다.

== Volume

``Volume``의 예시 두 가지로 시작해 봅시다.

=== EmptyDir

`emptyDir` volume은 Pod가 노드에 할당될 때 처음 생성되며, 그 Pod가 해당 노드에서 실행되는 동안 존재합니다.
이름 그대로, 처음에는 비어 있습니다.
같은 Pod 안의 모든 Container는 동일한 `emptyDir` volume을 읽고 쓸 수 있습니다.
Pod가 재시작되거나 제거되면 ``emptyDir``의 데이터는 영구적으로 사라집니다.

`volumes` 섹션에서는 volume을 정의하고, `volumeMounts` 섹션에서는 그 volume이 컨테이너 안에 어떻게 마운트되는지를 정의합니다.

  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    
    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  volumes:
  - name: demo-volume
    emptyDir: {}
EOF
----

==== Pod 안에서 EmptyDir 공유하기

``emptyDir``은 같은 Pod의 컨테이너 사이에 공유됩니다. 같은 pod 안에 같은 `emptyDir` volume을 마운트하는 두 개의 컨테이너를 만드는 deployment를 살펴봅시다.

:quick-open-file: myboot-pods-volume.yml

``{quick-open-file}``을 살펴봅시다:

[.console-output]
[source,yaml]
.{quick-open-file}
----
include::example$myboot-pods-volume.yml[]
----
<.> pod의 첫 번째 컨테이너는 myboot-demo-1이라는 이름을 가지며, ``/tmp/demo``에 ``demo-volume``을 마운트합니다.
<.> pod의 두 번째 컨테이너는 ``myboot-demo-2``라는 이름을 가지며, 같은 `/tmp/demo` 지점에 ``demo-volume``을 마운트합니다.
<.> 두 컨테이너는 완전히 동일한 이미지를 사용합니다.
<.> 컨테이너들이 pod의 포트를 공유하기 때문에 두 번째 컨테이너는 첫 번째와 다른 포트를 리슨해야 한다는 점에 주목하세요. 이 수준의 `env` 지시자는 `myboot-demo-2` 컨테이너에만 적용됩니다.
<.> volume은 한 번만 정의되지만 pod의 각 컨테이너에서 참조됩니다.

이제 `{set-namespace}` 네임스페이스에 이 deployment를 만들어 봅시다.

[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo-1 #<.>
    image: quay.io/rhdevelopers/myboot:v4
    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  - name: myboot-demo-2 #<.>
    image: quay.io/rhdevelopers/myboot:v4 #<.>

    env:
    - name: SERVER_PORT #<.>
      value: "8090"

    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  volumes:
  - name: demo-volume #<.>
    emptyDir: {}
EOF
----

=== HostPath


IMPORTANT: **hostPath 볼륨 사용 제한** +
OpenShift는 클러스터 노드의 파일 시스템 경로를 컨테이너에 직접 마운트하는 hostPath 볼륨의 사용을 기본적으로 금지합니다. 이는 보안상 중요한 이유 때문입니다.+
*SCC(Secure Context Constraints)* +
OpenShift는 Pod가 특정 보안 컨텍스트 제약 조건(SCC)에 맞아야 실행을 허용합니다. +
기본적으로 사용자는 restricted SCC가 할당되어 있고, 이는 hostPath 볼륨 사용을 허용하지 않습니다.+
**이 실습의 user계정은 admin 권한이 없기 때문에, `HostPath` 부분은 읽어만 보세요.**

<.> ``/mnt/data``는 이 pod가 할당되는 쿠버네티스 ``node``의 한 위치입니다.

...

앞의 스니펫에서 주목해야 할 점은, 애플리케이션에 속한 것들(즉 컨테이너, probe, 포트 등)로 더 __dev__ 쪽에 가까운 것과, 클라우드와 더 관련된 것들(즉 물리적 스토리지)로 더 __ops__ 쪽에 가까운 것이 뒤섞여 있다는 것입니다.

이런 개념의 뒤섞임을 피하기 위해, 쿠버네티스는 어느 정도 추상화 계층을 제공해서, 개발자는 그저 데이터를 저장할 공간을 요청하고(__persistent volume claim__), 운영팀이 물리적인 스토리지 설정을 제공하게 합니다.

== Persistent Volume과 Persistent Volume Claim

`PersistentVolume`(__PV__)은 관리자가 만들거나, ``Storage Classes``를 사용해 Pod와 독립적으로 동적으로 생성되는 쿠버네티스 리소스입니다.
이는 스토리지 구현의 세부 사항을 담고 있으며, NFS, Ceph, iSCSI, 또는 클라우드 제공업체 전용 스토리지 시스템일 수 있습니다.

`PersistentVolumeClaim`(__PVC__)은 사용자의 스토리지 요청입니다.
특정 volume 크기나, 예를 들어 접근 모드를 요청할 수 있습니다.

=== 정적 프로비저닝과 동적 프로비저닝

Persistent Volume은 **정적**으로 또는 **동적**으로 프로비저닝될 수 있습니다.

정적 프로비저닝은 클러스터 관리자가 기존 스토리지 장치(hostPath, 미리 준비된 NFS 경로, 클라우드 디스크 등)를 가리키는 ``PersistentVolume``을 미리 수동으로 만들어 두는 방식입니다. 이 방식에서는 PV와 PVC를 관리자와 사용자가 각각 수동으로 제공해야 합니다.

동적 프로비저닝은 클러스터 관리자가 스토리지를 미리 준비해 둘 필요를 없애줍니다.
대신, 사용자가 원하는 ``StorageClass``를 참조하는 ``PersistentVolumeClaim``만 만들면, 그에 맞는 실제 스토리지와 ``PersistentVolume``이 자동으로 만들어집니다.
동적 프로비저닝의 주된 목적은 클라우드/온프레미스 스토리지 솔루션과 함께 자동으로 동작하는 것입니다.

[IMPORTANT]
====
``PersistentVolume``은 특정 네임스페이스에 속하지 않는 **클러스터 범위(cluster-scoped)** 리소스라서, 정적 프로비저닝(PV를 직접 만드는 것)에는 보통 클러스터 관리자 권한이 필요합니다. +
**이 실습의 user 계정은 admin 권한이 없기 때문에, 아래 "정적 프로비저닝 예시(참고용)"는 개념 이해를 위해 읽어만 보시고, 실제 실습은 이어지는 "동적 프로비저닝으로 Persistent Volume Claim 만들기"부터 진행하세요.**
====

=== 동적 프로비저닝으로 Persistent Volume Claim 만들기

일반적으로 쿠버네티스 구현체는 기본(default) Storage Class를 제공해서 누구나 동적 프로비저닝을 빠르게 시작할 수 있게 해줍니다.
다음 명령으로 이 클러스터에 준비된 Storage Class 정보를 확인할 수 있습니다:

[.console-input]
[source,bash]
----
oc get sc
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                                              PROVISIONER                           AGE
ocs-external-storagecluster-ceph-rbd (default)    openshift-storage.rbd.csi.ceph.com     31h
----

이 클러스터는 Ceph 기반 외부 스토리지 클러스터를 가리키는 ``ocs-external-storagecluster-ceph-rbd``를 기본 Storage Class로 사용하도록 미리 구성되어 있습니다. (실제 표시되는 이름과 `PROVISIONER` 값은 클러스터 구성에 따라 다를 수 있습니다.)

그런 다음 Persistent Volume Claim을 생성하면 Persistent Volume이 자동으로 생성됩니다. kbd:[CTRL+p]를 사용해서 ``demo-dynamic-persistent.yaml``을 빠르게 열어보세요:

[source, yaml]
----
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: myboot-volumeclaim
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Mi
----

__storage class__를 따로 지정하지 않았지만 이 클러스터에는 기본값(`ocs-external-storagecluster-ceph-rbd`)이 정의되어 있으므로, __PVC__는 암묵적으로 그것을 참조합니다. (이 pod 정의를 앞서 살펴본 정적 프로비저닝 예시의 ``myboot-persistent-volume-claim.yaml``과 비교해 보는 것도 좋습니다.)

[.console-input]
[source,bash]
----
oc apply -f apps/kubefiles/demo-dynamic-persistent.yaml

oc get pvc
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                 STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS                            AGE
myboot-volumeclaim   Pending                                      ocs-external-storagecluster-ceph-rbd   46s
----

__PVC__가 __Pending__ STATUS인 것에 주목하세요. 우리가 만들고 있는 것이 동적 스토리지라는 것을 기억해 보면, 이는 __pod__가 volume을 요청하기 전까지는 __PVC__가 pending 상태로 남아 있고 __PV__도 생성되지 않는다는 의미입니다(스토리지 드라이버의 볼륨 바인딩 모드에 따라, PVC 생성 직후 바로 바인딩되는 경우도 있습니다).

[.console-input]
[source,bash]
----
oc apply -f apps/kubefiles/myboot-pod-volume-pvc.yaml
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME          READY   STATUS    RESTARTS   AGE
myboot-demo   1/1     Running   0          2m36s

[.console-input]
[source,bash]

myboot-volumeclaim   Bound    pvc-6de4f27e-bd40-4b58-bb46-91eb08ca5bd7   1Gi        RWO            ocs-external-storagecluster-ceph-rbd   116s

이제 volume claim이 volume에 __Bound__ 된 것에 주목하세요(요청한 10Mi보다 큰 용량이 잡혀 있을 수 있는데, 스토리지 드라이버의 최소 할당 단위 때문입니다).

마지막으로, __PV__가 자동으로 생성되었는지 확인할 수 있습니다:

pvc-6de4f27e-bd40-4b58-bb46-91eb08ca5bd7   1Gi        RWO            Delete           Bound    myspace/myboot-volumeclaim   ocs-external-storagecluster-ceph-rbd            77s

__CLAIM__ 필드가 __PV__ 생성을 담당한 __PVC__를 가리키는 것에 주목하세요. (정적 프로비저닝과 달리, 이 __PV__는 우리가 직접 만든 것이 아니라 __PVC__를 생성하자 스토리지 드라이버가 자동으로 만들어 준 것입니다.)

== 분산 파일 시스템

클라우드 제공업체는 데이터가 모든 노드에서 항상 사용 가능하도록 분산 스토리지를 제공한다는 점을 알아두는 것이 중요합니다.
마지막 예시에서 봤듯이, 이 storage class는 모든 노드가 동일한 디스크 콘텐츠를 보도록 보장합니다.

예를 들어, 온프레미스에서 쿠버네티스/OpenShift를 사용하고 있거나 특정 벤더 솔루션에 의존하고 싶지 않다면, 쿠버네티스에서도 분산 파일 시스템을 지원합니다.
그런 경우라면 NFS, https://www.gluster.org/[GlusterFS] 또는 https://ceph.io/[Ceph]를 사용하는 것을 권장합니다.

바로 앞서 실습에서 사용한 `ocs-external-storagecluster-ceph-rbd` Storage Class가 이러한 Ceph 기반 분산 스토리지의 실제 예시입니다.
