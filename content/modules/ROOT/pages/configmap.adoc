== 배경지식: ConfigMap

애플리케이션을 여러 환경에서 실행하다 보면 환경에 따라 달라지는 설정값이 생깁니다.

예를 들어 같은 애플리케이션이라도 개발 환경과 운영 환경에서는 다음과 같은 값이 서로 다를 수 있습니다.

* 데이터베이스 주소
* 메시지 브로커 주소
* 외부 API 주소
* 로그 레벨
* 애플리케이션의 기능을 제어하는 설정값

이러한 설정값을 애플리케이션 코드나 컨테이너 이미지 안에 직접 넣어두면, 환경이 바뀔 때마다 코드를 수정하거나 새로운 컨테이너 이미지를 만들어야 할 수 있습니다.

쿠버네티스의 **ConfigMap**은 이러한 **애플리케이션의 설정 정보를 코드와 컨테이너 이미지로부터 분리하여 관리**하기 위한 리소스입니다.

예를 들어 동일한 컨테이너 이미지를 사용하면서도,

----
개발 환경  → DATABASE_HOST=dev-database
테스트 환경 → DATABASE_HOST=test-database
운영 환경  → DATABASE_HOST=prod-database
----

와 같이 환경별로 서로 다른 설정을 전달할 수 있습니다.

이처럼 배포 환경에 따라 달라질 수 있는 설정을 애플리케이션 외부에서 관리하는 것은 12-Factor App에서도 권장하는 방식입니다.

참고: https://12factor.net/config[The Twelve-Factor App - Config]

ConfigMap에는 설정값을 **key=value 형태**로 저장할 수 있으며, Pod에서는 이러한 값을 여러 가지 방법으로 사용할 수 있습니다.

대표적인 방법은 다음과 같습니다.

* 환경 변수로 전달
* 애플리케이션의 명령줄 인자로 전달
* 파일 형태로 Pod에 마운트

이번 실습에서는 가장 이해하기 쉬운 **환경 변수 방식**을 사용합니다.

[IMPORTANT]
====
ConfigMap은 **기밀 정보가 아닌 설정값**을 저장하기 위한 리소스입니다.

비밀번호, API Token, 인증서 Private Key와 같은 민감한 정보는 ConfigMap이 아니라 **Secret**을 사용해야 합니다.
====

이번 실습에서는 다음 흐름을 통해 ConfigMap의 역할을 확인합니다.

. Deployment에 환경 변수를 직접 설정
. 환경 변수를 변경하면 새로운 Pod가 생성되는 과정 확인
. ConfigMap에 설정값 저장
. Deployment에서 ConfigMap 참조
. ConfigMap의 값을 변경
. 기존 Pod의 환경 변수에는 변경 내용이 자동으로 반영되지 않는 것을 확인
. Pod를 다시 생성하여 새로운 ConfigMap 값이 적용되는 것을 확인

=== 환경 변수

실습에서 사용하는 myboot 애플리케이션은 환경 변수에서 설정값을 읽도록 만들어져 있습니다.
MyRESTController.java의 일부 코드는 다음과 같습니다.

[source,java]
----
   @RequestMapping("/configure")
   public String configure() {
        String databaseConn = environment.getProperty("DBCONN","Default");
        String msgBroker = environment.getProperty("MSGBROKER","Default");
        String greeting = environment.getProperty("GREETING","Default");
        String love = environment.getProperty("LOVE","Default");
        return "Configuration: \n"
            + "databaseConn=" + databaseConn + "\n"
            + "msgBroker=" + msgBroker + "\n"
            + "greeting=" + greeting + "\n"
            + "love=" + love + "\n";
   }
----

즉, 애플리케이션은 다음 네 가지 환경 변수를 확인합니다.

* ``DBCONN``
* ``MSGBROKER``
* ``GREETING``
* ``LOVE``

환경 변수가 설정되어 있지 않으면 ``Default``라는 값을 사용합니다.

그럼 먼저 터미널 1에서 ``myboot``를 배포합니다:

=== Deployment에 환경 변수 직접 설정하기

먼저 ConfigMap을 사용하지 않고 Deployment에 직접 환경 변수를 설정해 보겠습니다.

터미널 1에서 다음 명령어를 실행합니다.

[#set-env-vars]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc set env deployment/myboot GREETING="namaste" \
  LOVE="Aloha" \
  DBCONN="jdbc:sqlserver://45.91.12.123:1443;user=MyUserName;password=*****;"
----

``oc set env`` 명령은 Deployment의 **Pod 템플릿에 환경 변수를 추가**합니다.

Deployment의 Pod 템플릿이 변경되었으므로 새로운 ReplicaSet이 만들어지고 새로운 Pod가 생성됩니다.

터미널 2를 확인해 봅니다.

myboot-785ff6bddc-ghwpc   1/1     Running       0          13s
----

터미널 2를 확인하면, 위와 같이 기존 Pod는 종료되면서 새로운 Pod가 생성되는 것을 볼 수 있습니다.

* 애플리케이션의 배포 정의와 설정값이 함께 관리됩니다.
* 여러 Deployment에서 동일한 설정을 재사용하기가 불편합니다.

===  ConfigMap 생성하기

이번에는 애플리케이션의 설정값을 Deployment 밖으로 분리하여 ConfigMap에 저장해 보겠습니다.

ConfigMap은 여러 가지 방법으로 만들 수 있습니다.

예를 들어 ``--from-env-file`` 옵션을 사용하면 ``key=value`` 형식으로 작성된 파일에서 ConfigMap을 생성할 수 있습니다.

[source,text]
----
# 파일에서 ConfigMap을 생성하는 예시
oc create configmap my-config --from-env-file=apps/config/some.properties
----

또는 ``--from-literal`` 옵션을 사용하면 명령줄에서 직접 ``key=value`` 값을 지정할 수 있습니다.

이번 실습에서는 ``--from-literal``을 사용합니다.

[#create-configmap-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc create configmap my-config --from-literal=GREETING=jambo --from-literal=LOVE=Amour
----

생성된 ConfigMap 목록을 확인합니다. 
(TIP: ``configmap``은 ``cm``으로 줄여서 사용할 수 있습니다.)

[#get-configmap-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get cm
----

``my-config`` ConfigMap의 기본 정보를 확인합니다.

[#get-configmap-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get cm my-config
----

ConfigMap에 저장된 실제 값을 확인해 봅니다.

[#get-configmap-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get cm my-config -o json
----


[.console-output]
[source,bash]
----

        "GREETING": "jambo",
        "LOVE": "Amour"
    },
    "kind": "ConfigMap",
...

또는 ``describe`` 명령으로도 확인할 수 있습니다. 

[#describe-configmap-configmaps]

----

이제 Deployment에서는 실제 값을 직접 가지고 있지 않고 이 ConfigMap을 참조하도록 만들어 보겠습니다.

=== Deployment에서 ConfigMap 사용하기

다음 Deployment에서는 ``envFrom``을 사용하여 ``my-config`` ConfigMap의 모든 ``key=value`` 값을 컨테이너의 환경 변수로 가져옵니다. 

[#deploy-myboot-configmap-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1  
        ports:
          - containerPort: 8080
        envFrom:
        - configMapRef:
            name: my-config
        resources:
          requests: 
            memory: "400Mi" 
            cpu: "250m" # 1/4 core
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
EOF
----


여기서 중요한 부분은 다음과 같습니다.

[source,yaml]
----
envFrom:
- configMapRef:
    name: my-config
----

``envFrom``은 ConfigMap 안에 있는 모든 key-value를 컨테이너의 환경 변수로 전달합니다.

터미널 2에서 새로운 Pod가 running 상태로 변하는 것을 확인한 후, 터미널 1에서 configure 엔드포인트를 통해 애플리케이션의 환경 변수 값을 확인합니다.

[#get-config4-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl $IP:$PORT/configure
----

[.console-output]
[source,bash]
----
Configuration for : myboot-84bfcff474-x6xnt
databaseConn=Default
msgBroker=Default
greeting=jambo
love=Amour
----

ConfigMap에 저장했던 값이 애플리케이션의 환경 변수로 전달된 것을 확인할 수 있습니다. 

=== ConfigMap 변경하기

이번에는 실행 중인 애플리케이션이 참조하고 있는 ConfigMap의 값을 변경해 보겠습니다.

OpenShift에서는 ``oc set data`` 명령을 사용하여 기존 ConfigMap의 값을 쉽게 변경할 수 있습니다.

터미널 1에서 다음 명령어를 실행합니다.

[#update-configmap-configmaps]
[.console-input]
[source,bash]
----
oc set data configmap/my-config \
  DBCONN='jdbc:sqlserver://123.123.123.123:1443;databaseName=sampledb' \
  MSGBROKER='tcp://localhost:61616?jms.useAsyncSend=true' \
  GREETING- \
  LOVE-
----

``GREETING-``과 ``LOVE-``는 해당 key를 제거한다는 의미입니다.

변경된 ConfigMap을 확인합니다.

[#get-updated-configmap-configmaps]
[.console-input]
[source,bash]
----
oc get cm my-config -o yaml
----

ConfigMap의 ``data``는 다음과 같이 변경되어 있습니다.

[.console-output]
[source,yaml]
----
data:
  DBCONN: jdbc:sqlserver://123.123.123.123:1443;databaseName=sampledb
  MSGBROKER: tcp://localhost:61616?jms.useAsyncSend=true
----

=== ConfigMap을 변경하면 실행 중인 Pod도 변경될까?

여기서 ConfigMap을 사용할 때 매우 중요한 동작을 확인해 보겠습니다.

현재 Deployment는 ConfigMap을 **환경 변수**로 사용하고 있습니다.

ConfigMap 자체의 내용은 이미 변경되었지만, 실행 중인 컨테이너의 환경 변수는 자동으로 변경되지 않습니다.

환경 변수는 **컨테이너가 시작되는 시점에 설정되기 때문입니다.**

Pod를 재시작하기 전에 다시 ``/configure``를 호출해 봅니다.

[#get-config-before-restart-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl $IP:$PORT/configure
----

여전히 기존 값이 보입니다.

[.console-output]
[source,bash]
----
Configuration for : myboot-84bfcff474-x6xnt
databaseConn=Default
msgBroker=Default
greeting=jambo
love=Amour
----

ConfigMap은 변경되었지만 **이미 실행 중인 컨테이너의 환경 변수는 그대로 유지되고 있는 것**입니다.

또한 ConfigMap을 변경한 것만으로는 Deployment의 Pod 템플릿이 변경되지 않기 때문에 새로운 Pod가 자동으로 만들어지지도 않습니다.

새로운 설정값을 환경 변수로 적용하려면 새로운 Pod가 만들어져야 합니다.

Deployment를 재시작합니다.

[#restart-deployment-configmaps]
[.console-input]
[source,bash]
----
oc rollout restart deployment/myboot
----

터미널 2를 보면 기존 Pod가 종료되고 새로운 Pod가 생성되는 것을 확인할 수 있습니다.

새 Pod가 생성된 후 다시 설정값을 확인합니다.

[#get-config5-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl $IP:$PORT/configure
----

[.console-output]
[source,bash]
----
Configuration for : myboot-694954fc6d-nzdvx
databaseConn=jdbc:sqlserver://123.123.123.123:1443;databaseName=sampledb
msgBroker=tcp://localhost:61616?jms.useAsyncSend=true
greeting=Default
love=Default
----

이번에는 변경한 ConfigMap의 값이 적용되었습니다.

[NOTE]
====
ConfigMap을 **파일(Volume)** 형태로 Pod에 마운트하면 동작 방식이 다릅니다.

일반적인 ConfigMap Volume은 ConfigMap이 변경되면 변경된 파일이 실행 중인 Pod에도 일정 시간이 지난 후 반영될 수 있습니다.

하지만 애플리케이션이 변경된 파일을 다시 읽을 수 있도록 만들어져 있어야 실제 애플리케이션 설정에도 반영됩니다.

이번 실습에서는 ConfigMap을 **환경 변수로 사용하는 방식**에 집중합니다.
====

ConfigMap을 가지고 즐길 수 있는 방법은 이 밖에도 많습니다. 공식 문서에서는 Deployment 대신 Pod 스펙을 직접 조작하지만 결과는 기본적으로 동일합니다:
https://kubernetes.io/docs/tasks/configure-pod-container/configure-pod-configmap


== 실습 환경 정리

터미널 2에서 kbd:[Ctrl+c]를 눌러 실행 중인 명령어를 취소하고, 생성했던 리소스들을 정리합니다.

[#clean-configmaps]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc delete deployment myboot
oc delete cm my-config
oc delete service myboot
----
