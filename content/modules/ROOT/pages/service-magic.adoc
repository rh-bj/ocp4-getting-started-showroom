= Service의 마법

앞 장에서는 Service를 Deployment 하나에 연결해서 사용했습니다. 이번 장에서는 그 이면의 진짜 동작 원리를 파헤쳐 봅니다: Service는 사실 Deployment와 직접 연결되어 있지 않습니다. Service는 오직 __레이블 셀렉터__만 보고, 그 레이블과 일치하는 Pod들의 IP 목록(__Endpoints__)을 실시간으로 관리할 뿐입니다. 이 관계를 눈으로 확인하기 위해, 서로 다른 애플리케이션 3개를 배포한 뒤 Service의 레이블을 하나씩 붙였다 뗐다 하면서 트래픽이 어떻게 옮겨 다니는지 살펴보겠습니다.

네임스페이스를 생성합니다:

[#create-namespace]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl create namespace {user}-funstuff
kubectl config set-context --current --namespace={user}-funstuff
----

먼저 서로 다른 언어로 작성된 애플리케이션 세 개(mypython, mygo, mynode)를 배포합니다. 각각 `app=mypython`, `app=mygo`, ``app=mynode``라는 서로 다른 레이블을 가지고 있으며, 아직은 어떤 것도 ``inservice=mypods``라는 레이블은 가지고 있지 않다는 점에 주목하세요 — 이것이 잠시 후 만들 Service의 셀렉터입니다.

== mypython 배포하기

[#deploy-mypython]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mypython-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mypython
  template:
    metadata:
      labels:
        app: mypython
    spec:
      containers:
      - name: mypython
        image: quay.io/rhdevelopers/mypython:v1
        ports:
        - containerPort: 8000
EOF
----

== mynode 배포하기

[#deploy-mynode]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mynode-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mynode
  template:
    metadata:
      labels:
        app: mynode
    spec:
      containers:
      - name: mynode
        image: quay.io/rhdevelopers/mynode:v1
        ports:
        - containerPort: 8000
EOF
----

세 애플리케이션이 모두 잘 떠 있는지, 그리고 각각 어떤 레이블을 가지고 있는지 확인합니다:

[#labels-service-magic]
[.console-input]
[source, bash]
----
kubectl get pods -w --show-labels
----

[.console-output]
[source,bash]
----
NAME                                   READY   STATUS    RESTARTS   AGE     LABELS
mygo-deployment-6d944c5c69-kcvmk       1/1     Running   0          2m11s   app=mygo,pod-template-hash=6d944c5c69
mynode-deployment-fb5457c5-hhz7h       1/1     Running   0          2m1s    app=mynode,pod-template-hash=fb5457c5
mypython-deployment-6874f84d85-2kpjl   1/1     Running   0          3m53s   app=mypython,pod-template-hash=6874f84d85
----

이제 Service를 만듭니다. ``selector``가 ``inservice: mypods``로 지정되어 있는데, 앞서 확인했듯이 지금 떠 있는 Pod 중에는 이 레이블을 가진 Pod가 __하나도 없습니다__. 이 상태에서 Service가 어떻게 동작하는지 지켜보는 것이 이번 실습의 핵심입니다:

[#deploy-myservice]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: my-service
  labels:
    app: mystuff
spec:
  ports:
  - name: http
    port: 8000
  selector:
    inservice: mypods
  type: LoadBalancer
EOF
----

Service를 describe해서 `Endpoints` 항목이 어떻게 표시되는지 확인합니다:

[#describe-myservice-service-magic]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl describe service my-service
----

Service를 만들 때마다 쿠버네티스는 __Endpoints__라는 객체를 자동으로 함께 관리합니다. Endpoints는 그 Service의 셀렉터와 일치하는 Pod들의 IP:Port 목록으로, 실제 트래픽이 전달될 대상 목록입니다. Service의 셀렉터에 맞는 Pod가 하나도 없으니, Endpoints도 비어 있을 것입니다:

[#get-endpoints-myservice]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get endpoints
----

[.console-output]
[source,bash]
----
NAME         ENDPOINTS   AGE
my-service   <none>      2m6s
----

또는 다음 명령으로 service 엔드포인트만 추출해 볼 수 있는데, 결과가 없을 것입니다:

[#get-endpoints1]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get endpoints my-service -o jsonpath='{.subsets[].addresses[*].ip}{"\n"}'
----

Endpoints가 비어 있는데도 실제로 요청을 보내면 어떻게 되는지 직접 확인해 봅시다. service에 접근하기 위해 ``IP``와 `PORT` 환경 변수를 초기화합니다:

[source,bash]
----

이제 `mypython` Pod에 Service가 찾고 있는 레이블(`inservice=mypods`)을 붙여 봅시다. Deployment를 다시 배포하거나 Service를 수정하는 것이 아니라, Pod에 레이블 하나만 추가하는 것으로 충분합니다. loop 창을 지켜보면, 레이블을 붙이는 즉시 연결 거부가 멈추고 응답이 오기 시작하는 것을 볼 수 있을 것입니다:

[#label-mypython]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl label pod -l app=mypython inservice=mypods
----

[.console-output]
[source,bash]
----
curl: (7) Failed to connect to 35.224.233.213 port 8000: Connection refused
Python Hello on mypython-deployment-6874f84d85-2kpjl
Python Hello on mypython-deployment-6874f84d85-2kpjl
Python Hello on mypython-deployment-6874f84d85-2kpjl
----

이번에는 `mynode` Pod에도 같은 레이블을 붙여 봅시다. ``mypython``의 레이블은 그대로 두었으므로, 이제 두 Pod __모두__ Service의 대상이 됩니다. loop 창에는 Python과 Node의 응답이 섞여서 나타날 것입니다:

[#label-mynode]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl label pod -l app=mynode inservice=mypods
----

[.console-output]
[source,bash]
----
Python Hello on mypython-deployment-6874f84d85-2kpjl
Python Hello on mypython-deployment-6874f84d85-2kpjl
Node Hello on mynode-deployment-fb5457c5-hhz7h 0
Node Hello on mynode-deployment-fb5457c5-hhz7h 1
Python Hello on mypython-deployment-6874f84d85-2kpjl
Python Hello on mypython-deployment-6874f84d85-2kpjl
Python Hello on mypython-deployment-6874f84d85-2kpjl
----

같은 방식으로 ``mygo``도 추가해 봅시다. 이제 세 애플리케이션이 모두 하나의 Service 뒤에서 함께 트래픽을 나눠 받게 됩니다:

[#label-mygo]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl label pod -l app=mygo inservice=mypods
----

[.console-output]
[source,bash]
----
Node Hello on mynode-deployment-fb5457c5-hhz7h 59
Node Hello on mynode-deployment-fb5457c5-hhz7h 60
Go Hello on mygo-deployment-6d944c5c69-kcvmk
Python Hello on mypython-deployment-6874f84d85-2kpjl
Python Hello on mypython-deployment-6874f84d85-2kpjl
----

이제 Endpoints를 다시 확인해 보면, 세 Pod의 IP가 모두 들어 있을 것입니다:

[#get-endpoints2]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get endpoints my-service -o jsonpath='{.subsets[].addresses[*].ip}{"\n"}'
----

[.console-output]
[source,bash]
----
10.130.2.43 10.130.2.44 10.130.2.45
----

Pod IP를 확인해서 방금 본 Endpoints 목록의 IP들과 실제로 일치하는지 비교해 보세요:

[#pod-ips]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get pods -o wide
----

마지막으로, Pod 자체를 지우지 않고도 Service에서 뺄 수 있다는 것을 보여드리겠습니다. 레이블 이름 뒤에 ``-``를 붙이면 그 레이블만 제거됩니다. `mypython` Pod는 계속 실행되지만, 더 이상 Service의 셀렉터와 일치하지 않으므로 Endpoints 목록에서는 빠지게 됩니다:

[#remove-label]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl label pod -l app=mypython inservice-
----

[#get-endpoints3]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
kubectl get endpoints my-service -o jsonpath='{.subsets[].addresses[*].ip}{"\n"}'
----

[.console-output]
[source,bash]
----
10.130.2.44 10.130.2.45
----

``mypython``의 IP는 더 이상 목록에 없습니다. 이번 장에서 확인했듯, Service는 Deployment나 특정 애플리케이션을 알지 못합니다. 그저 "이 레이블을 가진 Pod들에 접속을 전달한다"는 규칙만 알고 있을 뿐이며, 이 단순한 원리 덕분에 Blue/Green 배포나 카나리 배포 같은 여러 응용이 가능해집니다.
