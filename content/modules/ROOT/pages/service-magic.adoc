= Service의 마법
include::vars.adoc[]

앞 장에서는 Service를 생성하여 Deployment가 만든 Pod에 접근했습니다. 이번 장에서는 그 이면에서 Service가 **어떻게 트래픽을 전달할 Pod를 찾는지** 살펴보겠습니다.

여기서 중요한 점은 **Service가 Deployment와 직접 연결되어 있는 것은 아니라는 것**입니다. Service는 자신의 **레이블 셀렉터(Label Selector)** 와 일치하는 레이블을 가진 Pod를 찾아 트래픽을 전달합니다.

예를 들어 Service에 다음과 같은 셀렉터가 설정되어 있다면,
[source,yaml]
-----------
selector:
  app: my-app
-----------

Service는 Deployment의 이름이나 Pod의 이름을 확인하는 것이 아니라, 다음과 같이 `app=my-app` 레이블을 가진 Pod를 대상으로 선택합니다.

[source,text]
--------------------------
Service
selector: app=my-app
│
│ 레이블이 일치하는 Pod를 찾음
│
├── Pod A  [app=my-app]  ✓
├── Pod B  [app=my-app]  ✓
└── Pod C  [app=other]   ✗
--------------------------

Kubernetes는 이렇게 선택된 Pod들의 네트워크 정보를 **EndpointSlice**에 자동으로 등록하고 관리합니다. Pod가 새로 생성되거나 삭제되거나, Pod의 레이블이 변경되면 Service가 사용할 대상도 그에 맞게 자동으로 변경됩니다.
이번 실습에서는 이 관계를 직접 확인해 보겠습니다. 

서로 다른 애플리케이션 3개를 배포한 뒤, **각 Pod가 Service의 셀렉터와 일치하도록 레이블을 붙이거나 제거하면서** Service가 어느 Pod로 트래픽을 전달하는지 살펴보겠습니다.
이를 통해 Service가 특정 Deployment에 고정되어 있는 것이 아니라, **레이블 셀렉터를 기준으로 동적으로 Pod를 선택한다**는 것을 직접 확인할 수 있습니다.

먼저 네임스페이스를 생성합니다:

* *Terminal#1에서 작업*

[#create-namespace]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc new-project {user}-funstuff
----

그 다음, 서로 다른 언어로 작성된 애플리케이션 세 개(mypython, mygo, mynode)를 배포합니다. 각각 `app=mypython`, `app=mygo`, ``app=mynode``라는 서로 다른 레이블을 가지고 있으며, 아직은 어떤 것도 ``inservice=mypods``라는 레이블은 가지고 있지 않다는 점에 주목하세요 — 이것이 잠시 후 만들 Service의 셀렉터입니다.

== mypython 배포하기

[#deploy-mypython]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mypython-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mypython
  template:
    metadata:
      labels:
        app: mypython
    spec:
      containers:
      - name: mypython
        image: quay.io/rhdevelopers/mypython:v1
        ports:
        - containerPort: 8000
EOF
----

세 애플리케이션이 모두 잘 떠 있는지, 그리고 각각 어떤 레이블을 가지고 있는지 확인합니다:

[#labels-service-magic]
[.console-input]
[source, bash]
----
oc get pods -w --show-labels
----

[.console-output]
[source,bash]
----
NAME                                   READY   STATUS    RESTARTS   AGE     LABELS
mygo-deployment-6d944c5c69-kcvmk       1/1     Running   0          2m11s   app=mygo,pod-template-hash=6d944c5c69
mynode-deployment-fb5457c5-hhz7h       1/1     Running   0          2m1s    app=mynode,pod-template-hash=fb5457c5
mypython-deployment-6874f84d85-2kpjl   1/1     Running   0          3m53s   app=mypython,pod-template-hash=6874f84d85
----

NOTE: 배포된 pod를 label값을 포함하여 실시간으로 확인합니다. 배포되어 있는 pod들은 inservice=mypods label 값이 없는 것을 확인할 수 있습니다.

이제 Service를 만듭니다. ``selector``가 ``inservice: mypods``로 지정되어 있는데, 앞서 확인했듯이 지금 떠 있는 Pod 중에는 이 레이블을 가진 Pod가 __하나도 없습니다__. 이 상태에서 Service가 어떻게 동작하는지 지켜보는 것이 이번 실습의 핵심입니다:

[#deploy-myservice]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Service
metadata:
  name: my-service
  labels:
    app: mystuff
spec:
  ports:
  - name: http
    port: 8000
  selector:
    inservice: mypods
EOF
----

Service를 describe해서 `Endpoints` 항목이 어떻게 표시되는지 확인합니다:

[#describe-myservice-service-magic]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc describe service my-service
----

Service를 만들 때마다 쿠버네티스는 __EndpointSlice__라는 객체를 자동으로 함께 관리합니다. EndpointSlice는 그 Service의 셀렉터와 일치하는 Pod들의 IP:Port 목록으로, 실제 트래픽이 전달될 대상 목록입니다. Service의 셀렉터에 맞는 Pod가 하나도 없으니, EndpointSlice도 비어 있을 것입니다:

[#get-endpoints-myservice]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get endpointslice
----

[.console-output]
[source,bash]
----
NAME               ADDRESSTYPE   PORTS     ENDPOINTS   AGE
my-service-4lt5p   IPv4          <unset>   <unset>     96s
----

endpointslice가 비어 있는데도 실제로 요청을 보내면 어떻게 되는지 직접 확인해 봅시다. service에 접근하기 위해 ``IP``와 `PORT` 환경 변수를 초기화합니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
IP=$(oc get service {tmp-service-exposed} -o jsonpath="{.spec.clusterIP}")
PORT=$(oc get service {tmp-service-exposed} -o jsonpath="{.spec.ports[*].port}")
----

이제 `mypython` Pod에 Service가 찾고 있는 레이블(`inservice=mypods`)을 붙여 봅시다. Deployment를 다시 배포하거나 Service를 수정하는 것이 아니라, Pod에 레이블 하나만 추가하는 것으로 충분합니다. loop 창을 지켜보면, 레이블을 붙이는 즉시 연결 거부가 멈추고 응답이 오기 시작하는 것을 볼 수 있을 것입니다:

* *Terminal#3에서 작업*

[#label-mypython]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc label pod -l app=mypython inservice=mypods
----

Python Hello on mypython-deployment-6874f84d85-2kpjl
Python Hello on mypython-deployment-6874f84d85-2kpjl

이제 endpointslice를 다시 확인해 보면, 세 Pod의 IP가 모두 들어 있을 것입니다:

[#get-endpoints2]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get endpointslice
----

[.console-output]
[source,bash]
----
10.130.2.43 10.130.2.44 10.130.2.45
----

Pod IP를 확인해서 방금 본 Endpoints 목록의 IP들과 실제로 일치하는지 비교해 보세요:

[#pod-ips]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get pods -o wide
----

마지막으로, Pod 자체를 지우지 않고도 Service에서 뺄 수 있다는 것을 보여드리겠습니다. 레이블 이름 뒤에 ``-``를 붙이면 그 레이블만 제거됩니다. `mypython` Pod는 계속 실행되지만, 더 이상 Service의 셀렉터와 일치하지 않으므로 Endpoints 목록에서는 빠지게 됩니다:

[#remove-label]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc label pod -l app=mypython inservice-
----

[#get-endpoints3]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get endpointslice
----

[.console-output]
[source,bash]
----
10.130.2.44 10.130.2.45
----

``mypython``의 IP는 더 이상 목록에 없습니다. 이번 장에서 확인했듯, Service는 Deployment나 특정 애플리케이션을 알지 못합니다. 그저 "이 레이블을 가진 Pod들에 접속을 전달한다"는 규칙만 알고 있을 뿐이며, 이 단순한 원리 덕분에 Blue/Green 배포나 카나리 배포 같은 여러 응용이 가능해집니다.
