= Secret
include::vars.adoc[]
include::_attributes.adoc[]
:watch-terminal: 터미널 2

``Secret``은 비밀번호, 토큰, 인증서와 같이 **민감한 데이터를 애플리케이션과 분리하여 저장하고 전달하기 위한 Kubernetes 리소스**입니다.

앞에서 살펴본 ``ConfigMap``과 사용 방법은 비슷하지만 목적이 다릅니다.

[source,text]
-------------------------------------
ConfigMap
└─ 일반적인 설정 정보
예: URL, 포트 번호, 애플리케이션 설정값

Secret
└─ 민감한 정보
예: 비밀번호, API 토큰, TLS 인증서, 레지스트리 인증 정보
-------------------------------------

예를 들어 애플리케이션이 데이터베이스에 접속하기 위해 사용자 이름과 비밀번호가 필요하다고 가정해 보겠습니다.

이 값을 애플리케이션 코드나 컨테이너 이미지 안에 직접 작성하면 해당 코드를 보거나 이미지를 사용하는 사람에게 자격 증명이 노출될 위험이 있습니다.

[source,text]
----------------------------------------------
애플리케이션 코드 / 컨테이너 이미지

DB_USER=myuser
DB_PASSWORD=my-secret-password   ← 민감한 정보가 포함됨
----------------------------------------------

대신 이러한 정보를 Secret으로 분리하여 관리할 수 있습니다.

[source,text]
-----------
Secret
│
├─ username
└─ password
│
▼
Application
-----------

Pod는 필요한 Secret을 **환경 변수** 또는 **볼륨으로 마운트된 파일** 형태로 전달받아 사용할 수 있습니다.

대표적으로 Secret에는 다음과 같은 데이터를 저장할 수 있습니다.

* 데이터베이스 사용자 이름과 비밀번호
* API Token
* 이미지 레지스트리 인증 정보
* TLS 인증서와 Private Key
* SSH Key

=== Secret의 데이터는 Base64로 표현됩니다

Secret을 YAML이나 JSON으로 조회하면 ``data``에 저장된 값이 그대로 표시되지 않고 **Base64로 인코딩된 문자열**로 보입니다.

예를 들어 다음 Secret이 있다고 가정해 보겠습니다.

[source,yaml]
----------------------
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
  type: Opaque
data:
  username: YWRtaW4=
  password: cGFzc3dvcmQ=
----------------------

Base64 값을 디코딩하면 실제 값을 확인할 수 있습니다.

[source,bash]
----------------------
echo 'YWRtaW4=' | base64 -d
----------------------

[source,text]
----------------------
admin
----------------------

IMPORTANT: **Base64는 암호화가 아닙니다.** Base64는 바이너리 데이터를 문자열로 표현하기 위한 **인코딩 방식**일 뿐이며, 누구나 쉽게 원래 값으로 되돌릴 수 있습니다. 따라서 Secret의 값이 Base64로 표시된다는 사실 자체가 데이터를 안전하게 보호해 주는 것은 아닙니다.

WARNING: Secret은 민감한 데이터를 애플리케이션 코드나 컨테이너 이미지와 분리하여 관리할 수 있도록 해 주지만, **Secret 리소스를 사용하는 것만으로 데이터가 자동으로 암호화되는 것은 아닙니다.** +
Secret 역시 다른 Kubernetes 리소스와 마찬가지로 클러스터의 `etcd` 데이터 저장소에 저장됩니다. Secret을 API를 통해 조회하거나 수정할 수 있는 권한은 Kubernetes/OpenShift의 **RBAC**으로 제어됩니다. +
또한 Kubernetes와 OpenShift 모두 기본 설정에서는 `etcd`에 저장되는 Secret 데이터가 **저장 시점(at rest)에 암호화되지 않습니다.** +
OpenShift에서는 클러스터 관리자가 `etcd` 암호화를 활성화하여 Secret, ConfigMap, Route, OAuth Token 등의 데이터를 저장 시점에 추가로 암호화할 수 있습니다.
(OpenShift의 etcd 암호화에 대해서는 link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/etcd/enabling-etcd-encryption[OpenShift 공식 문서^]에서 자세히 확인할 수 있습니다.)

따라서 Secret을 사용할 때에는 다음과 같이 이해하는 것이 중요합니다.

[source,text]
-----------------
Secret을 사용하는 이유

민감한 정보를
애플리케이션 코드나 컨테이너 이미지에 직접 포함하지 않고
│
▼
별도의 Kubernetes 리소스로 분리하여
│
▼
필요한 Pod에만 전달하고
RBAC 등을 통해 접근을 제어
-----------------

즉, Secret은 **민감한 정보를 안전하게 관리하기 위한 기반을 제공하는 Kubernetes 리소스**이며, 실제 운영 환경에서는 적절한 RBAC 설정과 저장 데이터 암호화 등의 보안 설정을 함께 적용해야 합니다.

== Secret 생성하기

앞에서는 데이터베이스 연결 문자열(`user=MyUserName;password=pass:[*****]`)을 저장하는 데 ``ConfigMap``을 사용했습니다. 이번에는 이 민감한 데이터를 저장할 secret을 생성해 봅시다.

`oc` CLI는 데이터베이스 로그인처럼 일반적인(또는 `opaque`) secret을 생성하는 기능을 어느 정도 지원합니다.

[#create-secret-cli-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc create secret generic mysecret --from-literal=user='MyUserName' --from-literal=password='mypassword'
----

[#get-secret-cli-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get secrets
----

그러면 다음과 비슷한 출력을 얻게 됩니다. OpenShift는 빌드나 배포에 필요한 서비스 계정 토큰 같은 Secret을 기본적으로 여러 개 만들어 두므로, 방금 만든 `mysecret` 외에도 낯선 이름들이 함께 보일 것입니다:

[.console-output]
[source,bash]
----
NAME                       TYPE                                  DATA   AGE
builder-dockercfg-96ml5    kubernetes.io/dockercfg               1      3d6h
builder-token-h5g82        kubernetes.io/service-account-token   4      3d6h
builder-token-vqjqz        kubernetes.io/service-account-token   4      3d6h
default-dockercfg-bsnjr    kubernetes.io/dockercfg               1      3d6h
default-token-bl77s        kubernetes.io/service-account-token   4      3d6h
default-token-vlzsl        kubernetes.io/service-account-token   4      3d6h
deployer-dockercfg-k6npn   kubernetes.io/dockercfg               1      3d6h
deployer-token-4hb78       kubernetes.io/service-account-token   4      3d6h
deployer-token-vvh6r       kubernetes.io/service-account-token   4      3d6h
mysecret                   Opaque                                2      5s
----

이것은 ``ConfigMap``이 아니라 ``Secret``이기 때문에, user와 password 값이 바로 보이지 않습니다:

[#describe-secret-cli-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc describe secret mysecret
----

[.console-output]
[source,bash]
----
Name:         mysecret
Namespace:    myspace
Labels:       <none>
Annotations:  <none>

Type:  Opaque

Data
====
password:  10 bytes
user:      10 bytes
----

[#get-secret-cli-yaml-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get secret mysecret -o yaml
----


[source,yaml]
----
apiVersion: v1
data:
  password: bXlwYXNzd29yZA==
  user: TXlVc2VyTmFtZQ==
kind: Secret
metadata:
  creationTimestamp: "2020-03-31T20:19:26Z"
  name: mysecret
  namespace: myspace
  resourceVersion: "4944690"
  selfLink: /api/v1/namespaces/myspace/secrets/mysecret
  uid: e8c5f12e-bd71-4d6b-8d8c-7af9ed6439f8
type: Opaque
----

위의 password 필드 값이 base64로 인코딩되어 있다는 것을 확인하기 위해 이 값을 아래 echo 명령에 복사해 넣습니다.

[#get-secret-cli-password-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
echo 'bXlwYXNzd29yZA==' | base64 --decode
----

[.console-output]
[source,bash]
----
mypassword
----

[TIP]
====
시간이 부족하다면 대신 다음 명령을 실행할 수 있습니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
B64_PASSWORD=$(oc get secret mysecret -o jsonpath='{.data.password}')
echo "password:$B64_PASSWORD is decoded as $(echo $B64_PASSWORD | base64 --decode)"
----

====

그런 다음 사용자 이름에 대해서도 똑같이 해 봅니다.

[#get-secret-cli-username-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
echo 'TXlVc2VyTmFtZQ==' | base64 --decode
----

[.console-output]
[source,bash]
----
MyUserName
----

[TIP]
====
시간이 부족하다면 대신 다음 명령을 실행할 수 있습니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
B64_DATA=$(oc get secret mysecret -o jsonpath='{.data.user}')
echo "username:$B64_DATA is decoded as $(echo $B64_DATA | base64 --decode)"
----

====


또는 ``oc``를 사용해서 값을 가져올 수도 있습니다:

[#get-secret-kubectl-password-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get secret mysecret -o jsonpath='{.data.password}' | base64 --decode 
----

== Secret 사용하기

:quick-open-file: myboot-deployment-configuration-secret.yml

방금 만든 secret을 사용하는 deployment인 ``{quick-open-file}``을 살펴봅시다.

[.console-output]
[source,yaml,subs="+macros,+attributes"]
.{quick-open-file}
----
include::example$myboot-deployment-configuration-secret.yml[]
----
<.> 이 부분은 pod가 secret을 어디에서 찾을지 결정합니다. pod 안의 `/mystuff/secretstuff` 디렉터리에 있는 파일 형태로 제공됩니다.
<.> 이 부분은 ``mysecretvolume``이 실제로 무엇을 마운트해야 하는지 정의합니다. 여기서는 위에서 방금 만든 secret인 ``mysecret``입니다.

deployment(pod)가 secret을 사용할 수 있게 하는 한 가지 방법은 Volume Mount를 통해 제공하는 것입니다:

[source, yaml]
----
        volumeMounts:          
          - name: mysecretvolume
            mountPath: /mystuff/mysecretvolume
----

이 볼륨을 사용하도록 deployment를 업데이트해 봅시다:

[#replace-myboot-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc replace -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
          - containerPort: 8080
        volumeMounts:          
          - name: mysecretvolume #<.>
            mountPath: /mystuff/secretstuff
            readOnly: true
        resources:
          requests: 
            memory: "400Mi" 
            cpu: "250m" # 1/4 core
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
      volumes:
        - name: mysecretvolume #<.>
          secret:
            secretName: mysecret
EOF
----

__deployment가 업데이트되고 나면__, 새로 생성된 Pod에 exec로 접속합니다:

[#print-secrets-volume-secrets]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
PODNAME=$(oc get pod -l app=myboot --field-selector pass:['status.phase!=Terminating'] -o name)
oc exec $PODNAME -- ls -l /mystuff/secretstuff
oc exec $PODNAME -- cat /mystuff/secretstuff/password
----

결과:

[.console-output]
[source,bash]
----
total 0
lrwxrwxrwx. 1 root root 15 Jul 19 03:37 password -> ..data/password #<.>
lrwxrwxrwx. 1 root root 11 Jul 19 03:37 user -> ..data/user
mypassword #<.>
----
<.> secret 정의를 다시 떠올려 보세요. secret의 `.data` 섹션 아래에 있는 각 필드가 마운트된 secret을 나타내는 이 디렉터리 안의 파일이 되었습니다.
<.> `password` 파일의 내용을 ``cat``으로 확인하면 위에서 정의한 ``secret``의 `.data.password` 필드 값을 확인할 수 있습니다.

[TIP]
====
또는 다음 명령을 실행해서 pod에 rsh로 접속해 직접 둘러볼 수도 있습니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
PODNAME=$(oc get pod -l app=myboot --field-selector pass:['status.phase!=Terminating'] -o name)
oc exec -it $PODNAME -- /bin/bash
----
====


그런데 애플리케이션은 이 디렉터리에서 자격 증명을 찾아야 한다는 것을 어떻게 알까요? 애플리케이션(또는 properties)에 하드코딩할 수도 있지만, 환경 변수를 통해 `/mystuff/mysecretvolume` 경로를 pod에 제공해서 애플리케이션이 어디를 찾아야 할지 알게 할 수도 있습니다.

[TIP]
====
secret을 환경 변수로 직접 노출하는 것도 가능하지만, 이는 이 튜토리얼의 범위를 벗어납니다.
====

secret에 대해 더 자세히 알아보려면 https://kubernetes.io/docs/concepts/configuration/secret/[여기]를 참고하세요.
