== '리소스와 제한' 파트에서 사용한 deployment를 삭제한 경우

[TIP,subs="attributes+,+macros"]
====
방금 xref::resources.adoc[리소스와 제한 섹션, window=_blank]에서 넘어왔다면 필요한 pod와 deployment가 이미 실행 중일 것입니다. 그렇지 않다면 {user}-{set-namespace}에 필요한 요소들을 배포하기 위해 다음 명령을 실행해야 합니다.
====

만약 '리소스와 제한' 파트에서 사용한 deployment를 삭제해버렸다면 다음 명령어를 통해 Spring Boot 앱을 배포합니다:

[#deploy-myboot-rolling]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
###################################################
### '리소스와 제한' 파트에서 사용한 deployment를 삭제한 경우에만 실행
###################################################
cat <<EOF | oc create -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
          - containerPort: 8080
        resources:
          requests: 
            memory: "400Mi" 
            cpu: "250m" # 1/4 core
          # NOTE: These are the same limits we tested our Docker Container with earlier
          # -m matches limits.memory and --cpus matches limits.cpu
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
EOF
----

[#deploy-myboot-rolling]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
###################################################
### '리소스와 제한' 파트에서 사용한 service를 삭제한 경우에만 실행
###################################################
cat <<EOF | oc create -f -
apiVersion: v1
kind: Service
metadata:
  name: myboot
  labels:
    app: myboot    
spec:
  ports:
  - name: http
    port: 8080
  selector:
    app: myboot
EOF
----

Deployment를 describe(또는 `oc edit`)합니다:

:describe-deployment-name: myboot
:section-k8s: rolling-init

include::partial$describe-deployment.adoc[]

// The .no-query-replace tells the course ui to not attempt to replace tokens between % %
[.no-query-replace]
[.console-output]
[source,bash]
----
.
.
.
Replicas:               1 desired | 1 updated | 1 total | 1 available | 0 unavailable
StrategyType:           RollingUpdate
MinReadySeconds:        0
RollingUpdateStrategy:  25% max unavailable, 25% max surge
.

----

`StrategyType` 옵션에는 ``RollingUpdate``와 ``Recreate``가 있습니다(``Recreate``는 기존 Pod를 모두 내린 뒤에 새 Pod를 올리는, 더 단순하지만 다운타임이 있는 전략입니다). ``RollingUpdateStrategy``의 ``max unavailable``은 전환 중 동시에 내려갈 수 있는 Pod의 최대 비율을, ``max surge``는 원래 복제본 수보다 얼마나 더 많은 Pod를 일시적으로 추가할 수 있는지를 뜻합니다.

이제 복제본을 2개로 늘려서, 앞으로 있을 롤링 업데이트에서 Pod가 여러 개일 때 전환 과정을 관찰할 수 있게 준비해 둡시다. 복제본 수를 변경합니다:

[#edit-deployment-replicas-rolling]
[.console-input]
[source, bash]
----
oc edit deployment myboot
----

(위 명령어 대신 목적에 따라 oc scale, oc set image 등 간단한 명령어도 있지만, 여기에서는 `oc edit` 명령어를 통해 deployment의 내용을 수정하는 방법을 확인해봅시다)

"replicas"를 찾습니다:

[.console-output]
[source,yaml]
----
spec:
  progressDeadlineSeconds: 600
  replicas: 1
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app: myboot
----

그리고 "2"로 변경합니다:

[.console-output]
[source, yaml]
----
spec:
  progressDeadlineSeconds: 600
  replicas: 2
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app: myboot
----

TIP: 편집기의 단축키는 아래와 같습니다. +
- *`i`* : 입력 모드로 전환(커서 앞에서 입력 시작) +
- 입력모드 전환 후, 방향키로 커서를 이동 및 `백스페이스` 로 문자 삭제 가능 +
- *`:`* : 커멘드라인 모드로 전환 +
-(커맨드라인 모드에서) *`w`* : 파일 저장 +
-(커맨드라인 모드에서) *`q`* : 파일 종료 +

TIP: 아래와 같은 순서로 작업하세요. +
1. "replicas: 1"에서 숫자 1에 커서를 두고 `i` 키를 눌러 입력모드로 전환하세요. +
2. `방향키` 와 `백스페이스` 를 이용하여 숫자 "1"을 삭제 후, "2"를 입력하세요. +
3. `esc` 키를 눌러 입력모드를 종료하세요. +
4. `:` 키를 눌러 커멘드라인 모드로 전환하세요. +
5. `wq` 를 입력한 후 `enter` 키를 누르세요.


편집기를 저장하고 닫으면 새로운 pod가 생겨납니다:

[source, bash]
----

----

[.console-output]
[source,bash]
----

myboot-d78fb6d58-2fqml   1/1     Running   0          25s
myboot-d78fb6d58-ljkjp   1/1     Running   0          3m
----

이제 실제로 롤링 업데이트를 일으켜 봅시다. deployment에 연결된 이미지를 변경합니다:

[#edit-deployment-v2-rolling]
[.console-input]
[source, bash]
----
oc edit deployment myboot
----

image 속성을 찾습니다:

[source, yaml]
----
    spec:
      containers:
      - image: quay.io/rhdevelopers/myboot:v1
        imagePullPolicy: IfNotPresent
        name: myboot
----

그리고 이미지를 ``myboot:v2``로 변경합니다:

[source, yaml]
----
    spec:
      containers:
      - image: quay.io/rhdevelopers/myboot:v2
        imagePullPolicy: IfNotPresent
        name: myboot
----

-(커맨드라인 모드에서) *`q`* : 파일 종료 +

TIP: 아래와 같은 순서로 작업하세요. +
1. "image: quay.io/rhdevelopers/myboot:v1"에서 숫자 1에 커서를 두고 `i` 키를 눌러 입력모드로 전환하세요. +

4. `:` 키를 눌러 커멘드라인 모드로 전환하세요. +

[IMPORTANT]
====
현재 이 Deployment에는 아직 Liveness/Readiness Probe가 정의되어 있지 않으므로, 롤오버가 진행되는 동안 loop 창에서 다음과 같은 연결 오류가 몇 차례 발생할 수 있습니다:

[.console-output]
[source,bash]
----
Aloha from Spring Boot! 119 on myboot-d78fb6d58-2zp4h
curl: (7) Failed to connect to 192.168.99.100 port 31528: Connection refused
----

Readiness Probe가 없으면 쿠버네티스는 컨테이너가 `Running` 상태가 되는 즉시 그 Pod를 Service의 Endpoints에 추가합니다. 하지만 Spring Boot 애플리케이션이 실제로 요청을 받을 준비가 되기까지는 그보다 조금 더 시간이 걸리기 때문에, 그 짧은 틈에 들어온 요청은 실패합니다(이 문제는 xref:live-ready.adoc[Liveness와 Readiness] 장에서 Probe를 추가해 직접 해결해 봅니다).

연결 오류 없이 롤링 업데이트가 되는 것을 확인하시려면 Spring Boot 이미지 대신 Quarkus 이미지를 사용해 보세요.

[#describe-rollback-quarkus-rolling]
[.console-input]
[source, bash]
----
oc set image deployment/myboot myboot=quay.io/rhdevelopers/quarkus-demo:v1
----

그러면 오류가 발생하지 않아야 합니다. Quarkus는 그야말로 놀라울 정도로 빠르게 부팅됩니다.

[.console-output]
[source,bash]
----
Aloha from Spring Boot! 62 on myboot-d78fb6d58-smb7h
Aloha from Spring Boot! 63 on myboot-d78fb6d58-smb7h
Supersonic Subatomic Java with Quarkus myboot-5cf696848b-tlt6l:1
Supersonic Subatomic Java with Quarkus myboot-5cf696848b-tlt6l:2
----

다시 Spring Boot 이미지로 전환하기 위해서는 아래 명령어를 실행하세요.

[.console-input]
[source, bash]
----
oc set image deployment/myboot myboot=quay.io/rhdevelopers/myboot:v2
----
