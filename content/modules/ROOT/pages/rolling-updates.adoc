== 배경지식: 롤링 업데이트

앞서 xref:kubectl.adoc#set-image-myboot-v1[oc] 장에서 이미지를 바꿔서 잠깐 롤링 업데이트를 맛봤습니다. 이번 장에서는 그 과정을 한 단계씩 멈춰서 자세히 들여다봅니다.

Deployment의 이미지가 바뀌면 새 버전(revision)의 ReplicaSet이 만들어지고, 기존 ReplicaSet의 복제본 수를 서서히 줄이는 동시에 새 ReplicaSet의 복제본 수를 서서히 늘리면서 전환이 이루어집니다. 
이 전략 덕분에 애플리케이션을 완전히 내렸다가 올리지 않고도(즉, 무중단으로) 새 버전으로 넘어갈 수 있습니다.

=== 'Resource Requests & Limits' 파트에서 사용한 deployment를 삭제한 경우

[TIP,subs="attributes+,+macros"]
====
방금 xref::resources.adoc[Resource Requests & Limits 실습, window=_blank]에서 넘어왔다면 필요한 pod와 deployment가 이미 실행 중일 것입니다. 

그렇다면 바로 '실습 시작' 섹션으로 넘어가세요. 

그렇지 않다면 {user}-{set-namespace}에 필요한 요소들을 배포하기 위해 다음 명령을 실행해야 합니다.
====

다음 명령어를 통해 Spring Boot 앱을 배포합니다:

[#deploy-myboot-rolling]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
###################################################
### 이전 실습에서 사용한 deployment를 삭제한 경우에만 실행
###################################################
cat <<EOF | oc create -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myboot
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        ports:
          - containerPort: 8080
        resources:
          requests: 
            memory: "400Mi" 
            cpu: "250m" # 1/4 core
          # NOTE: These are the same limits we tested our Docker Container with earlier
          # -m matches limits.memory and --cpus matches limits.cpu
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
EOF
----

[#deploy-myboot-rolling]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
###################################################
### 이전 실습에서 사용한 service를 삭제한 경우에만 실행
###################################################
cat <<EOF | oc create -f -
apiVersion: v1
kind: Service
metadata:
  name: myboot
  labels:
    app: myboot    
spec:
  ports:
  - name: http
    port: 8080
  selector:
    app: myboot
EOF
----

`StrategyType` 옵션에는 ``RollingUpdate``와 ``Recreate``가 있고, 현재는 ``RollingUpdate``로 설정되어 있습니다.

이제 앞으로 있을 롤링 업데이트에서 여러 Pod가 새로운 버전으로 전환되는 과정을 관찰할 수 있도록 복제본 수를 2개로 늘려 봅시다.

Deployment의 복제본 수를 변경할 때는 ``oc scale`` 명령을 사용할 수 있습니다.

[#edit-deployment-replicas-rolling]
[.console-input]
[source,bash]
----
oc scale deployment/myboot --replicas=2
----

다음과 비슷한 결과가 표시됩니다.

[.console-output]
[source,text]
----
deployment.apps/myboot scaled
----

``--replicas=2``는 Deployment가 유지해야 할 Pod의 수를 2개로 설정한다는 의미입니다.

잠시 후 새로운 Pod가 추가로 생성되는 것을 확인합니다:

[#edit-deployment-replicas-get-pod-rolling]
[.console-input]
[source,bash]
----
oc get pods
----

[.console-output]
[source,bash]
----
NAME                     READY   STATUS    RESTARTS   AGE
myboot-d78fb6d58-2fqml   1/1     Running   0          25s
myboot-d78fb6d58-ljkjp   1/1     Running   0          3m
----

이제 실제로 롤링 업데이트를 일으켜 봅시다.

Deployment가 사용하는 컨테이너 이미지를 변경하면 Pod Template이 변경되면서 새로운 ReplicaSet이 생성되고 롤링 업데이트가 시작됩니다.

이미지를 변경할 때는 ``oc set image`` 명령을 사용할 수 있습니다. 

현재 myboot 앱은 v1 이미지를 사용하고 있으므로, v2 이미지로 변경해보겠습니다.

[#edit-deployment-v2-rolling]
[.console-input]
[source,bash]
----
oc set image deployment/myboot myboot=quay.io/rhdevelopers/myboot:v2
----

명령의 각 부분은 다음을 의미합니다.

[source,text]
----
oc set image deployment/myboot myboot=quay.io/rhdevelopers/myboot:v2
             └──────┬──────┘   └─┬─┘ └───────────────┬──────────────┘
                 Deployment    컨테이너             새 이미지
----

여기에서 ``myboot=`` 왼쪽의 ``myboot``는 Deployment 안에 정의된 **컨테이너 이름**입니다.

다음과 비슷한 결과가 표시됩니다.

[.console-output]
[source,text]
----
deployment.apps/myboot image updated
----

이미지가 변경되면 새로운 ReplicaSet과 Pod가 생성되면서 롤링 업데이트가 시작됩니다.

새 리비전의 Pod가 생성되는 동안 기존 리비전의 Pod가 아직 남아 있는 __과도기 상태__를 볼 수 있을 것입니다:

[#edit-deployment-v2-get-pod-rolling]
[.console-input]
[source,bash]
----
oc get pods
----

[.console-output]
[source,bash]
----
NAME                      READY   STATUS              RESTARTS   AGE
myboot-7fbc4b97df-4ntmk   1/1     Running             0          9s
myboot-7fbc4b97df-qtkzj   0/1     ContainerCreating   0          0s
myboot-d78fb6d58-2fqml    1/1     Running             0          3m29s
myboot-d78fb6d58-ljkjp    1/1     Terminating         0          8m
----

[IMPORTANT]
====
현재 이 Deployment에는 아직 Liveness/Readiness Probe가 정의되어 있지 않으므로, 롤오버가 진행되는 동안 loop 창에서 다음과 같은 연결 오류가 몇 차례 발생할 수 있습니다:

[.console-output]
[source,bash]
----
Aloha from Spring Boot! 119 on myboot-d78fb6d58-2zp4h
curl: (7) Failed to connect to 192.168.99.100 port 31528: Connection refused
----

Readiness Probe가 없으면 쿠버네티스는 컨테이너가 `Running` 상태가 되는 즉시 그 Pod를 Service의 Endpoints에 추가합니다. 하지만 Spring Boot 애플리케이션이 실제로 요청을 받을 준비가 되기까지는 그보다 조금 더 시간이 걸리기 때문에, 그 짧은 틈에 들어온 요청은 실패합니다(이 문제는 xref:live-ready.adoc[Liveness와 Readiness] 장에서 Probe를 추가해 직접 해결해 봅니다).

연결 오류 없이 롤링 업데이트가 되는 것을 확인하시려면 Spring Boot 이미지 대신 Quarkus 이미지를 사용해 보세요.

[#describe-rollback-quarkus-rolling]
[.console-input]
[source, bash]
----
oc set image deployment/myboot myboot=quay.io/rhdevelopers/quarkus-demo:v1
----

그러면 오류가 발생하지 않아야 합니다. Quarkus는 그야말로 놀라울 정도로 빠르게 부팅됩니다.

[.console-output]
[source,bash]
----
Aloha from Spring Boot! 62 on myboot-d78fb6d58-smb7h
Aloha from Spring Boot! 63 on myboot-d78fb6d58-smb7h
Supersonic Subatomic Java with Quarkus myboot-5cf696848b-tlt6l:1
Supersonic Subatomic Java with Quarkus myboot-5cf696848b-tlt6l:2
----

다시 Spring Boot 이미지로 전환하기 위해서는 아래 명령어를 실행하세요.

[.console-input]
[source, bash]
----
oc set image deployment/myboot myboot=quay.io/rhdevelopers/myboot:v2
----
