= Liveness와 Readiness
include::vars.adoc[]

쿠버네티스는 컨테이너가 정상인지를 스스로 판단하지 못합니다. 프로세스가 살아 있어도 내부적으로 멈춰 있거나(데드락 등), 아직 요청을 받을 준비가 안 되어 있을 수 있기 때문입니다. 이를 알려주기 위한 것이 __probe__입니다:

* __Liveness Probe__는 "이 컨테이너가 여전히 정상적으로 동작하고 있는가?"를 주기적으로 확인합니다. 실패하면 쿠버네티스는 그 컨테이너를 __재시작__합니다.
* __Readiness Probe__는 "이 컨테이너가 지금 트래픽을 받을 준비가 되었는가?"를 확인합니다. 실패해도 컨테이너를 재시작하지는 않지만, 그 Pod를 Service의 Endpoints 목록에서 __일시적으로 제외__시켜서 트래픽이 오지 않게 합니다.

이번 장에서는 이 두 Probe를 실제로 실패시켜 보면서 각각 어떤 다른 반응이 일어나는지 직접 확인해 봅니다.

이제 Liveness와 Readiness probe가 설정된 애플리케이션을 배포해 보겠습니다. 

[#create-app-live-ready]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
        env: dev
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        imagePullPolicy: Always
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "400Mi"
            cpu: "250m" # 1/4 core
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
        livenessProbe:
          httpGet:
              port: 8080
              path: /alive
          initialDelaySeconds: 10
          periodSeconds: 5
          timeoutSeconds: 2
        readinessProbe:
          httpGet:  
            path: /health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 3
EOF
----

:section-k8s: live-ready

`delay`(시작 후 첫 검사까지 대기 시간), `period`(검사 주기), `timeout`(응답 대기 시간), `failure`(연속 실패 허용 횟수) 값을 보면, 이 Probe가 얼마나 자주, 얼마나 관대하게 검사하는지 알 수 있습니다. Liveness는 `/alive` 경로를, Readiness는 ``/health``라는 별도의 경로를 사용하고 있는 것도 눈여겨보세요 — 두 Probe가 서로 다른 기준으로 애플리케이션을 검사할 수 있다는 뜻입니다.

== Readiness Probe

이 실습용 애플리케이션에는 스스로를 일부러 비정상 상태로 만드는 ``/misbehave``라는 디버그용 엔드포인트가 있습니다. Pod 하나에 exec로 접속해서 이 엔드포인트를 호출해, readiness 플래그를 실패 상태로 바꿔 봅시다:

[#misbehave-app-live-ready]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc exec -it deployment/myboot -- /bin/bash
----

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl localhost:8080/misbehave
exit
----

이제 pod가 더 이상 Ready 상태가 아닌 것을 확인합니다:

----

== Liveness Probe

이번에는 Readiness가 아니라 Liveness Probe를 실패시켜서, 앞서와 다르게 __Pod 자체가 재시작__된다는 것을 확인해 봅시다. 먼저 v3 이미지로 업데이트합니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc set image deployment/myboot myboot=quay.io/rhdevelopers/myboot:v3
----

롤아웃이 복제본 3개 모두에 걸쳐 완료될 때까지 기다립니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get pods -w
----

[.console-output]
[source.bash]
----
NAME                      READY   STATUS    RESTARTS   AGE
myboot-56659c9d69-6sglj   1/1     Running   0          2m2s
myboot-56659c9d69-mdllq   1/1     Running   0          97s
myboot-56659c9d69-zjt6q   1/1     Running   0          72s
----

curl loop/poller에서 이미지 변경에 따른 변화를 볼 수 있습니다.

[.console-output]
[source.bash]
----
Bonjour from Spring Boot! 490 on myboot-5bb9487586-s9qff
Jambo from Spring Boot! 40 on myboot-56659c9d69-mdllq
Jambo from Spring Boot! 26 on myboot-56659c9d69-zjt6q
Jambo from Spring Boot! 71 on myboot-56659c9d69-6sglj
----

v3 이미지에는 ``/shot``이라는 디버그용 엔드포인트가 있어서, 호출하면 애플리케이션이 (마치 데드락에 걸린 것처럼) 더 이상 응답하지 않는 상태를 흉내 냅니다. 이제 pod 중 하나를 골라 ``exec``로 접속해서 총을 쏴 봅니다:

[#shot-v3-live-ready]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc exec -it deployment/myboot -- /bin/bash
----

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl localhost:8080/shot
----

[.console-output]
[source.bash]
----
I have been shot in the head1000610000@myboot-558b4f8678-qbrgc:/app$ command terminated with exit code 137
----


Liveness Probe가 몇 차례 연속으로 실패하면, 쿠버네티스는 이 컨테이너가 되돌릴 수 없는 상태에 빠졌다고 판단하고 강제로 재시작합니다. 
잠시 기다린 후 다른 터미널에서 RESTARTS 열의 숫자가 올라간 것을 확인해 보세요(몇 분 간 기다려야할 수 있습니다):

[.console-output]
[source.bash]
----
NAME                      READY   STATUS    RESTARTS   AGE
myboot-558b4f8678-nw762   1/1     Running   0          4m7s
myboot-558b4f8678-qbrgc   1/1     Running   1          4m29s
myboot-558b4f8678-z7f9n   1/1     Running   0          3m44s
----

컨테이너 자체가 통째로 재시작되므로, 그 컨테이너 안에 붙어 있던 exec 세션도 함께 강제 종료됩니다(종료 코드 ``137``은 ``SIGKILL``로 강제 종료되었다는 의미입니다):

[.console-output]
[source.bash]
----
I have been shot in the head1000610000@myboot-558b4f8678-qbrgc:/app$ command terminated with exit code 137
----

== Startup Probe

일부 응용 프로그램은 처음 초기화할 때 추가 시작 시간이 필요합니다.

실행 시간 동안 이상을 감지하고 긴 시작 시간을 처리하기 위해 정상적인 동작을 구성해야 하기 때문에 이 시나리오를 활성/준비 프로브에 적용하는 것은 까다로울 수 있습니다.

예를 들어, 교착 상태에 빠질 수 있는 애플리케이션이 있고 이러한 문제를 즉시 파악하고 싶다면 다음과 같이 짧은 응답시간의 활성 및 준비 상태 프로브를 설정할 수 있습니다.

아래 Deployment를 배포합니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
        env: dev
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        imagePullPolicy: Always
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "400Mi"
            cpu: "250m" # 1/4 core
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
        livenessProbe:
          httpGet:
              port: 8080
              path: /alive
          periodSeconds: 2
          timeoutSeconds: 2
          failureThreshold: 2
        readinessProbe:
          httpGet:
            path: /health
            port: 8080
          periodSeconds: 3
EOF
----
NOTE: 해당 probe 설정은 timeout 시간이 매우 짧은 것을 볼 수 있습니다.

pod를 계속 감시해보면 계속해서 다시 시작되는 것을 볼 수 있으며, 때로는 성공적으로 부팅된 이후에도(kubelet이 재시작을 예약하기 때문에) pod가 계속 재시작되는데, 이는 SpringBoot가 시작되는 데에 오래 걸려서 Probe에 결국 실패하기 때문입니다.


[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc describe pods
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
Events:
  Type     Reason     Age                 From               Message
  ----     ------     ----                ----               -------
  Normal   Scheduled  96s                 default-scheduler  Successfully assigned myspace/myboot-849ccd6948-8vrfq to devnation
  Normal   Pulled     92s                 kubelet            Successfully pulled image "quay.io/rhdevelopers/myboot:v1" in 3.295180194s
  Normal   Created    55s (x2 over 92s)   kubelet            Created container myboot
  Normal   Started    55s (x2 over 92s)   kubelet            Started container myboot
  Normal   Pulled     55s                 kubelet            Successfully pulled image "quay.io/rhdevelopers/myboot:v1" in 3.289395484s
  Warning  Unhealthy  52s (x4 over 90s)   kubelet            Liveness probe failed: Get "http://172.17.0.4:8080/alive": dial tcp 172.17.0.4:8080: connect: connection refused
  Normal   Killing    52s (x2 over 88s)   kubelet            Container myboot failed liveness probe, will be restarted
  Normal   Pulling    22s (x3 over 95s)   kubelet            Pulling image "quay.io/rhdevelopers/myboot:v1"
  Warning  Unhealthy  19s (x10 over 88s)  kubelet            Readiness probe failed: Get "http://172.17.0.4:8080/health": dial tcp 172.17.0.4:8080: connect: connection refused
----

**Startup probe**는 이 문제를 해결해 줍니다. startup probe를 통과하기 전까지는 liveness나 readiness probe를 진행하지 않으며, startup probe가 한 번 성공하고 나면 나머지 probe들이 상태 검사를 시작하게 됩니다.

초기 기동 시간이 오래 걸리는 애플리케이션 등에 유용하게 활용할 수 있습니다.
