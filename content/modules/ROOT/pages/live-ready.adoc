== 배경지식: Readiness와 Liveness

쿠버네티스는 컨테이너가 정상인지를 스스로 판단하지 못합니다. 프로세스가 살아 있어도 내부적으로 멈춰 있거나(데드락 등), 아직 요청을 받을 준비가 안 되어 있을 수 있기 때문입니다. 이를 알려주기 위한 것이 __probe__입니다.

* __Readiness Probe__는 "이 컨테이너가 지금 트래픽을 받을 준비가 되었는가?"를 확인합니다. 실패해도 컨테이너를 재시작하지는 않지만, 그 Pod를 Service의 Endpoints 목록에서 __일시적으로 제외__시켜서 트래픽이 오지 않게 합니다.
* __Liveness Probe__는 "이 컨테이너가 여전히 정상적으로 동작하고 있는가?"를 주기적으로 확인합니다. 실패하면 쿠버네티스는 그 컨테이너를 __재시작__합니다.

이번 장에서는 이 두 Probe를 실제로 실패시켜 보면서 각각 어떤 다른 반응이 일어나는지 직접 확인해 봅니다.



== 배경지식: Readiness와 Liveness

쿠버네티스는 컨테이너의 프로세스가 실행 중인지 확인할 수 있지만, 그 안에서 실행되는 **애플리케이션이 실제로 정상적으로 동작하고 있는지까지 자동으로 판단할 수는 없습니다**.

예를 들어 컨테이너의 프로세스 자체는 실행 중이더라도 다음과 같은 상황이 발생할 수 있습니다.

* 애플리케이션이 아직 시작 중이어서 요청을 처리할 준비가 되지 않은 경우
* 데이터나 설정 파일을 불러오는 중인 경우
* 외부 시스템과의 연결 문제로 일시적으로 요청을 처리할 수 없는 경우
* 애플리케이션이 교착 상태(deadlock) 등에 빠져 더 이상 정상적으로 동작하지 않는 경우

쿠버네티스에서는 이러한 애플리케이션의 상태를 확인하기 위해 ``Probe``를 사용할 수 있습니다.

이번 실습에서는 먼저 **Readiness Probe**와 **Liveness Probe**의 차이를 살펴봅니다.

* **Readiness Probe**는 "이 컨테이너가 지금 요청을 처리할 준비가 되었는가?"를 확인합니다.
** Probe가 성공하면 Pod가 ``Ready`` 상태가 되고 Service를 통해 트래픽을 받을 수 있습니다.
** Probe가 실패하면 Pod가 ``NotReady`` 상태가 되고 Service가 트래픽을 전달하는 대상에서 제외됩니다.
** Readiness Probe가 실패하더라도 컨테이너를 재시작하지는 않습니다.

* **Liveness Probe**는 "이 컨테이너의 애플리케이션이 계속 정상적으로 동작하고 있는가?"를 확인합니다.
** 애플리케이션이 교착 상태처럼 스스로 복구하기 어려운 상태에 빠졌는지 확인할 때 사용할 수 있습니다.
** Liveness Probe가 설정된 횟수만큼 연속으로 실패하면 kubelet은 해당 **컨테이너를 재시작**합니다.
** Pod 자체를 새로 만드는 것이 아니라 같은 Pod 안에서 컨테이너가 다시 시작되므로 ``RESTARTS`` 값이 증가합니다.

Readiness와 Liveness는 서로 다른 목적을 가지고 있으며 독립적으로 동작합니다.

즉, Readiness Probe에 실패했다고 해서 컨테이너가 재시작되는 것은 아니며, 반대로 Liveness Probe는 해당 컨테이너가 Service의 트래픽을 받고 있는지와 관계없이 애플리케이션의 정상 동작 여부를 검사합니다.

Probe는 HTTP 요청, TCP 연결, 컨테이너 내부 명령 실행 등 여러 방법으로 구성할 수 있습니다. 이번 실습에서는 HTTP 요청을 사용하는 ``httpGet`` 방식을 사용합니다.

Probe의 동작은 다음과 같은 설정으로 조절할 수 있습니다.

* ``initialDelaySeconds``: 컨테이너가 시작된 후 첫 번째 Probe를 수행하기까지 기다리는 시간
* ``periodSeconds``: Probe를 반복해서 수행하는 주기
* ``timeoutSeconds``: 한 번의 Probe 응답을 기다리는 최대 시간
* ``failureThreshold``: 실패로 판단하기 전에 허용하는 연속 실패 횟수

이번 실습에서는 Readiness Probe와 Liveness Probe를 각각 의도적으로 실패시켜 보면서,

* Readiness 실패 시 Service 트래픽에서 제외되는 과정
* Liveness 실패 시 컨테이너가 재시작되는 과정

을 직접 확인해 봅니다.

=== Probe가 설정된 앱 배포

:quick-open-file: myboot-deployment-live-ready.yml

이제 Liveness와 Readiness probe가 설정된 애플리케이션을 배포해 보겠습니다. 

[#create-app-live-ready]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
        env: dev
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        imagePullPolicy: Always
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "400Mi"
            cpu: "250m" # 1/4 core
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
        livenessProbe:
          httpGet:
              port: 8080
              path: /alive
          initialDelaySeconds: 10
          periodSeconds: 5
          timeoutSeconds: 2
        readinessProbe:
          httpGet:  
            path: /health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 3
EOF
----

deployment를 describe합니다:

:describe-deployment-name: myboot
:section-k8s: live-ready

include::partial$describe-deployment.adoc[]

[.console-output]

`delay`(시작 후 첫 검사까지 대기 시간), `timeout`(응답 대기 시간), `period`(검사 주기), `failure`(연속 실패 허용 횟수) 값을 보면, 이 Probe가 얼마나 자주, 얼마나 관대하게 검사하는지 알 수 있습니다. Liveness는 `/alive` 경로를, Readiness는 ``/health``라는 별도의 경로를 사용하고 있는 것도 눈여겨보세요 — 두 Probe가 서로 다른 기준으로 애플리케이션을 검사할 수 있다는 뜻입니다.

== 배경지식: Startup Probe

Readiness와 Liveness Probe를 사용할 때 한 가지 주의해야 할 점이 있습니다.

일부 애플리케이션은 컨테이너가 시작된 뒤 실제 서비스를 제공할 수 있는 상태가 되기까지 비교적 긴 시간이 필요합니다. 예를 들어 대용량 데이터를 읽거나, 캐시를 초기화하거나, 여러 구성 요소를 초기화해야 하는 애플리케이션이 이에 해당합니다.

이런 애플리케이션에 Liveness Probe를 너무 일찍 실행하면 아직 정상적으로 시작 중인 애플리케이션을 장애 상태로 잘못 판단할 수 있습니다.

예를 들어 애플리케이션을 시작하는 데 20초가 필요한데 Liveness Probe가 컨테이너 시작 직후부터 실행된다면 다음과 같은 상황이 반복될 수 있습니다.

----
컨테이너 시작
      ↓
애플리케이션 초기화 중
      ↓
Liveness Probe 실패
      ↓
컨테이너 재시작
      ↓
다시 애플리케이션 초기화
      ↓
Liveness Probe 실패
      ↓
...
----

결국 애플리케이션이 정상적으로 시작될 기회를 얻지 못하고 계속 재시작될 수 있습니다.

이러한 문제를 해결하기 위해 사용할 수 있는 것이 **Startup Probe**입니다.

Startup Probe는 "애플리케이션의 시작이 완료되었는가?"를 확인합니다.

Startup Probe가 설정되어 있으면 컨테이너가 시작된 직후에는 Startup Probe만 실행되고, Startup Probe가 성공할 때까지 Liveness Probe와 Readiness Probe는 실행되지 않습니다.

----
컨테이너 시작
      ↓
Startup Probe
      ↓
Startup Probe 성공
      ↓
Readiness Probe + Liveness Probe 시작
----

Startup Probe가 한 번 성공하면 애플리케이션이 정상적으로 시작되었다고 판단하고, 이후에는 Readiness와 Liveness Probe가 각각의 역할에 따라 상태를 검사합니다.

따라서 Startup Probe를 사용하면 **시작 시간이 오래 걸리는 애플리케이션에는 충분한 초기화 시간을 제공하면서도**, 애플리케이션이 시작된 이후에는 Liveness Probe를 이용하여 장애 상태를 빠르게 감지하도록 구성할 수 있습니다.

== 실습: Startup Probe
=== Startup Probe

터미널 1에서 아래 Deployment를 배포합니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myboot
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myboot
  template:
    metadata:
      labels:
        app: myboot
        env: dev
    spec:
      containers:
      - name: myboot
        image: quay.io/rhdevelopers/myboot:v1
        imagePullPolicy: Always
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "400Mi"
            cpu: "250m" # 1/4 core
          limits:
            memory: "600Mi"
            cpu: "1000m" # 1 core
        livenessProbe:
          httpGet:
              port: 8080
              path: /alive
          periodSeconds: 2
          timeoutSeconds: 2
          failureThreshold: 2
        readinessProbe:
          httpGet:
            path: /health
            port: 8080
          periodSeconds: 3
EOF
----
NOTE: 이 Deployment의 probe 설정은 이전 Deployment와 달리, 초기에 상태 검사를 잠시 지연시키는 initialDelaySeconds가 설정되어 있지 않습니다.

**Startup probe**는 애플리케이션 초기화 시간 때문에 생기는 이러한 문제를 해결해 줍니다. startup probe를 통과하기 전까지는 liveness나 readiness probe를 진행하지 않으며, startup probe가 한 번 성공하고 나서야 나머지 probe들이 상태 검사를 시작하게 됩니다.
따라서 초기 기동 시간이 오래 걸리는 애플리케이션 등에 유용하게 활용할 수 있습니다.
