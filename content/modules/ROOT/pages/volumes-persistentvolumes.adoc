= Volume과 Persistent Volume
include::_attributes.adoc[]
:watch-terminal: 터미널 2
:file-watch-terminal: 터미널 3

컨테이너는 정의상 일시적입니다. 즉, 실행 중에 저장된 내용은 컨테이너가 멈추면 사라집니다.
이는 데이터베이스 컨테이너처럼 데이터를 영구적으로 보존해야 하는 컨테이너에 문제가 될 수 있습니다.

쿠버네티스 volume은 Pod 안의 Container들이 접근할 수 있는 디렉터리일 뿐입니다.
이 개념은 Docker volume과 비슷하지만, Docker에서는 컨테이너를 컴퓨터 호스트에 매핑하는 반면, 쿠버네티스 volume의 경우에는 그 volume을 뒷받침하는 매체와 내용이 사용된 특정 volume 유형에 따라 결정됩니다.

몇 가지 volume 유형은 다음과 같습니다:

* awsElasticBlockStore
* azureDisk
* cephfs
* nfs
* local
* empty dir
* host path

== Volume

``Volume``의 예시 두 가지로 시작해 봅시다.

=== EmptyDir

`emptyDir` volume은 Pod가 노드에 할당될 때 처음 생성되며, 그 Pod가 해당 노드에서 실행되는 동안 존재합니다.
이름 그대로, 처음에는 비어 있습니다.
같은 Pod 안의 모든 Container는 동일한 `emptyDir` volume을 읽고 쓸 수 있습니다.
Pod가 재시작되거나 제거되면 ``emptyDir``의 데이터는 영구적으로 사라집니다.

이제 Pod 안의 ``/tmp/demo``에 저장된 콘텐츠가 host 경로 ``/mnt/data``에 저장되므로, Pod가 죽더라도 콘텐츠는 사라지지 않는다는 점에 주목하세요.

하지만 Pod가 다운되어 다른 노드에 다시 스케줄되는 경우에는, 그 다른 노드에 데이터가 없을 것이기 때문에 이것이 모든 문제를 해결해주지는 않을 수 있습니다.

다른 예시로, 이번에는 Amazon EBS Volume을 살펴봅시다:

[source, yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: test-ebs
spec:
...  
  volumes:
    - name: test-volume
      awsElasticBlockStore:
        volumeID: <volume-id>
        fsType: ext4
----

앞의 스니펫에서 주목해야 할 점은, 애플리케이션에 속한 것들(즉 컨테이너, probe, 포트 등)로 더 __dev__ 쪽에 가까운 것과, 클라우드와 더 관련된 것들(즉 물리적 스토리지)로 더 __ops__ 쪽에 가까운 것이 뒤섞여 있다는 것입니다.

이런 개념의 뒤섞임을 피하기 위해, 쿠버네티스는 어느 정도 추상화 계층을 제공해서, 개발자는 그저 데이터를 저장할 공간을 요청하고(__persistent volume claim__), 운영팀이 물리적인 스토리지 설정을 제공하게 합니다.

== Persistent Volume과 Persistent Volume Claim

`PersistentVolume`(__PV__)은 관리자가 만들거나, ``Storage Classes``를 사용해 Pod와 독립적으로 동적으로 생성되는 쿠버네티스 리소스입니다.
이는 스토리지 구현의 세부 사항을 담고 있으며, NFS, Ceph, iSCSI, 또는 클라우드 제공업체 전용 스토리지 시스템일 수 있습니다.

`PersistentVolumeClaim`(__PVC__)은 사용자의 스토리지 요청입니다.
특정 volume 크기나, 예를 들어 접근 모드를 요청할 수 있습니다.

=== hostPath를 사용한 persistent volume/claim

:quick-open-file: demo-persistent-volume-hostpath.yaml

`hostPath` 전략을 사용하되, volume으로 직접 설정하지 않고 persistent volume과 persistent volume claim을 사용해 봅시다. ``{quick-open-file}``을 확인해 보세요:

include::partial$tip_vscode_quick_open.adoc[]

[source, yaml]
.{quick-open-file}
----
kind: PersistentVolume
apiVersion: v1
metadata:
  name: my-persistent-volume
  labels:
    type: local
spec:
  storageClassName: pv-demo 
  capacity:
    storage: 100Mi
  accessModes:
    - ReadWriteOnce
  hostPath:
    path: "/mnt/persistent-volume"
----

이제 `volume` 정보는 더 이상 pod에 있지 않고 __persistent volume__ 객체에 있습니다.

[.console-input]
[source,bash]
----
oc apply -f apps/kubefiles/demo-persistent-volume-hostpath.yaml 

oc get pv -w
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM                                           STORAGECLASS   REASON   AGE
my-persistent-volume                       100Mi      RWO            Retain           Available                                                   pv-demo                 5s
----

:mount-dir: /mnt/persistent-volume

volume이 만들어졌으면, 파일 watch 터미널이 volume의 새 위치인 ``{mount-dir}``을 보도록 업데이트해 봅시다.

큰 차이점은, 이제 pod의 `volumes` 섹션에는 volume 설정을 직접 정의하는 것이 아니라, 사용할 __persistent volume claim__만 정의한다는 것입니다. ``{quick-open-file}``을 확인하세요:

include::partial$tip_vscode_quick_open.adoc[]

[source, yaml]
.{quick-open-file}
----
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4

== 정적 vs 동적 프로비저닝

Persistent Volume은 동적으로 또는 정적으로 프로비저닝될 수 있습니다.

정적 프로비저닝은 클러스터 관리자가 **기존** 스토리지 장치를 클러스터에서 사용할 수 있게 해줍니다.
이 방식에서는 PV와 PVC를 수동으로 제공해야 합니다.

지금까지 마지막 예시에서 본 것이 바로 정적 프로비저닝입니다.

동적 프로비저닝은 클러스터 관리자가 미리 스토리지를 프로비저닝해야 할 필요성을 없애줍니다.
대신, 사용자가 요청하면 스토리지를 자동으로 프로비저닝합니다.
이를 동작시키려면 Storage Class 객체와 그것을 참조하는 PVC를 제공해야 합니다.
PVC가 생성되고 나면, 스토리지 장치와 PV가 자동으로 만들어집니다.
동적 프로비저닝의 주된 목적은 클라우드 제공업체 솔루션과 함께 동작하는 것입니다.

일반적으로 쿠버네티스 구현체는 기본 Storage Class를 제공해서 누구나 동적 프로비저닝을 빠르게 시작할 수 있게 해줍니다.
다음 명령으로 기본 Storage Class의 정보를 확인할 수 있습니다:

[.console-input]
[source,bash]
----
oc get sc
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME            PROVISIONER             AGE
gp2 (default)   kubernetes.io/aws-ebs   31h
----

OpenShift가 클라우드 제공업체에 설치되면 기본적으로 그 클라우드의 기반 영구 스토리지 기술을 사용하는 Storage Class를 자동으로 생성합니다.
예를 들어 AWS의 경우, AWS EBS를 가리키는 기본 Storage Class가 제공됩니다. (실제 표시되는 `PROVISIONER` 값은 이 클러스터가 어떤 클라우드에 설치되었는지에 따라 다를 수 있습니다.)

그런 다음 Persistent Volume Claim을 생성하면 Persistent Volume이 자동으로 생성됩니다. kbd:[CTRL+p]를 사용해서 ``demo-dynamic-persistent.yaml``을 빠르게 열어보세요:

[source, yaml]
----
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: myboot-volumeclaim
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Mi
----

__storage class__를 따로 지정하지 않았지만 기본값으로 정의된 것이 있으므로, __PVC__는 암묵적으로 그것을 참조합니다. (이 pod 정의를 ``myboot-persistent-volume-claim.yaml``과 비교해 보는 것도 좋습니다.)

.정적 PVC와 동적 PVC(정적 PV)의 차이
image::pv-static-vs-dynamic.png[]

[.console-input]
[source,bash]
----
oc apply -f apps/kubefiles/demo-dynamic-persistent.yaml

oc get pvc
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                 STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
myboot-volumeclaim   Pending                                      gp2            46s
----

__PVC__가 __Pending__ STATUS인 것에 주목하세요. 우리가 만들고 있는 것이 동적 스토리지라는 것을 기억해 보면, 이는 __pod__가 volume을 요청하기 전까지는 __PVC__가 pending 상태로 남아 있고 __PV__도 생성되지 않는다는 의미입니다.

[.console-input]
[source,bash]
----

----


이제 volume claim이 volume에 __Bound__ 된 것에 주목하세요.

마지막으로, __PV__가 자동으로 생성되었는지 확인할 수 있습니다:

== 분산 파일 시스템

클라우드 제공업체는 데이터가 모든 노드에서 항상 사용 가능하도록 분산 스토리지를 제공한다는 점을 알아두는 것이 중요합니다.
마지막 예시에서 봤듯이, 이 storage class는 모든 노드가 동일한 디스크 콘텐츠를 보도록 보장합니다.

예를 들어, 온프레미스에서 쿠버네티스/OpenShift를 사용하고 있거나 특정 벤더 솔루션에 의존하고 싶지 않다면, 쿠버네티스에서도 분산 파일 시스템을 지원합니다.
그런 경우라면 NFS, https://www.gluster.org/[GlusterFS] 또는 https://ceph.io/[Ceph]를 사용하는 것을 권장합니다.
