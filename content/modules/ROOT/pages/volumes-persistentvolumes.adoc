= Volume과 Persistent Volume
include::vars.adoc[]
include::_attributes.adoc[]
:watch-terminal: 터미널 2
:file-watch-terminal: 터미널 3

컨테이너는 기본적으로 **일시적인(ephemeral) 실행 환경**입니다.

컨테이너가 실행되는 동안 파일을 생성하거나 데이터를 저장할 수 있지만, 이러한 데이터가 컨테이너 자체의 파일 시스템에만 저장되어 있다면 컨테이너가 삭제되거나 새로 생성될 때 그대로 유지된다는 보장이 없습니다.

예를 들어 데이터베이스를 컨테이너로 실행하면서 데이터 파일까지 컨테이너 내부에만 저장한다면, 컨테이너가 재생성되었을 때 중요한 데이터가 사라질 수 있습니다.

Kubernetes에서는 이러한 문제를 해결하기 위해 **Volume**을 사용할 수 있습니다.

Volume은 Pod에 정의되고, Pod 안의 하나 이상의 컨테이너에 특정 디렉터리로 마운트하여 사용할 수 있는 저장 공간입니다.

[source,text]
-------------------
Pod
│
├─ Container A
│     └─ /data ───┐
│                 │
├─ Container B    │
│     └─ /shared ─┤
│                 │
└─ Volume ────────┘
-------------------

즉, 컨테이너는 Volume을 자신의 파일 시스템 안에 있는 일반적인 디렉터리처럼 사용할 수 있습니다.

Volume의 실제 데이터가 어디에 저장되고 얼마나 오래 유지되는지는 **어떤 종류의 Volume을 사용하느냐**에 따라 달라집니다.

대표적으로 다음과 같은 방식이 있습니다.

* `emptyDir`
  ** Pod가 실행되는 동안 사용할 임시 저장 공간입니다.
  ** 컨테이너가 재시작되어도 같은 Pod가 유지되는 동안에는 데이터가 남아 있습니다.
  ** 하지만 Pod가 삭제되면 데이터도 함께 사라집니다.

* `hostPath`
  ** Worker Node의 특정 디렉터리를 Pod에 직접 마운트합니다.
  ** Pod가 다른 Node로 이동하면 같은 데이터를 사용할 수 없기 때문에 일반적인 애플리케이션의 영구 저장소로 사용하는 것은 적합하지 않습니다.

* **Persistent Volume**
  ** Pod의 수명과 관계없이 데이터를 유지해야 할 때 사용합니다.
  ** 애플리케이션은 일반적으로 `PersistentVolumeClaim(PVC)`을 통해 필요한 저장 공간을 요청합니다.
  ** 실제 저장소는 NFS, Ceph, 클라우드 Block Storage 등 다양한 시스템이 될 수 있으며, 현재 Kubernetes에서는 주로 **CSI(Container Storage Interface)** 드라이버를 통해 이러한 외부 스토리지를 연결합니다.

[source,text]
-------------------------
Pod
│
│ mount
▼
PVC (PersistentVolumeClaim)
│
▼
PV (PersistentVolume)
│
▼
실제 Storage
(NFS, Ceph, Cloud Disk 등)
-------------------------

따라서 중요한 것은 **Volume 자체가 항상 영구적인 저장 공간을 의미하는 것은 아니라는 점**입니다.

[source,text]
------------------------------------------
emptyDir      → Pod가 없어지면 데이터도 사라짐
PersistentVolume → Pod가 없어져도 데이터를 유지할 수 있음
------------------------------------------

이번 실습에서는 실제로 Volume을 생성하고 컨테이너에 마운트하여, 컨테이너에서 데이터를 어떻게 저장하고 사용할 수 있는지 확인해 보겠습니다.

== Volume

``Volume``의 예시 두 가지로 시작해 봅시다.

=== EmptyDir

`emptyDir` volume은 Pod가 노드에 할당될 때 처음 생성되며, 그 Pod가 해당 노드에서 실행되는 동안 존재합니다.
이름 그대로, 처음에는 비어 있습니다.
같은 Pod 안의 모든 Container는 동일한 `emptyDir` volume을 읽고 쓸 수 있습니다.
Pod가 재시작되거나 제거되면 ``emptyDir``의 데이터는 영구적으로 사라집니다.

<.> pod 안에 Volume을 마운트할 지점입니다. 
<.> 이 값은 우리가 정의할 volume의 이름과 일치해야 하며, 이 경우 파일 맨 아래에 정의되어 있습니다.

`volumes` 섹션에서는 volume을 정의하고, `volumeMounts` 섹션에서는 그 volume이 컨테이너 안에 어떻게 마운트되는지를 정의합니다.

  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    
    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  volumes:
  - name: demo-volume
    emptyDir: {}
EOF
----

==== Pod 안에서 EmptyDir 공유하기

``emptyDir``은 같은 Pod의 컨테이너 사이에 공유됩니다. 같은 pod 안에 같은 `emptyDir` volume을 마운트하는 두 개의 컨테이너를 만드는 deployment를 살펴봅시다.

:quick-open-file: myboot-pods-volume.yml

``{quick-open-file}``을 살펴봅시다:

[.console-output]
[source,yaml]
.{quick-open-file}
----
include::example$myboot-pods-volume.yml[]
----
<.> pod의 첫 번째 컨테이너는 myboot-demo-1이라는 이름을 가지며, ``/tmp/demo``에 ``demo-volume``을 마운트합니다.
<.> pod의 두 번째 컨테이너는 ``myboot-demo-2``라는 이름을 가지며, 같은 `/tmp/demo` 지점에 ``demo-volume``을 마운트합니다.
<.> 두 컨테이너는 완전히 동일한 이미지를 사용합니다.
<.> 컨테이너들이 pod의 포트를 공유하기 때문에 두 번째 컨테이너는 첫 번째와 다른 포트를 리슨해야 한다는 점에 주목하세요. 이 수준의 `env` 지시자는 `myboot-demo-2` 컨테이너에만 적용됩니다.
<.> volume은 한 번만 정의되지만 pod의 각 컨테이너에서 참조됩니다.

이제 `{set-namespace}` 네임스페이스에 이 deployment를 만들어 봅시다.

[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo-1 #<.>
    image: quay.io/rhdevelopers/myboot:v4
    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  - name: myboot-demo-2 #<.>
    image: quay.io/rhdevelopers/myboot:v4 #<.>

    env:
    - name: SERVER_PORT #<.>
      value: "8090"

    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  volumes:
  - name: demo-volume #<.>
    emptyDir: {}
EOF
----

----

`2/2` ready 상태에 주목하세요. 이는 pod 정의의 컨테이너 2개를 나타냅니다.
--

=== HostPath


IMPORTANT: **hostPath 볼륨 사용 제한** +
OpenShift는 클러스터 노드의 파일 시스템 경로를 컨테이너에 직접 마운트하는 hostPath 볼륨의 사용을 기본적으로 금지합니다. 이는 보안상 중요한 이유 때문입니다. +
*SCC(Secure Context Constraints)* +
OpenShift는 Pod가 특정 보안 컨텍스트 제약 조건(SCC)에 맞아야 실행을 허용합니다. +
기본적으로 사용자는 restricted SCC가 할당되어 있고, 이는 hostPath 볼륨 사용을 허용하지 않습니다. +
**이 실습의 user계정은 admin 권한이 없기 때문에, `HostPath` 부분은 읽어만 보세요.**

<.> ``/mnt/data``는 이 pod가 할당되는 쿠버네티스 ``node``의 한 위치입니다.

Pod의 정의 안에 애플리케이션 실행에 필요한 정보와 실제 인프라에 대한 정보가 함께 들어가게 됩니다.

[source,text]
--------------------------------------
Pod
│
├─ Container Image
├─ Port
├─ Probe
│
└─ AWS EBS Volume ID   ← 특정 인프라에 대한 정보
--------------------------------------

애플리케이션 개발자는 보통 다음과 같은 것을 알고 싶습니다.

[source,text]
--------------------------
"이 애플리케이션에 10Gi 크기의 영구 저장 공간이 필요합니다."
--------------------------

반면 실제로 그 저장 공간을 AWS EBS로 만들 것인지, Ceph로 만들 것인지, NFS로 제공할 것인지와 같은 내용은 클러스터의 스토리지 환경에 따라 달라질 수 있습니다.

Kubernetes는 이러한 **스토리지 사용 방법과 실제 스토리지 구현을 분리**하기 위해 `PersistentVolume`, `PersistentVolumeClaim`, ``StorageClass``라는 추상화 계층을 제공합니다.

[source,text]
------------------------
Application / Pod
│
│ 저장 공간이 필요함
▼
PVC (PersistentVolumeClaim)
│
│ 필요한 스토리지 요청
▼
PV (PersistentVolume)
│
│ 실제 Storage와 연결
▼
Physical / Cloud Storage
------------------------

이 구조를 통해 애플리케이션은 실제 스토리지가 어디에 있는지 자세히 알지 못해도 필요한 저장 공간을 사용할 수 있습니다.

현재 Kubernetes와 OpenShift에서는 다양한 스토리지 시스템을 연결하기 위해 주로 **CSI(Container Storage Interface)** 드라이버를 사용합니다.

== PersistentVolume과 PersistentVolumeClaim

`PersistentVolume`(**PV**)은 Kubernetes 클러스터에서 사용할 수 있는 **영구 저장 공간을 나타내는 리소스**입니다.

PV는 관리자가 미리 생성할 수도 있고, ``StorageClass``를 통해 필요할 때 동적으로 생성할 수도 있습니다.

PV는 특정 Pod의 수명과 독립적으로 존재하며, 실제로는 다음과 같은 스토리지와 연결될 수 있습니다.

* AWS EBS
* Ceph
* NFS
* 기타 CSI 기반 스토리지

`PersistentVolumeClaim`(**PVC**)은 사용자가 **필요한 저장 공간을 요청하는 리소스**입니다.

예를 들어 애플리케이션 개발자는 다음과 같이 요청할 수 있습니다.

[source,yaml]
-------------
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
name: my-data
spec:
accessModes:
- ReadWriteOnce
resources:
requests:
storage: 10Gi
-------------

이 PVC는 다음과 같은 의미입니다.

[source,text]
----------------------
"10Gi 크기의 영구 저장 공간이 필요합니다."

크기       : 10Gi
접근 방식  : ReadWriteOnce
----------------------

중요한 점은 이 YAML에는 다음과 같은 실제 스토리지 구현 정보가 없다는 것입니다.

[source,text]
---------
AWS EBS Volume ID
Ceph Pool
스토리지 서버 주소
물리 디스크 정보
---------

애플리케이션은 **어떤 저장 공간이 필요한지만 요청**하고, 실제 스토리지를 어떻게 제공할지는 Kubernetes와 클러스터의 스토리지 구성이 담당합니다.

=== 정적 프로비저닝

정적 프로비저닝(Static Provisioning)은 클러스터 관리자가 사용할 스토리지를 미리 준비하고 이에 대응하는 ``PersistentVolume``을 직접 생성하는 방식입니다.

[source,text]
--------------------------
관리자
│
├─ 실제 Storage 준비
│
└─ PersistentVolume 생성
│
▼
사용자가 PVC 생성
│
▼
조건이 일치하는 PV와 PVC가 연결(Bind)
--------------------------

예를 들어 관리자가 이미 준비되어 있는 NFS 디렉터리나 클라우드 디스크를 PV로 등록해 둘 수 있습니다.

사용자가 PVC를 생성하면 Kubernetes는 요청한 용량, 접근 모드, StorageClass 등의 조건을 확인하여 적절한 PV와 PVC를 연결합니다.

[source,text]
---------------
PVC
request: 10Gi
│
│ 조건이 일치
▼
PV
capacity: 20Gi
│
▼
기존에 준비된 Storage
---------------

정적 프로비저닝에서는 **사용자가 요청하기 전에 관리자가 스토리지를 준비해야 한다**는 특징이 있습니다.

=== 동적 프로비저닝

동적 프로비저닝(Dynamic Provisioning)은 사용자가 PVC를 생성했을 때 필요한 스토리지를 **자동으로 생성하는 방식**입니다.

이때 중요한 역할을 하는 리소스가 ``StorageClass``입니다.

[source,text]
----------

사용자
│
│ PVC 생성
▼
PersistentVolumeClaim
│
│ StorageClass 참조
▼
StorageClass
│
│ CSI Provisioner
▼
실제 Storage 자동 생성
│
▼
PersistentVolume 자동 생성
│
▼
PVC와 PV 연결
----------

예를 들어 클러스터에 다음과 같은 StorageClass가 있다고 가정해 보겠습니다.

[source,bash]
----
oc get storageclass
----

[source,text]
---------------------------------------
NAME                    PROVISIONER
gp3-csi                 ebs.csi.aws.com
---------------------------------------

사용자는 실제 AWS EBS API나 Volume ID를 알 필요 없이 다음처럼 PVC를 요청할 수 있습니다.

[source,yaml]
-------------
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-data
spec:
  storageClassName: gp3-csi
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
-------------

PVC가 생성되면 StorageClass에 설정된 CSI Provisioner가 요청에 맞는 실제 스토리지를 생성하고, 이에 대응하는 PV도 자동으로 생성합니다.

[source,text]
--------------
PVC: my-data
10Gi 요청
│
▼
StorageClass: gp3-csi
│
▼
AWS EBS 10Gi 생성
│
▼
PV 자동 생성
│
▼
PVC ↔ PV Bound
--------------

클러스터에 **기본(Default) StorageClass**가 설정되어 있다면 PVC에서 ``storageClassName``을 직접 지정하지 않아도 기본 StorageClass가 사용될 수 있습니다.

정리하면 다음과 같습니다.

[source,text]
--------
**[정적 프로비저닝]**

관리자가 Storage와 PV를 먼저 준비
↓
사용자가 PVC 요청
↓
PVC ↔ PV

**[동적 프로비저닝]**

사용자가 PVC 요청
↓
StorageClass
↓
Storage와 PV가 자동 생성
↓
PVC ↔ PV
--------

실제 Kubernetes/OpenShift 환경에서는 **StorageClass와 CSI를 이용한 동적 프로비저닝**이 널리 사용됩니다.

이제 현재 OpenShift 클러스터에 어떤 StorageClass가 제공되고 있는지 확인하고, PVC를 생성하여 실제 영구 스토리지를 요청해 보겠습니다.

[IMPORTANT]
====
``PersistentVolume``은 특정 네임스페이스에 속하지 않는 **클러스터 범위(cluster-scoped)** 리소스라서, 정적 프로비저닝(PV를 직접 만드는 것)에는 보통 클러스터 관리자 권한이 필요합니다. +
**이 실습의 user 계정은 admin 권한이 없기 때문에, 아래 "정적 프로비저닝 예시(참고용)"는 개념 이해를 위해 읽어만 보시고, 실제 실습은 이어지는 "동적 프로비저닝으로 Persistent Volume Claim 만들기"부터 진행하세요.**
====

=== 동적 프로비저닝으로 Persistent Volume Claim 만들기

일반적으로 쿠버네티스 구현체는 기본(default) Storage Class를 제공해서 누구나 동적 프로비저닝을 빠르게 시작할 수 있게 해줍니다.
다음 명령으로 이 클러스터에 준비된 Storage Class 정보를 확인할 수 있습니다:

[.console-input]
[source,bash]
----
oc get sc
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                                              PROVISIONER                           AGE
ocs-external-storagecluster-ceph-rbd (default)    openshift-storage.rbd.csi.ceph.com     31h
----

이 클러스터는 Ceph 기반 외부 스토리지 클러스터를 가리키는 ``ocs-external-storagecluster-ceph-rbd``를 기본 Storage Class로 사용하도록 미리 구성되어 있습니다. (실제 표시되는 이름과 `PROVISIONER` 값은 클러스터 구성에 따라 다를 수 있습니다.)

그런 다음 Persistent Volume Claim을 생성하면 Persistent Volume이 자동으로 생성됩니다. 

[source, yaml]
----
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: myboot-volumeclaim
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Mi
----

__storage class__를 따로 지정하지 않았지만 이 클러스터에는 기본값(`ocs-external-storagecluster-ceph-rbd`)이 정의되어 있으므로, __PVC__는 암묵적으로 그것을 참조합니다. (이 pod 정의를 앞서 살펴본 정적 프로비저닝 예시의 ``myboot-persistent-volume-claim.yaml``과 비교해 보는 것도 좋습니다.)

[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: myboot-volumeclaim
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Mi
EOF
oc get pvc
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                 STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS                            AGE
myboot-volumeclaim   Pending                                      ocs-external-storagecluster-ceph-rbd   46s
----

__PVC__가 __Pending__ STATUS인 것에 주목하세요. 우리가 만들고 있는 것이 동적 스토리지라는 것을 기억해 보면, 이는 __pod__가 volume을 요청하기 전까지는 __PVC__가 pending 상태로 남아 있고 __PV__도 생성되지 않는다는 의미입니다(스토리지 드라이버의 볼륨 바인딩 모드에 따라, PVC 생성 직후 바로 바인딩되는 경우도 있습니다).

[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    
    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  volumes:
  - name: demo-volume
    persistentVolumeClaim:
      claimName: myboot-volumeclaim
EOF
----

====
{watch-terminal}::
+
--
[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME          READY   STATUS    RESTARTS   AGE
myboot-demo   1/1     Running   0          2m36s
----
--
====

pod가 __Running__ 상태가 되면, __PVC__와 __PV__의 매개변수를 확인할 수 있습니다.

[.console-input]
[source,bash]
----
oc get pvc
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----

myboot-volumeclaim   Bound    pvc-6de4f27e-bd40-4b58-bb46-91eb08ca5bd7   1Gi        RWO            ocs-external-storagecluster-ceph-rbd   116s
----

이제 volume claim이 volume에 __Bound__ 된 것에 주목하세요(요청한 10Mi보다 큰 용량이 잡혀 있을 수 있는데, 스토리지 드라이버의 최소 할당 단위 때문입니다).

마지막으로, 일반 유저들은 확인할 수 없지만, admin 권한을 가진 유저는 __PV__가 자동으로 생성된 것을 확인할 수 있습니다:

[source,test]
----
oc get pv
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM                        STORAGECLASS                            REASON   AGE
pvc-6de4f27e-bd40-4b58-bb46-91eb08ca5bd7   1Gi        RWO            Delete           Bound    myspace/myboot-volumeclaim   ocs-external-storagecluster-ceph-rbd            77s
----

__CLAIM__ 필드가 __PV__ 생성을 담당한 __PVC__를 가리키는 것에 주목하세요. (정적 프로비저닝과 달리, 이 __PV__는 우리가 직접 만든 것이 아니라 __PVC__를 생성하자 스토리지 드라이버가 자동으로 만들어 준 것입니다.)

=== 데이터 영속성 확인하기

Pod가 사라져도 __PersistentVolumeClaim__에 저장된 데이터는 그대로 유지되는지 확인해 봅시다. ``emptyDir``의 일시성을 확인했던 것과 같은 방식으로, pod를 지우고 같은 PVC를 참조하는 pod를 다시 만들어서 확인합니다.

아직 닫지 않았다면 컨테이너의 셸을 닫으세요:

[tabs]
====
컨테이너::
+
--
[.console-input]
[source,bash]
----
exit
----
--
====

그리고 pod를 삭제합니다:

[.console-input]
[source,bash]
----
oc delete pod myboot-demo
----

[IMPORTANT]
====
다시 배포를 시도하기 전에 pod가 완전히 삭제될 때까지 기다려야 합니다.
====

그런 다음 같은 PVC를 참조하는 동일한 pod를 다시 배포합니다:

[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    
    volumeMounts:
    - mountPath: /tmp/demo
      name: demo-volume

  volumes:
  - name: demo-volume
    persistentVolumeClaim:
      claimName: myboot-volumeclaim
EOF
----

그리고 `Running` 상태가 되면 pod에 ``exec``로 접속합니다:

[.console-input]
[source,bash]
----
oc exec -ti myboot-demo -- /bin/bash
----

[tabs]
====
컨테이너::
+
--

새 pod의 마운트 지점 내용을 조회해 봅시다.

[.console-input]
[source,bash]
----
ls /tmp/demo && cat /tmp/demo/greeting.txt
----

이전 pod에서 만든 ``greeting.txt`` 파일이 그대로 남아 있는 것을 확인할 수 있는데, 이는 데이터가 pod가 아니라 __PersistentVolumeClaim__(그리고 그 뒤의 실제 스토리지)에 저장되어 있어서, pod가 삭제되고 다시 만들어져도 사라지지 않기 때문입니다. ``emptyDir``의 경우와 대조해 보세요.

[.console-output]
[source,bash]
----
total 4
-rw-r--r--. 1 root root 5 Jul 19 14:06 greeting.txt
Jambo
----

pod를 나갑니다.

[.console-input]
[source,bash]
----
exit
----

--
====

=== 정리

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get pvc
----

결과:

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                 STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS                            AGE
myboot-volumeclaim   Bound    pvc-6de4f27e-bd40-4b58-bb46-91eb08ca5bd7   1Gi        RWO            ocs-external-storagecluster-ceph-rbd   14m
----

pod가 삭제되었더라도 PVC(그리고 PV)는 여전히 남아 있으며, 수동으로 삭제해야 합니다.

[.console-input]
[source,bash]
----
oc delete pod myboot-demo
oc delete pvc myboot-volumeclaim
----

== 분산 파일 시스템

클라우드 제공업체는 데이터가 모든 노드에서 항상 사용 가능하도록 분산 스토리지를 제공한다는 점을 알아두는 것이 중요합니다.
마지막 예시에서 봤듯이, 이 storage class는 모든 노드가 동일한 디스크 콘텐츠를 보도록 보장합니다.

예를 들어, 온프레미스에서 쿠버네티스/OpenShift를 사용하고 있거나 특정 벤더 솔루션에 의존하고 싶지 않다면, 쿠버네티스에서도 분산 파일 시스템을 지원합니다.
그런 경우라면 NFS, https://www.gluster.org/[GlusterFS] 또는 https://ceph.io/[Ceph]를 사용하는 것을 권장합니다.

바로 앞서 실습에서 사용한 `ocs-external-storagecluster-ceph-rbd` Storage Class가 이러한 Ceph 기반 분산 스토리지의 실제 예시입니다.
