== 배경지식: Volume과 PersistentVolume

컨테이너는 기본적으로 **일시적인(ephemeral) 실행 환경**입니다.

컨테이너가 실행되는 동안에는 컨테이너의 파일 시스템에 파일을 생성할 수 있지만, 컨테이너가 새로 만들어지면 기존 컨테이너의 파일 시스템에 저장했던 데이터는 그대로 유지된다고 보장할 수 없습니다.

예를 들어 데이터베이스를 컨테이너로 실행하면서 데이터 파일까지 컨테이너의 파일 시스템에만 저장한다면, 컨테이너가 새로 생성되었을 때 중요한 데이터가 사라질 수 있습니다.

Kubernetes에서는 애플리케이션의 데이터를 저장하기 위해 **Volume**을 사용할 수 있습니다.

Volume은 Pod에 정의하고, Pod 안의 하나 이상의 컨테이너에 특정 디렉터리로 마운트해서 사용할 수 있습니다.

[source,text]
----
Pod
│
├── Container A
│      └── /data ──────┐
│                      │
├── Container B        │
│      └── /shared ────┤
│                      │
└── Volume ────────────┘
----

컨테이너에서는 Volume이 일반적인 디렉터리처럼 보입니다.

하지만 **Volume을 사용한다고 해서 데이터가 항상 영구적으로 보존되는 것은 아닙니다.**

데이터가 얼마나 오래 유지되는지는 사용하는 Volume의 종류에 따라 달라집니다.

대표적으로 다음과 같은 종류가 있습니다.

* ``emptyDir``
** Pod를 위한 임시 저장 공간입니다.
** Pod가 생성될 때 비어 있는 상태로 만들어집니다.
** 같은 Pod 안에 있는 여러 컨테이너가 함께 사용할 수 있습니다.
** 컨테이너가 재시작되더라도 같은 Pod가 유지되는 동안에는 데이터가 유지됩니다.
** 하지만 Pod가 삭제되면 ``emptyDir``의 데이터도 함께 사라집니다.

* ``hostPath``
** Node의 특정 디렉터리를 Pod에 직접 마운트합니다.
** 데이터가 특정 Node에 종속되기 때문에 Pod가 다른 Node에서 실행될 경우 동일한 데이터를 사용할 수 없습니다.
** OpenShift에서는 보안상 일반 사용자에게 ``hostPath`` 사용이 제한되는 경우가 많으며, 일반적인 애플리케이션의 영구 저장소로 사용하는 것은 권장되지 않습니다.

* ``PersistentVolume``
** Pod의 수명과 독립적으로 데이터를 유지해야 할 때 사용할 수 있습니다.
** 애플리케이션은 일반적으로 ``PersistentVolumeClaim(PVC)``을 통해 필요한 저장 공간을 요청합니다.
** 실제 저장소는 클라우드 Block Storage, Ceph, NFS 등의 다양한 스토리지 시스템이 될 수 있습니다.
** 최근 Kubernetes/OpenShift 환경에서는 주로 **CSI(Container Storage Interface)** 드라이버를 통해 외부 스토리지와 연결됩니다.

[source,text]
----
Pod
 │
 │ mount
 ▼
PVC (PersistentVolumeClaim)
 │
 ▼
PV (PersistentVolume)
 │
 ▼
실제 Storage
(Cloud Disk, Ceph, NFS 등)
----

따라서 다음 차이를 먼저 기억해 두는 것이 중요합니다.

[source,text]
----
emptyDir
  → Pod와 수명을 함께함
  → Pod 삭제 시 데이터도 삭제됨

PersistentVolume
  → Pod와 독립적인 수명을 가질 수 있음
  → Pod가 삭제되어도 PVC가 유지되는 동안 데이터를 계속 사용할 수 있음
----

이번 실습에서는 먼저 ``emptyDir``을 통해 **Pod와 Volume의 관계**를 살펴보고, 이후 ``PersistentVolumeClaim``을 사용하여 **Pod가 삭제되어도 데이터를 유지하는 방법**을 확인합니다.

== 실습: emptyDir Volume

=== emptyDir 생성하기

먼저 가장 간단한 Volume인 ``emptyDir``을 사용해 보겠습니다.

``emptyDir``은 Pod가 Node에 배치될 때 생성되며 처음에는 비어 있습니다.

Pod 안의 컨테이너는 이 Volume을 자신의 파일 시스템의 특정 디렉터리에 마운트해서 사용할 수 있습니다.

다음 Pod를 생성합니다.

[#create-emptydir-pod]
[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    volumeMounts:
    - name: demo-volume
      mountPath: /tmp/demo

  volumes:
  - name: demo-volume
    emptyDir: {}
EOF
----

여기서 중요한 부분은 다음 두 가지입니다.

먼저 ``volumes``에서 Pod가 사용할 Volume을 정의합니다.

[source,yaml]
----
volumes:
- name: demo-volume
  emptyDir: {}
----

그리고 ``volumeMounts``에서 이 Volume을 컨테이너의 어느 경로에 연결할지 정의합니다.

[source,yaml]
----
volumeMounts:
- name: demo-volume
  mountPath: /tmp/demo
----

관계를 그림으로 표현하면 다음과 같습니다.

[source,text]
----
Pod
│
├── Container: myboot-demo
│       │
│       └── /tmp/demo
│               │
└── emptyDir: demo-volume
----

터미널 2에서 Pod가 ``Running`` 상태가 된 것을 확인합니다.

필요한 경우 다음 명령으로 Pod가 준비될 때까지 기다릴 수도 있습니다.

[#wait-emptydir-pod]
[.console-input]
[source,bash]
----
oc wait --for=condition=Ready pod/myboot-demo --timeout=120s
----


=== emptyDir에 데이터 저장하기

``myboot`` 애플리케이션에는 ``/tmp/demo`` 디렉터리에 파일을 생성하는 실습용 기능이 있습니다.

다음 명령으로 애플리케이션의 ``/appendgreetingfile`` 엔드포인트를 호출합니다.

[#write-emptydir]
[.console-input]
[source,bash]
----
oc exec myboot-demo -- curl -s localhost:8080/appendgreetingfile
----

이제 ``/tmp/demo``을 확인합니다.

[#list-emptydir]
[.console-input]
[source,bash]
----
oc exec myboot-demo -- ls -l /tmp/demo
----

다음과 같이 ``greeting.txt`` 파일이 생성된 것을 확인할 수 있습니다.

[.console-output]
[source,bash]
----
total 4
-rw-r--r--. 1 1000 1000 5 Jul 13 08:11 greeting.txt
----

파일의 내용을 확인합니다.

[#read-emptydir]
[.console-input]
[source,bash]
----
oc exec myboot-demo -- cat /tmp/demo/greeting.txt
----

[.console-output]
[source,text]
----
Jambo
----

즉, 애플리케이션이 생성한 데이터가 컨테이너의 ``/tmp/demo`` 경로에 마운트된 ``emptyDir`` Volume에 저장되어 있습니다.


=== emptyDir의 수명 확인하기

이번에는 Pod를 삭제해 보겠습니다.

[#delete-emptydir-pod]
[.console-input]
[source,bash]
----
oc delete pod myboot-demo
----

Pod가 완전히 삭제될 때까지 기다린 다음, 동일한 정의로 다시 생성합니다.

[#recreate-emptydir-pod]
[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    volumeMounts:
    - name: demo-volume
      mountPath: /tmp/demo

  volumes:
  - name: demo-volume
    emptyDir: {}
EOF
----

새 Pod가 준비될 때까지 기다립니다.

[.console-input]
[source,bash]
----
oc wait --for=condition=Ready pod/myboot-demo --timeout=120s
----

새로운 Pod의 ``/tmp/demo`` 디렉터리를 확인합니다.

[#check-recreated-emptydir]
[.console-input]
[source,bash]
----
oc exec myboot-demo -- ls -la /tmp/demo
----

이전에 만들었던 ``greeting.txt`` 파일이 더 이상 존재하지 않는 것을 확인할 수 있습니다.

이는 ``emptyDir``의 수명이 **Pod의 수명과 연결되어 있기 때문**입니다.

[source,text]
----
첫 번째 Pod
    │
    └── emptyDir
          └── greeting.txt
                │
                ▼
           Pod 삭제
                │
                ▼
       emptyDir도 함께 삭제


두 번째 Pod
    │
    └── 새로운 emptyDir
           └── 비어 있음
----

[NOTE]
====
``emptyDir``의 데이터는 **컨테이너가 재시작되는 것만으로는 삭제되지 않습니다.**

같은 Pod 안에서 컨테이너만 재시작되는 경우 ``emptyDir``은 그대로 유지됩니다.

``emptyDir``의 데이터가 사라지는 것은 Pod가 Node에서 제거되고 해당 ``emptyDir``의 수명이 끝났을 때입니다.
====

실습에 사용한 Pod를 삭제합니다.

[.console-input]
[source,bash]
----
oc delete pod myboot-demo
----


=== 같은 Pod의 컨테이너끼리 emptyDir 공유하기

``emptyDir``은 같은 Pod 안에 있는 여러 컨테이너가 함께 사용할 수도 있습니다.

이번에는 하나의 Pod 안에 두 개의 컨테이너를 실행하고 동일한 ``emptyDir``을 두 컨테이너 모두에 마운트해 보겠습니다.

[#create-shared-emptydir]
[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo-1
    image: quay.io/rhdevelopers/myboot:v4
    volumeMounts:
    - name: demo-volume
      mountPath: /tmp/demo

  - name: myboot-demo-2
    image: quay.io/rhdevelopers/myboot:v4
    env:
    - name: SERVER_PORT
      value: "8090"
    volumeMounts:
    - name: demo-volume
      mountPath: /tmp/demo

  volumes:
  - name: demo-volume
    emptyDir: {}
EOF
----

두 컨테이너가 모두 준비될 때까지 기다립니다.

[.console-input]
[source,bash]
----
oc wait --for=condition=Ready pod/myboot-demo --timeout=120s
----

터미널 2에서는 다음과 같이 ``READY``가 ``2/2``가 된 것을 확인할 수 있습니다.

[.console-output]
[source,bash]
----
NAME          READY   STATUS    RESTARTS   AGE
myboot-demo   2/2     Running   0          20s
----

하나의 Pod 안에 두 개의 컨테이너가 실행되고 있다는 의미입니다.

두 컨테이너는 각각 다음과 같이 동일한 Volume을 사용하고 있습니다.

[source,text]
----
Pod: myboot-demo
│
├── Container: myboot-demo-1
│       └── /tmp/demo ───────┐
│                            │
├── Container: myboot-demo-2 │
│       └── /tmp/demo ───────┤
│                            │
└── emptyDir: demo-volume ───┘
----

먼저 첫 번째 컨테이너에서 파일을 만듭니다.

[#write-shared-volume]
[.console-input]
[source,bash]
----
oc exec myboot-demo -c myboot-demo-1 -- \
  /bin/bash -c 'echo "Hello from container 1" > /tmp/demo/shared.txt'
----

이번에는 **두 번째 컨테이너**에서 같은 파일을 읽어 봅니다.

[#read-shared-volume]
[.console-input]
[source,bash]
----
oc exec myboot-demo -c myboot-demo-2 -- \
  cat /tmp/demo/shared.txt
----

[.console-output]
[source,text]
----
Hello from container 1
----

첫 번째 컨테이너가 생성한 파일을 두 번째 컨테이너에서도 바로 확인할 수 있습니다.

즉, Volume은 단순히 데이터를 저장하기 위한 용도뿐 아니라 **같은 Pod 안의 컨테이너들이 데이터를 공유하는 용도**로도 사용할 수 있습니다.

Pod의 Volume 정보를 확인해 봅니다.

[#describe-emptydir-pod]
[.console-input]
[source,bash]
----
oc describe pod myboot-demo
----

출력의 ``Volumes`` 부분에서 ``demo-volume``이 ``EmptyDir`` 타입인 것을 확인할 수 있습니다.

[.console-output]
[source,text]
----
Volumes:
  demo-volume:
    Type:       EmptyDir
    Medium:
    SizeLimit:  <unset>
----

실습에 사용한 Pod를 삭제합니다.

[#cleanup-emptydir]
[.console-input]
[source,bash]
----
oc delete pod myboot-demo
----


== 배경지식: PersistentVolume과 PersistentVolumeClaim

``emptyDir`` 실습에서는 Pod를 삭제하자 데이터도 함께 사라지는 것을 확인했습니다.

하지만 데이터베이스처럼 Pod가 새로 만들어져도 데이터를 계속 유지해야 하는 애플리케이션도 있습니다.

Kubernetes에서는 이러한 영구 스토리지를 추상화하기 위해 ``PersistentVolume``과 ``PersistentVolumeClaim``을 사용합니다.


=== PersistentVolume

``PersistentVolume``(**PV**)은 Kubernetes 클러스터에서 사용할 수 있는 **스토리지 리소스**를 나타냅니다.

PV는 특정 Pod와 독립적인 수명을 가집니다.

실제 PV 뒤에는 환경에 따라 다양한 스토리지 시스템이 연결될 수 있습니다.

예를 들면 다음과 같습니다.

* AWS EBS
* Ceph
* NFS
* 기타 CSI 기반 스토리지

``PersistentVolume``은 특정 프로젝트에 속하지 않는 **클러스터 범위(cluster-scoped) 리소스**입니다.


=== PersistentVolumeClaim

애플리케이션 사용자가 직접 PV를 만들거나 실제 스토리지의 세부 정보를 알고 있을 필요는 없습니다.

대신 ``PersistentVolumeClaim``(**PVC**)을 통해 필요한 저장 공간을 요청합니다.

PVC는 Namespace에 속하는 리소스입니다.

예를 들어 다음 PVC는 1Gi의 저장 공간을 요청합니다.

[source,yaml]
----
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-data
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
----

이 요청은 대략 다음과 같은 의미입니다.

[source,text]
----
"1Gi 크기의 저장 공간이 필요합니다."

크기       : 1Gi
접근 모드  : ReadWriteOnce
----

여기에는 다음과 같은 실제 스토리지의 세부 정보가 들어 있지 않습니다.

[source,text]
----
AWS EBS Volume ID
Ceph Pool
Storage Server 주소
실제 Disk 경로
----

애플리케이션 개발자는 **어떤 저장 공간이 필요한지 요청**하고, 실제 저장 공간을 어떻게 제공할지는 Kubernetes/OpenShift의 스토리지 구성이 담당합니다.


=== PV와 PVC의 관계

전체 관계를 정리하면 다음과 같습니다.

[source,text]
----
애플리케이션 개발자
        │
        │ PVC 생성
        ▼
PersistentVolumeClaim
        │
        │ 요청 조건에 맞는 스토리지
        ▼
PersistentVolume
        │
        ▼
실제 Storage
----

그리고 Pod에서는 PV를 직접 지정하지 않고 **PVC를 참조**합니다.

[source,text]
----
Pod
 │
 │ persistentVolumeClaim
 ▼
PVC
 │
 ▼
PV
 │
 ▼
Storage
----


=== 정적 프로비저닝과 동적 프로비저닝

PV를 제공하는 방법은 크게 두 가지로 나눌 수 있습니다.

==== 정적 프로비저닝

정적 프로비저닝(Static Provisioning)은 클러스터 관리자가 실제 스토리지와 PV를 **미리 준비**하는 방식입니다.

[source,text]
----
클러스터 관리자
      │
      ├── 실제 Storage 준비
      │
      └── PV 생성
              │
              ▼
사용자가 PVC 생성
              │
              ▼
조건이 맞는 PV와 PVC가 Bind
----

사용자가 요청하기 전에 관리자가 스토리지를 준비해야 한다는 특징이 있습니다.

PV는 클러스터 범위 리소스이며 이번 실습의 일반 사용자에게는 PV를 생성할 권한이 없습니다.

따라서 이번 실습에서는 정적 PV를 직접 생성하지 않습니다.


==== 동적 프로비저닝

현대적인 Kubernetes/OpenShift 환경에서는 **동적 프로비저닝(Dynamic Provisioning)**이 널리 사용됩니다.

사용자가 PVC를 생성하면 필요한 실제 스토리지와 PV를 자동으로 생성하는 방식입니다.

이때 중요한 역할을 하는 것이 ``StorageClass``입니다.

[source,text]
----
사용자
 │
 │ PVC 생성
 ▼
PersistentVolumeClaim
 │
 │
 ▼
StorageClass
 │
 │ CSI Provisioner
 ▼
실제 Storage 생성
 │
 ▼
PersistentVolume 생성
 │
 ▼
PVC ↔ PV Bound
----

``StorageClass``는 클러스터 관리자가 미리 정의해 둔 스토리지의 종류와 프로비저닝 방법을 나타냅니다.

예를 들어 환경에 따라 다음과 같은 StorageClass가 있을 수 있습니다.

[source,text]
----
gp3-csi
ceph-rbd
standard
fast-storage
----

애플리케이션 사용자는 실제 스토리지 API나 디스크 ID를 알 필요 없이 PVC만 생성하면 됩니다.

클러스터에 **기본(Default) StorageClass**가 설정되어 있다면 PVC에서 ``storageClassName``을 지정하지 않아도 해당 StorageClass가 자동으로 사용됩니다.


== 실습: PersistentVolumeClaim

=== StorageClass 확인하기

현재 OpenShift 클러스터에 어떤 StorageClass가 준비되어 있는지 확인합니다.

[#get-storageclass]
[.console-input]
[source,bash]
----
oc get storageclass
----

환경에 따라 출력되는 StorageClass의 이름과 Provisioner는 다를 수 있습니다.

예를 들면 다음과 같습니다.

[.console-output]
[source,text]
----
NAME            PROVISIONER       RECLAIMPOLICY   VOLUMEBINDINGMODE
gp3-csi (default) ebs.csi.aws.com Delete          WaitForFirstConsumer
----

``(default)``가 표시된 StorageClass가 **기본 StorageClass**입니다.

[NOTE]
====
실습 환경에 표시되는 StorageClass의 이름은 위 예시와 다를 수 있습니다.

이번 실습에서는 클러스터에 기본 StorageClass가 구성되어 있다고 가정합니다.
====


=== PVC 생성하기

이제 1Gi의 영구 저장 공간을 요청하는 PVC를 생성합니다.

[#create-pvc]
[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: myboot-volumeclaim
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
EOF
----

생성된 PVC를 확인합니다.

[#get-pvc]
[.console-input]
[source,bash]
----
oc get pvc myboot-volumeclaim
----

StorageClass의 설정에 따라 PVC는 곧바로 ``Bound``가 될 수도 있고 다음과 같이 ``Pending`` 상태로 보일 수도 있습니다.

[.console-output]
[source,text]
----
NAME                 STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
myboot-volumeclaim   Pending                                      gp3-csi        5s
----

여기서 ``Pending``이 반드시 오류를 의미하는 것은 아닙니다.

StorageClass에는 Volume을 언제 생성하고 PVC에 연결할지를 결정하는 ``volumeBindingMode``라는 설정이 있습니다.

대표적으로 다음 두 가지 방식이 있습니다.

* ``Immediate``
** PVC가 생성되면 곧바로 Volume을 생성하고 연결합니다.

* ``WaitForFirstConsumer``
** PVC를 실제로 사용하는 Pod가 생성될 때까지 Volume 생성과 연결을 기다립니다.

따라서 사용하는 StorageClass가 ``WaitForFirstConsumer`` 방식이라면 PVC만 만든 상태에서는 ``Pending``으로 보일 수 있습니다.

반대로 ``Immediate`` 방식이라면 이미 ``Bound`` 상태일 수도 있습니다.


=== PVC를 사용하는 Pod 생성하기

이제 ``myboot-volumeclaim``을 사용하는 Pod를 만들어 보겠습니다.

[#create-pvc-pod]
[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    volumeMounts:
    - name: demo-volume
      mountPath: /tmp/demo

  volumes:
  - name: demo-volume
    persistentVolumeClaim:
      claimName: myboot-volumeclaim
EOF
----

여기서 앞의 ``emptyDir``과 가장 중요한 차이점을 확인할 수 있습니다.

``emptyDir``에서는 다음과 같이 Volume의 종류를 Pod가 직접 정의했습니다.

[source,yaml]
----
volumes:
- name: demo-volume
  emptyDir: {}
----

이번에는 Pod에서 스토리지 종류를 직접 정의하지 않고 PVC를 참조합니다.

[source,yaml]
----
volumes:
- name: demo-volume
  persistentVolumeClaim:
    claimName: myboot-volumeclaim
----

즉,

[source,text]
----
Pod
 │
 │ claimName
 ▼
PVC: myboot-volumeclaim
 │
 ▼
PV
 │
 ▼
실제 Storage
----

의 관계가 만들어집니다.

Pod가 준비될 때까지 기다립니다.

[#wait-pvc-pod]
[.console-input]
[source,bash]
----
oc wait --for=condition=Ready pod/myboot-demo --timeout=180s
----

PVC의 상태를 다시 확인합니다.

[#get-bound-pvc]
[.console-input]
[source,bash]
----
oc get pvc myboot-volumeclaim
----

정상적으로 프로비저닝되었다면 ``STATUS``가 ``Bound``로 표시됩니다.

[.console-output]
[source,text]
----
NAME                 STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
myboot-volumeclaim   Bound    pvc-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx   1Gi        RWO            gp3-csi        1m
----

``VOLUME``에는 PVC와 연결된 PV의 이름이 표시됩니다.

실제 값은 실습 환경마다 다릅니다.

[NOTE]
====
PV는 클러스터 범위 리소스이므로 일반 프로젝트 사용자에게는 PV를 직접 조회할 권한이 없을 수 있습니다.

중요한 것은 ``oc get pvc``에서 PVC가 ``Bound`` 상태인지 확인하는 것입니다.
====


=== PersistentVolume에 데이터 저장하기

앞의 ``emptyDir`` 실습과 동일하게 데이터를 만들어 보겠습니다.

[#write-pvc-data]
[.console-input]
[source,bash]
----
oc exec myboot-demo -- curl -s localhost:8080/appendgreetingfile
----

파일을 확인합니다.

[#read-pvc-data]
[.console-input]
[source,bash]
----
oc exec myboot-demo -- cat /tmp/demo/greeting.txt
----

[.console-output]
[source,text]
----
Jambo
----

현재 ``greeting.txt``는 컨테이너 자체가 아니라 PVC를 통해 제공된 스토리지에 저장되어 있습니다.


=== 데이터 영속성 확인하기

이제 ``emptyDir`` 실습에서 했던 것처럼 Pod를 삭제해 보겠습니다.

[#delete-pvc-pod]
[.console-input]
[source,bash]
----
oc delete pod myboot-demo
----

중요한 것은 **Pod만 삭제했을 뿐 PVC는 삭제하지 않았다는 점**입니다.

PVC를 확인합니다.

[#check-pvc-after-pod-delete]
[.console-input]
[source,bash]
----
oc get pvc myboot-volumeclaim
----

PVC는 여전히 존재하며 ``Bound`` 상태입니다.

[source,text]
----
Pod 삭제
   │
   X
PVC는 그대로 존재
   │
   ▼
PV
   │
   ▼
Storage의 데이터 유지
----

같은 PVC를 사용하는 새로운 Pod를 다시 만듭니다.

[#recreate-pvc-pod]
[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: myboot-demo
spec:
  containers:
  - name: myboot-demo
    image: quay.io/rhdevelopers/myboot:v4
    volumeMounts:
    - name: demo-volume
      mountPath: /tmp/demo

  volumes:
  - name: demo-volume
    persistentVolumeClaim:
      claimName: myboot-volumeclaim
EOF
----

새로운 Pod가 준비될 때까지 기다립니다.

[.console-input]
[source,bash]
----
oc wait --for=condition=Ready pod/myboot-demo --timeout=180s
----

새로운 Pod에서 ``/tmp/demo``을 확인합니다.

[#verify-persistent-data]
[.console-input]
[source,bash]
----
oc exec myboot-demo -- ls -l /tmp/demo
----

그리고 파일의 내용을 읽어 봅니다.

[.console-input]
[source,bash]
----
oc exec myboot-demo -- cat /tmp/demo/greeting.txt
----

[.console-output]
[source,text]
----
Jambo
----

이전 Pod에서 생성했던 ``greeting.txt``가 새로운 Pod에서도 그대로 보입니다.

이것이 앞에서 살펴본 ``emptyDir``과 가장 중요한 차이입니다.

[source,text]
----
emptyDir
────────

Pod A
 └── emptyDir
      └── greeting.txt

Pod A 삭제
      ↓
데이터 삭제

Pod B
 └── 새로운 emptyDir
      └── 비어 있음


PersistentVolume
────────────────

Pod A
 └── PVC
      └── greeting.txt

Pod A 삭제
      ↓
PVC와 데이터 유지

Pod B
 └── 같은 PVC
      └── greeting.txt
          그대로 존재
----

즉, **Pod는 교체될 수 있지만 데이터는 PVC를 통해 Pod의 수명과 분리하여 유지할 수 있습니다.**


=== 정리: emptyDir과 PersistentVolume

이번 실습에서 확인한 차이를 정리하면 다음과 같습니다.

[cols="2,2,2",options="header"]
|===
|구분
|emptyDir
|PersistentVolume/PVC

|주요 목적
|임시 데이터
|영구 데이터

|수명
|Pod와 연결됨
|Pod와 독립적

|컨테이너 재시작
|데이터 유지
|데이터 유지

|Pod 삭제
|데이터 삭제
|PVC가 유지되면 데이터 유지

|여러 컨테이너에서 사용
|가능
|가능하며 실제 가능 범위는 스토리지와 Access Mode에 따라 달라짐

|대표적인 용도
|임시 파일, 캐시, 같은 Pod의 컨테이너 간 파일 공유
|DB 데이터, 사용자 업로드 파일 등 지속적으로 보존할 데이터
|===


== 실습 환경 정리

먼저 Pod를 삭제합니다.

[#delete-persistent-pod]
[.console-input]
[source,bash]
----
oc delete pod myboot-demo
----

Pod가 삭제된 후에도 PVC가 남아 있는 것을 다시 확인할 수 있습니다.

[.console-input]
[source,bash]
----
oc get pvc myboot-volumeclaim
----

PVC가 더 이상 필요하지 않다면 삭제합니다.

[#delete-pvc]
[.console-input]
[source,bash]
----
oc delete pvc myboot-volumeclaim
----

[NOTE]
====
PVC를 삭제한 후 실제 PV와 스토리지의 데이터가 어떻게 처리되는지는 해당 PV 또는 StorageClass에 설정된 **Reclaim Policy**에 따라 달라집니다.

동적으로 프로비저닝된 스토리지에서는 ``Delete`` 정책이 사용되는 경우가 많으며, 이 경우 PVC 삭제 후 PV와 실제 스토리지도 제거됩니다.

반대로 ``Retain`` 정책이라면 PVC를 삭제해도 PV와 실제 스토리지가 자동으로 삭제되지 않고 관리자가 별도로 처리해야 합니다.
====
