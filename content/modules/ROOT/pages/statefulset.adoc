== 배경지식: StatefulSet

앞에서 살펴본 ``Deployment``는 일반적으로 **서로 구분할 필요가 없는 동일한 Pod들을 여러 개 실행**할 때 사용합니다.

예를 들어 Deployment가 Pod를 3개 실행하면 다음과 같이 임의의 이름을 가진 Pod가 생성됩니다.

[source,text]
----
myapp-7d86f5c9b4-ab123
myapp-7d86f5c9b4-cd456
myapp-7d86f5c9b4-ef789
----

이러한 Pod들은 기본적으로 서로 동일한 역할을 하므로 애플리케이션 입장에서 특정 Pod의 이름을 기억할 필요가 없습니다.

반면 ``StatefulSet``은 **각 Pod를 서로 구분해야 하는 애플리케이션**을 위해 사용합니다.

StatefulSet으로 replicas를 3개 생성하면 Pod 이름이 다음과 같이 만들어집니다.

[source,text]
----
myapp-0
myapp-1
myapp-2
----

뒤의 숫자를 **ordinal(서수)**이라고 합니다.

각 Pod는 자신의 ordinal을 기반으로 고유한 식별자를 가지며, Pod가 삭제되어 다시 생성되더라도 같은 이름을 사용합니다.

[source,text]
----
myapp-0
   │
   └── 삭제
         │
         ▼
     다시 생성
         │
         ▼
      myapp-0
----

또한 StatefulSet은 기본적으로 Pod를 순서대로 생성하고 제거합니다.

[source,text]
----
Scale Up

myapp-0
   ↓
myapp-1
   ↓
myapp-2
----

Scale Down에서는 반대 순서로 제거됩니다.

[source,text]
----
myapp-2
   ↓
myapp-1
   ↓
myapp-0
----

StatefulSet은 다음과 같이 **Pod의 고유한 식별성이 필요한 애플리케이션**에서 주로 사용합니다.

* 안정적이고 고유한 Pod 이름이 필요한 경우
* 각 Pod에 안정적인 네트워크 이름이 필요한 경우
* 각 Pod가 자신만의 영구 스토리지를 사용해야 하는 경우
* Pod의 생성 또는 종료 순서가 중요한 경우

대표적으로 데이터베이스나 분산 시스템 등이 이에 해당합니다.


=== Deployment와 StatefulSet

간단히 비교하면 다음과 같습니다.

[cols="2,2,2",options="header"]
|===
|구분
|Deployment
|StatefulSet

|Pod 식별
|Pod들을 일반적으로 서로 구분하지 않음
|각 Pod가 고유한 ordinal을 가짐

|Pod 이름
|임의의 suffix
|``app-0``, ``app-1``, ``app-2``

|생성/삭제 순서
|특정 순서를 기본적으로 보장하지 않음
|기본적으로 순서대로 생성/삭제

|안정적인 네트워크 ID
|일반적으로 필요 없음
|지원

|대표적인 용도
|웹 서버, API 서버
|DB, 분산 시스템
|===


=== StatefulSet과 Headless Service

StatefulSet에서는 각 Pod가 안정적인 네트워크 이름을 가질 수 있도록 **Headless Service**를 함께 사용합니다.

일반적인 Service는 하나의 ClusterIP를 제공하고 여러 Pod 뒤로 트래픽을 전달합니다.

[source,text]
----
             ┌── Pod A
Client → Service ── Pod B
             └── Pod C
----

반면 Headless Service는 하나의 가상 Service IP를 제공하지 않습니다.

대신 각 Pod를 DNS를 통해 직접 찾을 수 있도록 해 줍니다.

Headless Service는 다음과 같이 ``clusterIP: None``으로 정의합니다.

[source,yaml]
----
spec:
  clusterIP: None
----

StatefulSet과 Headless Service를 함께 사용하면 각 Pod는 다음과 같은 안정적인 DNS 이름을 사용할 수 있습니다.

[source,text]
----
<Pod 이름>.<Service 이름>

quarkus-statefulset-0.quarkus
quarkus-statefulset-1.quarkus
quarkus-statefulset-2.quarkus
----

이를 통해 애플리케이션이 특정 StatefulSet Pod를 직접 찾을 수 있습니다.

=== StatefulSet 생성하기

먼저 StatefulSet이 사용할 Headless Service와 StatefulSet을 함께 생성합니다.

Headless Service를 먼저 정의한 것에 주목하세요.

[#create-statefulset]
[.console-input]
[source,bash]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Service
metadata:
  name: quarkus
spec:
  clusterIP: None
  selector:
    app: quarkus-statefulset
  ports:
  - name: web
    port: 8080
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: quarkus-statefulset
spec:
  serviceName: quarkus
  replicas: 3
  selector:
    matchLabels:
      app: quarkus-statefulset
  template:
    metadata:
      labels:
        app: quarkus-statefulset
    spec:
      containers:
      - name: quarkus
        image: quay.io/rhdevelopers/quarkus-demo:v1
        ports:
        - name: web
          containerPort: 8080
EOF
----

StatefulSet의 다음 부분이 Headless Service와 연결됩니다.

[source,yaml]
----
serviceName: quarkus
----

그리고 Headless Service에는 다음 설정이 들어 있습니다.

[source,yaml]
----
clusterIP: None
----

두 리소스의 관계는 다음과 같습니다.

[source,text]
----
Headless Service: quarkus
          │
          │ network identity
          ▼
StatefulSet: quarkus-statefulset
          │
          ├── quarkus-statefulset-0
          ├── quarkus-statefulset-1
          └── quarkus-statefulset-2
----


=== Pod 이름과 생성 순서 확인하기

터미널 2를 살펴봅니다.

StatefulSet은 기본 설정에서 Pod를 순서대로 생성합니다.

[source,text]
----
quarkus-statefulset-0
          ↓
quarkus-statefulset-1
          ↓
quarkus-statefulset-2
----

최종적으로 다음과 같이 3개의 Pod가 보입니다.

[.console-output]
[source,bash]
----
NAME                     READY   STATUS    RESTARTS   AGE
quarkus-statefulset-0    1/1     Running   0          1m
quarkus-statefulset-1    1/1     Running   0          50s
quarkus-statefulset-2    1/1     Running   0          40s
----

Deployment에서 보았던 임의의 Pod 이름과 달리 StatefulSet의 Pod에는 ``0``, ``1``, ``2``라는 예측 가능한 ordinal이 붙습니다.

StatefulSet 자체도 확인합니다.

[#get-statefulset]
[.console-input]
[source,bash]
----
oc get statefulset
----

[.console-output]
[source=text]
----
NAME                  READY   AGE
quarkus-statefulset   3/3     1m
----

TIP: ``statefulset``은 ``sts``로 줄여서 사용할 수 있습니다.


=== Pod를 삭제하면 어떻게 될까?

StatefulSet Pod 중 하나를 직접 삭제해 보겠습니다.

터미널 2의 Pod 목록을 계속 보면서 터미널 1에서 다음 명령을 실행합니다.

[#delete-statefulset-pod]
[.console-input]
[source,bash]
----
oc delete pod quarkus-statefulset-1
----

잠시 후 다시 Pod를 확인합니다.

[#get-statefulset-pods]
[.console-input]
[source,bash]
----
oc get pods
----

다시 다음 세 Pod가 존재하는 것을 확인할 수 있습니다.

[.console-output]
[source=text]
----
NAME                     READY   STATUS    RESTARTS   AGE
quarkus-statefulset-0    1/1     Running   0          3m
quarkus-statefulset-1    1/1     Running   0          15s
quarkus-statefulset-2    1/1     Running   0          2m
----

``quarkus-statefulset-1`` Pod를 삭제했지만 StatefulSet이 새로운 Pod를 만들면서 **동일한 이름인 ``quarkus-statefulset-1``을 다시 사용**했습니다.

[source,text]
----
quarkus-statefulset-1
          │
        삭제
          │
          ▼
StatefulSet이 다시 생성
          │
          ▼
quarkus-statefulset-1
----

이것이 StatefulSet이 제공하는 **안정적인 Pod 식별자**의 중요한 특징입니다.


=== 안정적인 DNS 이름 확인하기

이번에는 Headless Service가 각 StatefulSet Pod에 안정적인 DNS 이름을 제공하는지 확인합니다.

클러스터 안에서 DNS 조회를 수행하는 임시 Pod를 실행합니다.

[#statefulset-dns]
[.console-input]
[source,bash]
----
oc run dns-test \
  --rm -i \
  --restart=Never \
  --image=busybox:1.36 \
  -- nslookup quarkus-statefulset-1.quarkus
----

다음과 비슷한 결과가 나타납니다.

[.console-output]
[source,text]
----
Name:      quarkus-statefulset-1.quarkus
Address:   10.128.x.x
----

IP 주소는 실습 환경마다 다릅니다.

중요한 것은 다음 이름으로 특정 Pod를 찾을 수 있다는 점입니다.

[source,text]
----
quarkus-statefulset-1.quarkus
----

전체 DNS 이름은 일반적으로 다음과 같은 형태가 됩니다.

[source,text]
----
<Pod 이름>.<Service 이름>.<Namespace>.svc.cluster.local
----

따라서 현재 예에서는 다음과 같은 이름을 사용할 수 있습니다.

[source,text,subs="+attributes"]
----
quarkus-statefulset-1.quarkus.{set-namespace}.svc.cluster.local
----

즉, Pod가 새로 생성되어 IP 주소가 변경되더라도 애플리케이션은 **안정적인 DNS 이름**을 사용하여 해당 Pod를 찾을 수 있습니다.


=== Scale Down 순서 확인하기

현재 StatefulSet에는 3개의 Pod가 있습니다.

[source,text]
----
quarkus-statefulset-0
quarkus-statefulset-1
quarkus-statefulset-2
----

replicas를 2개로 줄여 보겠습니다.

[#scale-statefulset]
[.console-input]
[source,bash]
----
oc scale statefulset quarkus-statefulset --replicas=2
----

터미널 2를 보면 ``quarkus-statefulset-2``가 먼저 종료되는 것을 확인할 수 있습니다.

[.console-output]
[source=text]
----
NAME                     READY   STATUS        RESTARTS   AGE
quarkus-statefulset-0    1/1     Running       0          5m
quarkus-statefulset-1    1/1     Running       0          2m
quarkus-statefulset-2    0/1     Terminating   0          4m
----

StatefulSet은 기본적으로 scale down할 때 **가장 높은 ordinal을 가진 Pod부터 제거**합니다.

[source,text]
----
3 replicas

-0
-1
-2
 │
 │ replicas=2
 ▼
-2 삭제

남은 Pod:
-0
-1
----

Deployment와 달리 Pod 생성과 제거에 일정한 순서가 있다는 것을 확인할 수 있습니다.


=== StatefulSet과 영구 스토리지

StatefulSet의 또 다른 중요한 특징은 각 Pod에 **자신만의 영구 스토리지**를 연결할 수 있다는 것입니다.

일반적으로 StatefulSet에서는 ``volumeClaimTemplates``를 사용하여 각 Pod마다 별도의 PVC를 생성할 수 있습니다.

예를 들어 다음과 같은 형태가 됩니다.

[source,text]
----
StatefulSet
│
├── myapp-0 ─── PVC-0 ─── Storage
│
├── myapp-1 ─── PVC-1 ─── Storage
│
└── myapp-2 ─── PVC-2 ─── Storage
----

Pod가 다시 생성되더라도 같은 ordinal의 Pod가 기존 스토리지와 다시 연결될 수 있습니다.

[source,text]
----
myapp-1 ─── PVC-1
   │
   └── Pod 삭제
          │
          ▼
       myapp-1
          │
          └── 기존 PVC-1 사용
----

앞의 **Volume과 PersistentVolume 실습**에서 이미 PVC와 데이터 영속성을 확인했으므로 이번 실습에서는 별도의 스토리지 실습을 반복하지 않습니다.

StatefulSet에서는 **안정적인 Pod 식별자와 안정적인 스토리지를 연결할 수 있다**는 점만 기억해 두면 됩니다.


=== 정리: StatefulSet의 핵심

이번 실습에서 확인한 StatefulSet의 특징은 세 가지입니다.

[cols="2,4",options="header"]
|===
|특징
|설명

|안정적인 Pod 식별자
|``myapp-0``, ``myapp-1``처럼 예측 가능한 이름을 사용하며 Pod가 다시 생성되어도 동일한 식별자를 사용

|안정적인 네트워크 식별자
|Headless Service를 통해 각 Pod를 고유한 DNS 이름으로 찾을 수 있음

|순서가 있는 동작
|기본 설정에서는 Pod를 낮은 ordinal부터 생성하고 높은 ordinal부터 제거
|===

그리고 StatefulSet은 필요에 따라 각 Pod에 별도의 PersistentVolumeClaim을 연결하여 안정적인 스토리지까지 제공할 수 있습니다.

따라서 애플리케이션이 이러한 특성을 필요로 하지 않는다면 일반적으로 StatefulSet보다 **Deployment가 더 단순하고 적합합니다.**
