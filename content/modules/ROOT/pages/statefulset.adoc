= StatefulSet
include::_attributes.adoc[]
:watch-terminal: 터미널 2

``StatefulSet``은 자신이 관리하는 Pod에 고유한 식별성을 부여합니다.
``StatefulSet``은 애플리케이션이 Pod의 (재)스케줄링 전반에 걸쳐 고유한 네트워크 식별자나 영구 스토리지를 필요로 할 때, 또는 배포와 스케일링의 순서에 대한 보장이 필요할 때 특히 유용합니다.

``StatefulSet``을 사용하는 가장 대표적인 예시 중 하나는 프라이머리/세컨더리 서버(예: 데이터베이스 클러스터)를 배포해야 하는 경우로, 이때는 클러스터를 시작하기 전에 각 서버의 호스트 이름을 미리 알아야 합니다.
또한 스케일 업/다운을 할 때도 정해진 순서대로 진행하고 싶을 것입니다(예: 프라이머리 노드를 먼저 시작하고 그다음에 세컨더리 노드를 시작).

[IMPORTANT]
====
``StatefulSet``에 접근하려면 표준 쿠버네티스 __service__가 아니라 쿠버네티스 __Headless Service__가 필요합니다. 이에 대해서는 아래에서 더 자세히 다룹니다.
====

== StatefulSet

StatefulSet은 쿠버네티스의 `StatefulSet` 리소스를 사용해서 생성합니다:

[source, yaml]
----
apiVersion: apps/v1beta1
kind: StatefulSet
metadata:
  name: quarkus-statefulset
  labels:
    app: quarkus-statefulset
spec:
  serviceName: "quarkus" # <.>
  replicas: 2
  selector:
    matchLabels:
      app: quarkus-statefulset
  template:
    metadata:
      labels:
        app: quarkus-statefulset
    spec:
      containers:
      - name: quarkus-statefulset
        image: quay.io/rhdevelopers/quarkus-demo:v1
        ports:
        - containerPort: 8080
          name: web
----
<.> ``serviceName``은 이 ``StatefulSet``을 관장하는 (headless) service의 이름입니다. 이 service는 StatefulSet보다 먼저 존재해야 하며, 세트의 네트워크 식별성을 책임집니다.

[#hostname-formula]
다음 "공식"을 사용하면 ``StatefulSet``에 속한 어떤 pod의 호스트 이름이든 예측할 수 있습니다:

****
`StatefulSet.name` + `-` + "ordinal index" 
****

"서수 인덱스"는 ``StatefulSet``이 생성한 첫 번째 pod에서 ``0``으로 시작하는 숫자이며, 추가되는 복제본 pod마다 1씩 증가합니다. 따라서 이번 경우, 위 ``StatefulSet``의 첫 번째 pod는 다음과 같은 호스트 이름을 가질 것으로 예상할 수 있습니다:

****
`quarkus-statefulset-0`
****

마지막으로, 앞서 언급했듯이 StatefulSet의 pod로 트래픽을 라우팅하려면 **headless service**도 만들어야 합니다:

[source, yaml,subs="+quotes"]
----
apiVersion: v1
kind: Service
metadata:
  name: #quarkus# #<.>
  labels:
    app: quarkus-statefulset
spec:
  ports:
  - port: 8080
    name: web
  clusterIP: None #<.>
  selector:
    app: quarkus-statefulset
----
<.> 이 값이 ``StatefulSet``의 `serviceName` 필드와 일치한다는 점에 주목하세요. dns 항목을 생성하려면 반드시 일치해야 합니다.
<.> ``clusterIP``를 ``None``으로 설정하는 것이 service를 "headless"로 만드는 부분입니다.

앞서 살펴본 ``StatefulSet``과 그에 대응하는 headless service를 생성하기 위해 다음 ``.yaml``을 클러스터에 적용합니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----

----

=== 안정적인 네트워크 식별성

앞서 **headless service**를 만든 이유는 stateful set의 pod들을 클러스터 __내부에서__ 찾을 수 있도록 하기 위해서였습니다(클러스터 외부에서 service에 접근하는 방법은 <<Exposing StatefulSets,Exposing StatefulSets>>를 참고하세요).

각 Pod가 생성될 때마다 `$(podname).$(governing service domain)` 형태의 DNS 서브도메인이 함께 부여되는데, 여기서 governing service는 StatefulSet의 `serviceName` 필드로 정의됩니다footnote:[쿠버네티스 공식 문서 link:https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#stable-network-id[여기]도 참고하세요]

클러스터 내에 pod를 하나 만들고 클러스터 내부에서 ``nslookup``을 실행해 보면 이를 테스트할 수 있습니다. 다음 명령을 실행해서, 클러스터 로컬 `nslookup` 쿼리를 실행할 수 있는 pod를 네임스페이스에 생성하세요.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc run -it --restart=Never --rm --image busybox:1.28 dns-test 
----

컨테이너 안에서 다음 명령을 실행해서 StatefulSet의 pod를 찾을 수 있는지 확인합니다.

[tabs]
====
Container::
+
--
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
nslookup quarkus-statefulset-0.quarkus
----

그러면 다음과 같은 출력을 얻게 됩니다(단, 표시되는 IP 주소는 다를 수 있습니다).

[.console-output]
[source,bash,subs="+macros,+attributes,+quotes"]

Name:      quarkus-statefulset-0.quarkus
Address 1: 172.17.0.3 #quarkus-statefulset-0.quarkus.myspace.svc.cluster.local# #<.>
----
<.> 전체 주소가 `$(podname).$(governing service domain).$(namespace)`.svc.cluster.local 형태라는 점에 주목하세요.

이제 다음 명령을 실행해서 pod를 종료할 수 있습니다(이 pod는 정리됩니다):

[.console-input]
[source,bash,subs="+macros,+attributes"]

====

이렇게 headless service의 도움으로, StatefulSet과 headless service가 만들어내는 내부 DNS 이름을 사용해서 StatefulSet의 어떤 pod든 찾을 수 있습니다.

== Exposing StatefulSets

우리의 stateful set은 headless service를 사용해야 했기 때문에, 클러스터 __외부__에서 pod에 접근할 때 사용할 외부 IP가 할당되지 않는다는 것을 알 수 있습니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc describe svc quarkus-statefulset
----

[.console-output]
[source,bash,subs="+macros,+attributes,+quotes"]
----
Name:              quarkus-statefulset
Namespace:         myspace
Labels:            app=quarkus-statefulset
Annotations:       <none>
Selector:          app=quarkus-statefulset
Type:              ClusterIP
IP Family Policy:  SingleStack
IP Families:       IPv4
#IP:                None#
#IPs:               None#
Port:              web  8080/TCP
TargetPort:        8080/TCP
Endpoints:         172.17.0.3:8080,172.17.0.4:8080,172.17.0.5:8080
Session Affinity:  None
Events:            <none>
----

대신 (내부) 엔드포인트만 할당됩니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc describe endpoints quarkus-statefulset
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
Name:         quarkus-statefulset
Namespace:    myspace
Labels:       app=quarkus-statefulset
              service.kubernetes.io/headless=
Annotations:  endpoints.kubernetes.io/last-change-trigger-time: 2021-07-20T04:45:21Z
Subsets:
  Addresses:          172.17.0.3,172.17.0.4,172.17.0.5
  NotReadyAddresses:  <none>
  Ports:
    Name  Port  Protocol
    ----  ----  --------
    web   8080  TCP

Events:  <none>
----

이는 어느 정도 당연한데, ``StatefulSet``을 사용하는 핵심 목적이 일반(headless가 아닌) ``Service``에 의해 추상화되는 대신 예측 가능한 이름으로 특정 pod를 참조할 수 있게 하는 것이기 때문입니다. 이름으로 pod에 접근할 수 있도록, 쿠버네티스는 모든 `StatefulSet` pod에 레이블을 부여하며, 이를 우리 service의 selector로 사용할 수 있습니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc describe pod quarkus-statefulset-2
----

축약된 출력에서 우리 레이블을 확인할 수 있습니다(강조 표시됨).

[.console-output]
[source,bash,subs="+macros,+attributes,+quotes"]
----
Name:         quarkus-statefulset-2
Namespace:    myspace
Priority:     0
Node:         devnation/192.168.49.2
Start Time:   Tue, 20 Jul 2021 04:45:04 +0000
Labels:       app=quarkus-statefulset
              controller-revision-hash=quarkus-statefulset-6bf5d59699
              #statefulset.kubernetes.io/pod-name=quarkus-statefulset-2#
Annotations:  <none>
----

:quick-open-file: quarkus-statefulset-external-svc.yaml

이 레이블을 이 특정 pod를 대상으로 하는 service의 selector로 사용할 수 있습니다. ``{quick-open-file}``을 살펴봅시다:

include::partial$tip_vscode_quick_open.adoc[]

[.console-output]
[source,yaml,subs="+macros,+attributes"]
.{quick-open-file}
----
include::example$quarkus-statefulset-external-svc.yaml[]
----
<.> 이 service가 LoadBalancer를 통해 노출되어야 함을 나타냅니다.
<.> 트래픽을 노드로 직접 라우팅해서 불필요한 홉을 방지합니다.
<.> 쿠버네티스 StatefulSet 기능이 자동으로 제공하는 레이블을 활용하는 selector입니다.

service를 살펴봤으니 이제 생성해 봅시다:

[.console-input]

----

== 스케일 다운과 정리

마지막으로, 인스턴스를 2개로 스케일 다운하면, 제거되는 것은 무작위로 선택되는 것이 아니라 더 나중에 시작된 것(`quarkus-statefulset-2`)입니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc scale sts quarkus-statefulset --replicas=2
----

[tabs]
====
{watch-terminal}::
+
--
[.console-output]
[source,bash,subs="+quotes"]
----

quarkus-statefulset-1   1/1     Running       0          7m49s
#quarkus-statefulset-2   0/1     Terminating   0          7m48s#
----
--
====

stateful set과 service를 함께 사용할 때는 이로 인해 문제가 생길 수 있다는 점에 주의하세요. 위에서 만든 service는 stateful set 안의 바로 그 pod를 참조하고 있었다는 것을 기억하세요. 지금 접근을 시도하면

[.console-input]

----

----

=== 정리

이제 이 섹션의 끝에 도달했습니다. statefulset을 만든 yaml(그리고 external service)을 삭제하면 statefulset의 모든 요소를 정리할 수 있습니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc delete -f apps/kubefiles/quarkus-statefulset.yaml
oc delete -f apps/kubefiles/quarkus-statefulset-external-svc.yaml
----
