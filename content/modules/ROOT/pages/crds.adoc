= Operator
include::_attributes.adoc[]
:watch-terminal: 터미널 2
:log-terminal: 터미널 3
:section-namespace: pizzahat

Operator는 우리가 제공하는 쿠버네티스 API 확장 기능을 관리하는 자동화된 컨트롤러를 설치해서, 쿠버네티스 클러스터의 기능을 확장하는 방법입니다.

이 섹션에서는 Operator가 이를 위해 쿠버네티스 API와 어떻게 상호작용하는지 더 깊이 살펴보겠습니다.

.실제 세계의 Operator
****
이 튜토리얼을 마스터 클래스에서 시연할 때는, OpenShift의 Kafka Operator를 보여주는 것도 좋습니다(대략적인 개요는 <<kafka-operator-install,여기>> 참고). OpenShift 클러스터에서 시연할 때 핵심 포인트는 다음과 같습니다:

. OperatorHub를 사용해서 얼마나 다양한 Operator가 있는지 보여줍니다.
. `AMQStreams` 또는 `Strimzi` Operator를 설치해서 클러스터에 Kafka 지원(즉, 우리가 곧 보게 될 CRD)을 추가합니다.
. Operator가 설치되면, `Kafka` CR을 설치할 네임스페이스를 하나 선택합니다.
. Developer Perspective에서 Operator가 Kafka를 생성하는 모습을 보여줍니다.

이 튜토리얼의 이 섹션에서는 직접 만든 장난감 같은 "Pizza Operator"로 Operator의 이런 측면들을 시연해 보겠습니다.
****

== CRD

Custom Resource는 API를 확장합니다.

Custom Controller는 원하는 상태를 지속적으로 유지하는 기능을 제공합니다. 즉, 상태를 모니터링하고 리소스를 설정과 일치하도록 조정합니다.

https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/

https://kubernetes.io/docs/tasks/access-kubernetes-api/custom-resources/custom-resource-definitions/

Custom Resource Definition(CRD)은 버전 1.7에 도입되었습니다.

CRD는 쿠버네티스 API를 확장합니다. 이 api 리소스들은 쉽게 확인할 수 있습니다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc api-resources
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
NAME                              SHORTNAMES   APIVERSION                             NAMESPACED   KIND
bindings                                       v1                                     true         Binding
componentstatuses                 cs           v1                                     false        ComponentStatus
configmaps                        cm           v1                                     true         ConfigMap
endpoints                         ep           v1                                     true         Endpoint
... #<.>
----
<.> 이 목록은 일부가 생략되었습니다.

이 목록에서 ``Deployments``처럼 이미 배운 몇몇 리소스를 확인할 수 있습니다.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc api-resources | grep Deployment
----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----

<1> 누군가 이 CRD를 describe할 때 표시될 설명입니다.
<2> 우리 ``CustomResource``가 가질 값 중 하나를 설명합니다. 바로 (`array`) 토핑 목록((`string`) 타입)입니다.
<3> ``CustomResource``의 spec에 정의할 수 있는 두 번째 필드를 설명합니다. 사용할 소스의 이름((`string`) 타입)입니다.

[IMPORTANT]
====
많은 CRD는 노출되는 필드에 대한 메타데이터를 포함해서, 쿠버네티스 API가 CR을 검증할 수 있게 합니다. API 버전 `v1` 이전에는 이것이 강제되지 않았지만, 쿠버네티스 v1.22부터는 모든 ``CustomResource``가 ``v1``이어야 하므로 객체 스키마를 정의해야 합니다.

=== Operator 배포하기

우리 CRD는 특정 네임스페이스에 한정되지 않지만, `pizza` CR을 다룰 operator를 배치할 네임스페이스는 필요합니다.

근본적으로 operator는 이전에 배포했던 `myboot` 애플리케이션과 같은 하나의 애플리케이션일 뿐입니다. 차이점은 operator가 쿠버네티스 API와 상호작용하는 방법을 알고, 자신이 관심 있는 리소스를 지켜본다는 것입니다.

:quick-open-file: PizzaResourceWatcher.java

곧 배포할 Pizza operator는 link:https://github.com/java-operator-sdk/java-operator-sdk[java operator sdk^]를 사용해서 link:https://quarkus.io/[Quarkus^]로 작성되었습니다. 이 operator의 코드는 이 저장소 안에 있습니다. operator 컨트롤러의 핵심 클래스 중 하나인 ``{quick-open-file}``을 확인해 보세요:

include::partial$tip_vscode_quick_open.adoc[]

[.console-output]
[source,java,subs="+macros,+attributes"]
.{quick-open-file}
----
package org.acme;

import io.fabric8.kubernetes.api.model.ContainerBuilder;
import io.fabric8.kubernetes.api.model.ObjectMetaBuilder;
import io.fabric8.kubernetes.api.model.Pod;
import io.fabric8.kubernetes.api.model.PodBuilder;
import io.fabric8.kubernetes.api.model.PodSpecBuilder;
import io.fabric8.kubernetes.client.KubernetesClient;
import io.fabric8.kubernetes.client.KubernetesClientException;
import io.fabric8.kubernetes.client.Watcher;
import io.fabric8.kubernetes.client.dsl.NonNamespaceOperation;
import io.fabric8.kubernetes.client.dsl.Resource;
import io.quarkus.runtime.StartupEvent;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import javax.enterprise.event.Observes;
import javax.inject.Inject;

public class PizzaResourceWatcher {

    @Inject
    KubernetesClient defaultClient;

    @Inject
    NonNamespaceOperation<PizzaResource, PizzaResourceList, PizzaResourceDoneable, Resource<PizzaResource, PizzaResourceDoneable>> crClient;

    void onStartup(@Observes StartupEvent event) {
        System.out.println("Startup");
        crClient.watch(new Watcher<PizzaResource>() { //<.>
            @Override
            public void eventReceived(Action action, PizzaResource resource) {
                System.out.println("Event " + action.name());
                if (action == Action.ADDED) {
                    final String app = resource.getMetadata().getName();
                    final String sauce = resource.getSpec().getSauce();
                    final List<String> toppings = resource.getSpec().getToppings();
                    final Map<String, String> labels = new HashMap<>();
                    labels.put("app", app);
                    final ObjectMetaBuilder objectMetaBuilder = new ObjectMetaBuilder().withName(app + "-pod")
                            .withNamespace(resource.getMetadata().getNamespace()).withLabels(labels);
                    final ContainerBuilder containerBuilder = new ContainerBuilder().withName("pizza-maker")
                            .withImage("quay.io/lordofthejars/pizza-maker:1.0.0").withCommand("/work/application")
                            .withArgs("--sauce=" + sauce, "--toppings=" + String.join(",", toppings));
                    final PodSpecBuilder podSpecBuilder = new PodSpecBuilder().withContainers(containerBuilder.build())
                            .withRestartPolicy("Never");
                    final PodBuilder podBuilder = new PodBuilder().withMetadata(objectMetaBuilder.build())
                            .withSpec(podSpecBuilder.build());
                    final Pod pod = podBuilder.build();
                    defaultClient.resource(pod).createOrReplace();

                }
            }

            @Override
            public void onClose(KubernetesClientException e) {
            }
        });
    }

}

네임스페이스의 모든 것을 정리해 봅시다.

[#delete-pizzas-crds]
[.console-input]
[source,bash,subs="+macros,+attributes"]

oc delete all --all #<.>
oc delete project {section-namespace}
----
<.> 네임스페이스는 보통 내부 리소스를 자동으로 정리하는 경향이 있지만, `finalizer` 문제가 생기지 않도록 먼저 비워두는 것이 대체로 좋은 습관입니다.

[.console-output]
[source,bash]

== Kafka 만들어보기

지금까지 Pizza Operator라는 장난감으로 CRD와 Operator의 동작 원리를 익혔습니다. 이번에는 실제로 널리 쓰이는 오픈소스 Operator인 https://github.com/strimzi/strimzi-kafka-operator/blob/master/install/cluster-operator/040-Crd-kafka.yaml[Strimzi Kafka Operator]를 설치해서, 같은 원리가 실무에서는 어떻게 훨씬 복잡한 시스템(Kafka 클러스터)을 자동화하는 데 쓰이는지 확인해 봅시다.

이 실습을 위해 새 네임스페이스를 생성합니다:

[#create-namespace-franz]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc new-project franz
----

[#kafka-operator-install]
=== Operator 설치하기

OpenShift 웹 콘솔의 __OperatorHub__(Operators → OperatorHub)에서 `Streams for Apache Kafka`(또는 `Strimzi`) Operator를 검색해서 설치합니다.

image:operator-hub-openshift.png[OperatorHub in OpenShift]

=== 설치 확인하기

Operator 설치가 끝났으면, 그 Operator가 실제로 클러스터에 떠 있는지(`csv`, 즉 ClusterServiceVersion)와 ``Kafka``라는 CRD가 새로 추가되었는지 확인해 봅시다:

[#verify-install]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get csv -n operators
oc get crds | grep kafka
----

다른 터미널에서 watch를 시작합니다:

[#watch-pods]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc get pods -w
----

Pizza Operator 때와 마찬가지로, 이제 우리가 할 일은 원하는 상태를 나타내는 Custom Resource 하나를 배포하는 것뿐입니다. Kafka 브로커와 ZooKeeper를 몇 개씩 띄울지 같은 세부 사항은 Kafka Operator가 알아서 처리합니다. Kafka 클러스터를 요청하는 리소스를 배포합니다:

[#deploy-cluster]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc apply -f apps/kubefiles/mykafka.yml
----
