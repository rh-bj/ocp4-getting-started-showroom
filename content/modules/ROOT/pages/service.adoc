= Service
include::vars.adoc[]

Deployment가 만드는 Pod들은 재시작되거나 스케일될 때마다 이름과 IP가 계속 바뀝니다. 그렇다면 다른 애플리케이션이나 사용자는 이 애플리케이션에 어떻게 안정적으로 접근할 수 있을까요? 이때 필요한 것이 __Service__입니다. Service는 레이블 셀렉터로 자신이 대상으로 하는 Pod 집합을 정의하고, 그 Pod들이 바뀌더라도 항상 동일한 이름과 IP(`ClusterIP`)로 접근할 수 있는 안정적인 창구를 제공합니다. 즉, Deployment가 "무엇을 얼마나 실행할지"를 책임진다면, Service는 "그것에 어떻게 접근할지"를 책임집니다.

NOTE: 이 장은 이전 장에서 만든 Deployment를 이어서 사용합니다.

올바른 네임스페이스에 있는지 확인합니다:

:section-k8s: services
:set-namespace: myspace

include::partial$new-terminal.adoc[]

Service를 만들기 전에, 먼저 이전 장에서 만든 Deployment → ReplicaSet → Pod가 여전히 살아 있는지 차례로 확인해 둡시다. Service는 이 Pod들의 레이블(`app=quarkus-demo`)을 기준으로 대상을 찾으므로, Pod가 실제로 그 레이블을 달고 실행 중이어야 합니다.

Deployment가 있는지 확인합니다:

[.console-input]
[source,bash]
----
oc get deployments
----

[.console-output]
[source,bash]
----

quarkus-demo-deployment   3/3     3            3           8m33s
----

----

[.console-output]
[source,bash]

----

Pod가 있는지 확인합니다:

[#have-pods-service]
[.console-input]
[source,bash]
----

----

[.console-output]

quarkus-demo-deployment-5979886fb7-gdtnz   1/1     Running   0          9m17s
quarkus-demo-deployment-5979886fb7-grf59   1/1     Running   0          9m17s
----

이제 Service를 생성합니다. ``selector``는 이 Service가 어떤 Pod들을 대상으로 할지를 레이블로 지정하는 부분이고, ``ports``는 Service가 외부에 노출할 ``port``와 실제 컨테이너가 리슨하는 ``targetPort``를 연결하는 부분입니다.

[#create-service]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Service
metadata:
  name: the-service
spec:
  selector:
    app: quarkus-demo
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
EOF
----

방금 만든 Service를 지켜보면서, 어떤 주소들이 할당되는지 확인해 봅시다:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----

----

[.console-output]
[source,bash,subs="+macros,+attributes"]
----

the-service   ClusterIP   172.231.60.16   <none>        80/TCP    3s
----

== Route로 외부에 노출하기

앞에서 `Service`를 생성하여 여러 Pod에 안정적으로 접근할 수 있는 하나의 접점을 만들었습니다.

하지만 우리가 생성한 Service의 타입은 `ClusterIP`입니다. +
`ClusterIP`는 **OpenShift 클러스터 내부에서만 사용할 수 있는 주소**이기 때문에, 일반 사용자가 웹 브라우저를 열고 이 주소로 직접 애플리케이션에 접근할 수는 없습니다.

[source,text]
------
클러스터 내부

Pod ─┐
Pod ─┼── Service (ClusterIP)
Pod ─┘
------

그렇다면 클러스터 외부의 사용자가 애플리케이션에 접근하게 하려면 어떻게 해야 할까요?

OpenShift에서는 **Route**를 사용하여 Service를 클러스터 외부에 노출할 수 있습니다.

Route를 생성하면 애플리케이션에 접근할 수 있는 **호스트 이름(URL)** 이 만들어지고, OpenShift의 Router가 이 주소로 들어오는 요청을 해당 Service로 전달합니다.

[source,text]
-------------------------------------------
외부 사용자
│
│ http://quarkus-demo-<project>.apps.<cluster-domain>
▼
┌─────────────────────────────────────────┐
│ OpenShift Cluster                       │
│                                         │
│            Router                       │
│               │                         │
│               │ Route                   │
│               ▼                         │
│          Service                        │
│          /   |   \                      │
│         ▼    ▼    ▼                     │
│       Pod   Pod   Pod                   │
│                                         │
└─────────────────────────────────────────┘
-------------------------------------------

각 리소스의 역할을 구분해 보면 다음과 같습니다.

* **Pod**: 실제 애플리케이션이 실행되는 곳
* **Service**: 여러 Pod를 하나의 안정적인 주소로 묶어 주고, 클러스터 내부에서 접근할 수 있게 함
* **Route**: Service에 외부에서 접근할 수 있는 호스트 이름을 제공
* **Router**: Route에 정의된 규칙을 보고 실제 외부 요청을 적절한 Service로 전달

외부 사용자 → Route → Service → Pod
라고 기억하면 이해하기 쉽습니다.

OpenShift 클러스터에는 일반적으로 외부 요청을 처리하는 **Ingress Controller(Router)** 가 기본으로 구성되어 있습니다. +
우리가 Route를 생성하면 이 Router가 Route의 호스트 이름을 확인하고, 해당 요청을 Route가 가리키는 Service로 전달합니다.

예를 들어 `quarkus-demo` Service를 외부에 노출해 보겠습니다.

[#expose-service]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc expose service the-service
oc get routes
----

[.console-output]
[source,bash]
----
NAME          HOST/PORT                                                       PATH   SERVICES      PORT   TERMINATION   WILDCARD
the-service   the-service-{user}-myspace.{openshift_cluster_ingress_domain}          the-service   8080                 None
----

`oc expose service` 명령은 지정한 Service를 대상으로 하는 `Route` 리소스를 생성합니다.
여기서 `HOST/PORT`에 표시되는 주소가 **클러스터 외부에서 애플리케이션에 접근할 때 사용할 주소**입니다.

별도의 호스트 이름을 지정하지 않으면 OpenShift의 Ingress Controller가 사용하는 도메인을 기반으로 Route의 호스트 이름이 결정됩니다. 일반적인 OpenShift 환경에서는 다음과 비슷한 형태를 볼 수 있습니다.

[source,bash,subs="+macros,+attributes"]
----
<route-name>-<project-name>.apps.<cluster-domain>
----

이제 표시된 주소로 요청을 보내 봅니다.

[#curl-services-route]
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
curl the-service-{user}-myspace.{openshift_cluster_ingress_domain}
----

또는 웹 브라우저에서 해당 주소에 접근해도 됩니다.

[.console-output]
[source,bash,subs="+macros,+attributes"]
----
Supersonic Subatomic Java with Quarkus quarkus-demo-deployment-5979886fb7-gdtnz:3
----

지금까지 service를 통한 클러스터 내부에서의 pod 노출과 Route/Ingress를 통한 외부로의 Service 노출을 확인하였습니다.
